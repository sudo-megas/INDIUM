# P23 — the redesign, and the grand update it belongs to

*In progress. This document accumulates as the round runs; it is not finished until the release.*

PXX ended the beta and shipped no redesign, by its own charter. Then the maker studied his fifth
project, **Resonance 1.2.0** — a Tauri/WebKitGTK config vault — and asked what INDIUM could take
from it. The study is why this round exists, and the answer it produced was not the one it set out
with: of the four things Resonance appeared to do better, **two INDIUM already does and beats**,
and of the two real deltas, **the argument against one of them did not survive being measured**.

The maker's ruling on how this lands, verbatim:

> tag changelogs as v2.2 but no release. redesign changes then if any then tag v2.3 quietly again
> with no release. then hardening with everything hard as a diamond. after all everything done tag
> v2.5, release v2.5 only

**So the freeze moves.** It was to be after PXX; it is now after v2.5. Three tags, one release.

| Tag | Carries | Released? |
| --- | --- | --- |
| **v2.2** | PXX's fixes, tests and instrument — the tree as PXX left it | **No.** Tag and changelog only |
| **v2.3** | This round: rounding, the cast, the typeface, the type scale, icons, movable popups | **No.** Tagged quietly |
| **v2.5** | Hardening — PXX Phase 3's audit — then the release | **Yes. The only release** |

The name is this document's own assumption and the cheapest thing here to change. The maker names
his rounds; he ruled out `P23` as a name for **PXX** specifically, not as a number, and 23 is the
next free one. If he wants it called something else, it is a `git mv`.

## What was established before the first line of Stage 2 was written

Four findings, each of which changes the work rather than merely describing it.

### 1. epaint 0.36 has no rounded clipping at all

`ClippedShape.clip_rect` is an `emath::Rect`. `set_clip_rect` takes a `Rect`. There is no rounded
clip anywhere in the crate, so **the plan must not be written around a call that does not exist**.
The mechanisms available for a rounded zone are corner covers painted after the content, or
insetting the fill that would otherwise overhang. Nothing else.

### 2. At R ≤ 8, the table needs no corner covers

The tightest case is the entry table, and it is tight because `egui::Frame` does not clip: it
builds one `RectShape` and paints it *behind* the content (`theme.rs:188-194`), so a selected
first or last row's full-bleed orange fill would overhang a rounded arc.

But `table.rs:48` gives that frame `inner_margin(4)`, and the 2px edge is drawn `Inside`. Content
therefore starts **4px in from the frame's corner on both axes**, and a fill's corner clears the
stroke's inner edge while **R ≤ 8**. At R = 10 it crosses by about half a pixel.

**So R_ZONE = 6 buys the rounding with no covers and 2px of margin left over** — to be confirmed
on screen, because this is geometry on paper and the project has been wrong on paper before.

### 3. `only_three_corner_radii_exist` needs no edit

It asserts against the **constants** `[R_ZONE, R_CTRL, R_POPUP]`, and `install_visuals` never
assigns `R_ZONE` to anything — every widget radius there is `R_CTRL` or `R_POPUP`. `R_ZONE` is
read in exactly one place, `zone()` at `theme.rs:737`. Moving its *value* changes no test.

### 4. No doc-as-test pins the face or the radius sentence — so nothing here strands the suite

This was the sequencing question, and it had to be answered before the order of work could be
fixed. Eight files parse `CORE.md`, and every one anchors on a **structural list**:

| Test | Anchors on |
| --- | --- |
| `lib.rs:76` | `## 3. ARCHITECTURE` — the module table |
| `theme.rs:1520` | `## 6. LOOK` → the `\| Base \|` ground-ladder row |
| `tasks.rs:2118` | `### The method verdicts` |
| `tasks.rs:2186` · `mod.rs:4108` | `### The popups` |
| `keys.rs:135` | `### Keyboard` |
| `sidebar.rs:434` | `**Sidebar**` |
| `settings.rs:273` | `5. **Settings** (`,`)` |

**None reads §6's prose** — not the radius vocabulary at `:377-379`, not the face at `:385`, not
§2's rationale at `:87-92`. So 2a and 2b can be written and go green before the maker touches
CORE; the suite will not sit red on his schedule.

**That is not permission to ship the contradiction.** CORE is design law and it is edited by his
hand alone (`CORE.md:3-5`, `:623`). Code that rounds a zone while the document says *"square for a
zone"* is a tree that disagrees with its own law, and **v2.3 is not tagged until the amendments
below are his.** The work proceeds; the tag waits.

## The CORE amendments, drafted — for the maker's hand only

Four, quoted against the text as it stood. Each is a replacement for a sentence that this round's
code would otherwise contradict.

**All four are now applied**, on the maker's instruction and in two commits: A, B and C together in
`0f104f1`, and E in `57c7f9c` with the code it is bound to. The drafts are left below exactly as
they were put to him — a draft rewritten after approval is no longer the thing that was approved,
and the round document's job is to show what he was asked.

### A. The radius vocabulary — §6, lines 377–379

**Now:**

> The radius vocabulary stays at three values and no fourth — square for a zone, 3px for a row,
> half-height for a control and for a popup, which at the sizes this window uses are the same
> number.

**Proposed:**

> The radius vocabulary stays at three values and no fourth — 6px for a zone, 3px for a row,
> half-height for a control and for a popup, which at the sizes this window uses are the same
> number.

**Why this is one word and not a new clause.** The vocabulary is *already* three values: 0, 3 and
10. Moving the zone off 0 changes one of the three; it does not add a fourth. The sentence's own
count survives untouched, and so does the test that guards it (finding 3 above).

**`:377` is the only place CORE calls a zone square** — grepping the document for *square* and
*corner* returns three hits and the other two are the capsule rule at `:373-374`, which is
untouched. Everything else that says a zone is square is code prose and mine to fix rather than
his: `theme.rs:188`'s *"Zones are square, and that is a decision rather than an omission"* and its
whole doc-comment, and `theme.rs:722`'s *"a fill, a 2px edge all round, square corners"*.

### B. A zone may cast — §6

**The clause that actually forbids it** is not the popup-contrast sentence at `:358-359`; it is
**`CORE.md:399-400`**:

> A folder glyph beside a path that already looks like a path is decoration, and §6 has no room
> for decoration

That is absolute, and `theme.rs:509-510` invokes it by name to refuse a zone shadow: *"a shadow
there would leak onto its neighbour — which is decoration, and CORE §6 forbids it."* A §6 argument
has to be answered in §6.

**Proposed** — `:399-400` stands unchanged, and one sentence joins the told-apart rule at `:358-359`:

> A zone may also cast into the gutter. That is the same rule and not an exception to it: a cast
> says a zone is *above* the gutter, which is a thing the reader has to be told apart, and it is
> not ornament. It is bounded so it cannot become one — one zone's cast never reaches its
> neighbour, and it is measured rather than eyeballed, at **ΔE 8–12 against the gutter it falls
> on**. Under that floor it is invisible and merely costs; over it, it is a glow, and a glow is
> decoration.

**The premise this round set out with was false, and is withdrawn.** I recommended against zone
shadows on the grounds that a shadow on `#180412` would be *"very nearly invisible"*. Measured,
black at the popup's own `from_black_alpha(120)` composites to **ΔE 6.0 over `VOID`** — the same
order as Resonance's own `--spine`/`--bg` step (6.1) and its `--bg`/`--border` (8.1). It is
perceptible. The maker said so before the measurement did.

What *is* true is narrower and is **geometry, not colour**: `blur: 20` with `offset: [0, 8]`
(`theme.rs:511-515`) cannot resolve inside a `GUTTER` of 8 applied as half per side
(`theme.rs:222`) — it reaches the neighbour before it reaches its own opacity. Four pixels is not
enough room for a twenty-pixel blur. Either the blur comes down to about 8, or the gutter goes up.

**The web research the maker asked for.** His two options were a brighter theme with today's tints
used as darkness, or a counter-hue drawn from what colourists actually recommend for aubergine —
he guessed *"cyan, yellow, goldish"*.

- **The curators' answer for aubergine is green, yellow and gold**, plus metallics. His guess is
  what the sources name.
- **The hue maths agrees, and the counter-hues are already in the palette.** `VOID`, `WINDOW`,
  `PANEL` and `CONTROL` all sit at **318°** — a disciplined single-hue ramp. Its complement is 138°
  (green); its triad reaches 78° (gold) and 198°, the last essentially where `POPUP` (207°)
  already is. `ORANGE` is 15.5° and `WARNING` 50.8°.
- **Material's dark-theme guidance** is that elevation on dark is carried by *lighter surface
  overlays* rather than by shadows, and that a tinted shadow should be a darker tint of the surface
  colour rather than black.
- **The halation literature** warns that saturated colour on a near-black ground vibrates, and puts
  the safe floor near RGB 30–40. `WINDOW` (L 11.4%) and `PANEL` (L 14.5%) are inside that band;
  only `VOID` (L 5.5%) is below it — which is an argument for keeping the cast quiet, not for
  skipping it.

Composited over `VOID`, a warm cast is not weak. It is far too strong at every obvious alpha:

| cast | over `VOID` | ΔE | reads as |
| --- | --- | --- | --- |
| black α 0.47 — today's popup | `#0C0209` | 6.0 | depth, subtle |
| gold `#FFD800` α 0.15 | `#3B240F` | 25.6 | louder than `PANEL` vs `VOID` |
| gold α 0.25 | `#52390E` | 40.6 | neon |
| amber `#E8A33D` α 0.25 | `#4C2C1D` | 27.4 | still loud |

The target is therefore **ΔE 8–12 — gold at roughly α 0.05–0.08** — a warm lift in the gutter, not
a colour anyone notices as one.

**The colour cannot be `WARNING`.** `CORE.md:368` already forbids it: *"It is not an accent and
never decorates."* The cast needs its own token, and that token is **not a ground** — the
five-ground ladder and `the_ground_ladder_is_the_one_core_six_lists` are untouched by it.

**Option 1 is kept and not spent here.** The 318° ramp can rise about **+6 lightness points**
before `TEXT_MUTED` on `PANEL` falls through AA 4.5 (5.68 → 4.72 at +6, 4.39 at +8). `TEXT` never
binds — 12.85 at +6. So *"brighter by a wide margin"* means re-deriving the text ramp as well as
the grounds, plus every ink test, both screenshots and §6's palette table — and the measurement
says that still would not be the thing that makes a cast read. It is worth its own round; it is
not worth spending v2.3 on.

### C. The face — §6, line 385

**Now:**

> The face is **Fira Mono Nerd Font**, regular and bold.

**Proposed:**

> The face is **CaskaydiaMono Nerd Font Mono**, regular and bold.

**`Mono`, not `Cove`, and the difference is not cosmetic** — see §2b below. CaskaydiaCove is
the Nerd Font patch of Cascadia *Code*, which ligates; CaskaydiaMono is the patch of
Cascadia *Mono*, which does not. The two differ by one word in a filename and by whether an
archive's contents are drawn correctly.

### D. Why the face may change at all — §2, lines 87–92 — **WITHDRAWN**

This draft proposed rewriting §2's no-ligature rationale on the grounds that the guarantee
came from the toolkit rather than the face. **It was wrong, it is withdrawn, and §2 needs no
amendment at all.** The reasoning is in §2b below; the short form is that `epaint` 0.36
shapes through `harfrust` with HarfBuzz's default features, so a face's `calt` ligatures fire,
and CORE's sentence —

> Fira Mono carries **no ligatures at all**, which is the property that matters here — a
> filename holding `->` must render as the two characters the archive stores, and a face that
> cannot form the ligature cannot get that wrong.

— is exactly right about the mechanism. Only the *name* in it changes, which draft C already
does. Had this draft been applied, the document would have blessed the reasoning that nearly
put a ligature face in an archive manager.

The single-cell requirement is unchanged and was verified before the face was proposed: `'0'`,
`U+F187` and `U+F071` all measure advance **1200/2048** in both `CaskaydiaMonoNerdFontMono`
weights, and all ten Font Awesome icons sit inside the `0xF000..=0xF2E0` range
`every_icon_comes_from_the_font_awesome_range_and_no_second_one` asserts. The advance moves
**0.600 em → 0.586 em**, narrowing every column about 2.4%; widths are measured at runtime, so
they adapt, but the layout has to be re-walked. Licence is **SIL OFL 1.1**, as Fira's was.

Three characters written into §4 are in **neither embedded weight**. Verified twice by
different means: the suite's own `face_covers` cmap reader over both `include_bytes!` faces,

agree on every codepoint below.

| `⇄` U+21C4 | `:301` | **absent** | `keys.rs:38`, verbatim — **tofu in every release** |

The two lines resolve in **opposite directions**, and that is the point of splitting them:

### F. The colour the cast is made of — §6, the palette table

**This draft could not have been written when the others were, and that is the argument for it.**
Draft B binds a cast by its *measurement* — ΔE 8–12 against the gutter — and deliberately names no
colour, because at the time it was drafted no colour existed to name. §2a-shadow then had to pick
one, sample it and pin it, and `GLOW` `#E8A33D` is now in the tree. So §6 is in the position it is
written specifically to avoid: **the palette table names every colour in the window, and there is
now one it does not name.**

Nothing fails without this. The only row any test pins is `| Base |`, through
`the_ground_ladder_is_the_one_core_six_lists`, and a cast is not a ground. That is precisely why it
is worth asking rather than assuming: the document would simply go quiet about a colour, and no
gate anywhere would mention it.

**Proposed** — a new row, placed directly beneath `| Warning |`, so the window's two golds are read
one after the other rather than four rows apart:

> | Cast | `#E8A33D`, and the only colour here never drawn at full strength — how much of it reaches
> the gutter is set by the measurement above rather than written down here, because a hex and an
> alpha would be two pins where the band is one. It is the depth cue the ladder cannot give: five
> grounds say which surface is which, and not one of them says a pane sits *above* the background
> rather than being painted onto it. Gold because the window is a single hue at 318° throughout, so
> a counter-hue has to come out of that hue's own triad — which is also where the colourists'
> answer for aubergine lands, and where the maker's guess landed before either was checked. **It is
> not `Warning`**, the gold in the row above: that colour means something has gone wrong, and a
> cast sitting under every zone in the window would spend it on nothing. It is not a ground either
> — not on the ladder, carrying no text, and no ink is ever measured against it. |

**Why beneath `Warning` and not beside `Popup`.** The prose above the table already ties the cast to
the popup exception, so that argument is made and does not need making twice. The risk this row
actually carries is the other one: two golds in one palette, one of which must never appear except
when something is wrong. Putting them adjacent makes the distinction the first thing a reader meets
rather than something they must hold across four rows.

**What it does not change.** No test, no code, no figure. `GLOW` and `GLOW_A` stay exactly where
they are; the band in draft B stays the binding constraint. This adds a name to a document that
names things.

## Stage 2 — v2.3, the redesign

### 2b. The typeface — and the ligature that nearly shipped

Commit `1997ded`. The maker asked to *"swap caskaydia"*, and what shipped is
**CaskaydiaMono Nerd Font Mono** — the Nerd Font patch of Cascadia **Mono**. The family is
the one he named; the *cut* is the part this section is about, because the round very nearly
chose the other one.

#### The premise was false, and it was the plan's own

This round's plan justified the swap like this: Caskaydia's ligatures cannot matter, because
**egui applies no OpenType shaping at all** — `epaint` was said to resolve glyphs through a
`HashMap<char, GlyphIdResolution>` with no HarfBuzz and no rustybuzz anywhere, so `liga` and
`calt` could never fire whatever the face offered.

**Every clause of that is wrong.** `epaint-0.36.1` depends on **`harfrust` 0.12**, which is a
HarfBuzz port:

| Where | What |
| --- | --- |
| `epaint/src/text/font.rs:361` | `shaper_data: harfrust::ShaperData` — the parsed GSUB/GPOS |
| `font.rs:426` | `ShaperData::new(&font.borrow_dependent().skrifa)` |
| `text_layout.rs` | `shaper.shape(buffer, harfrust::ShapeOptions::new())` |
| `text_layout.rs:227` | *"…ligatures), zero-width 'continuation' glyphs are emitted for the extra"* |

`ShapeOptions::new()` is HarfBuzz's **default** feature set for horizontal text, which has

#### Measured, not reasoned

| Face | Result |
| --- | --- |
| Fira Mono Nerd Font Mono (shipped until now) | **no substitution** in 20/20 |

`www` is the clearest single case: in the Cove cut it becomes one glyph **23 pixels wide**
followed by **two zero-width continuations**, which is epaint's documented ligature mechanism
seen from the outside. `a->b` would have drawn as `a⟶b`. In a program whose whole subject is
the names inside an archive, that is a correctness defect and not a matter of taste.

**The first attempt at this measurement was itself wrong, and the way it was wrong is worth
keeping.** Comparing each glyph's `uv_rect` against the standalone rendering reported *every
face* as substituting — including Fira, and including `www`, which no face ligates. The cause

origin, so the same `w` at x=7.62 and x=15.24 lands in different atlas slots at different
pixel sizes. That is *position*, and the question was *identity*. Switching binning off inside
the probe made the answer unambiguous in both directions. A measurement that agrees with every
hypothesis is not evidence.

### 2d. The icons — and the two premises measurement withdrew

The plan brought three claims to this section. **Two did not survive being measured, and the
third was the real defect all along.** The pattern is 2b's: a premise stated confidently in the
plan, checked before it was acted on, and withdrawn with the numbers that withdrew it.

**The instrument.** Each glyph is laid out at a common **18.2pt** (`13.0 * ICON_SCALE`) with
sub-pixel binning switched off, and the alpha channel of the font atlas is summed over the
glyph's own `uv_rect` and divided by that box's area. "Ink" is therefore *how much of its own
bounding box a glyph fills*. Its limit is worth stating: box-relative ink **conflates a thin
stroke with an outline style** — it cannot tell a hairline solid from a wireframe. What it does
answer is "does this glyph read lighter than the column it sits in", which is exactly what the
premise claimed, so it is the right instrument for this question and not for every question.

### 2a. The zones round — and two constants that were leaning on the zero

`R_ZONE` moves **0 → 6** at `theme.rs:223`, and `zone()` at `:793` stops promising square
corners. That is the whole of the visible change, and it is not the whole of the work: the
constant had been zero since P7, and two places in the tree had quietly come to depend on that
rather than on what the constant means.

#### The hazard did not go away; the arithmetic did

The reason zones were square is recorded at `theme.rs:188-194` and is still true. `egui::Frame`
does **not** clip its children — it builds one `RectShape` and paints it *behind* the content —
so nothing prevents a header row or a full-bleed selection fill from painting straight across a
corner the frame has already cut away. epaint 0.36 offers no rounded clip to fix it with, as
this document's opening section established.

What changed is not the hazard but whether anything actually collides with it. A rounded rect of
radius `R` admits a point `(c, c)` in from its corner when `c ≥ R(1 − 1/√2)` — **1.76px at
R = 6** — and every zone insets its content by `inner_margin + 2` for the stroke:

| Zone | `inner_margin` | content inset (`+ 2` for the stroke) |
| --- | --- | --- |
| sidebar (`sidebar.rs:121`) | `symmetric(12, 14)` | 14 · 16 |
| inspector (`inspector.rs:71`) | `same(12)` | 14 |
| status bar (`mod.rs` `sb_frame`) | `symmetric(12, 10)` | 14 · 12 |
| tray (`tray.rs:26`) | `symmetric(10, 6)` | 12 · 8 |
| **table** (`table.rs:48`) | **`same(4)`** | **6** ← the binding one |

Six clears 1.76 by a factor of three, and the table's content corner lands *exactly on the arc's
own centre* — the furthest inside the shape a corner can be. No corner covers, no inset first
row, no rounded clip.

#### The first alias: a ring that meant "square" and said `R_ZONE`

`table.rs` drew the cursor ring with `theme::R_ZONE` as its radius. The comment above it was
already correct and already gave the right reason — the wash it encircles is
`CornerRadius::ZERO`, and *"a rounded ring around a square wash reads as a mistake"* — but the
constant it reached for describes **zones**, and a table row is not a zone. It had been right by
coincidence for three rounds.

Nothing in the suite reads a painted ring's radius, so shipping the radius move alone would have
produced exactly the mistake that comment names, silently. It is written as
`egui::CornerRadius::ZERO` now (`table.rs:363`), and it rode in the same commit as the move.

**The groundwork counted the readers and got the count wrong.** §3 above says `R_ZONE` is *"read
in exactly one place, `zone()` at `theme.rs:737`"*. The line was right — `zone()` was on it in
that tree — and the count was not. Three places read the constant there: `zone()`, the set
`only_three_corner_radii_exist` validates against (`theme.rs:1434`), and this ring
(`table.rs:356`). §3 was asking a narrower question — whether the test needed editing — and for
*that* question the miscount was harmless, because the reader it missed is not a test. It was not
harmless for the question the same sentence appeared to settle. The missed reader is the one that
would have shipped the defect, and *"read in exactly one place"* reads as a clearance to move the
value.

#### The second: the one thing that paints where no inset reaches

Every zone clears its arc through an inner margin. The status bar's proportion bar **backs out of
that margin on purpose** — CORE §4 puts it *"along the bar's own top edge"*, so it expands by
`inner_margin` to land on the line the 2px stroke draws. That makes it the only thing in the
window painting against a zone's own rect rather than its content lane, and therefore the only
thing the table above does not protect.

The failure is not a crash. At `R_ZONE = 6` the status bar's top edge is straight only between
`left + 6` and `right − 6`; a run starting at the frame's own left begins *inside* the top-left
arc, where the fill has been cut away — so every small fraction would draw a six-pixel orange
stub standing in the notch, against `VOID`. Both ends are pulled in by `R_ZONE` now, and not just
the left, because a proportion whose ends are measured from different insets has stopped being
one.

**Three numbers were written down for this before anybody looked at a window; the fourth is the

### 2c. The type scale — six roles, and the eight numbers they replace

The maker asked for two things in one sentence: *"swap caskaydia + rethinking on the all text
sizes"*, with an example he disowned in the same breath — *"i am anaphoring the targeted process,
so do not take these values as things that i want"*. 2b did the swap. This is the rethink, and the
process he was pointing at is the one the example illustrates: **name the levels, then set them
once.**

#### The census, which the plan undercounted by twelvefold

The plan named nine call sites and a constant. The tree has **a hundred and eleven**, plus two
more behind a file-local constant — and `install_spacing`, the only place the program came close
to stating a scale, set five text styles between them. That gap is where the trouble hid: five
entries naming **three** distinct sizes, and eight drawn.

| Drawn at | Sites | What it was doing |
| --- | --- | --- |
| **28** | 1 | the wordmark in About, beside the 150px mark |
| **23** | 1 | the wordmark in the sidebar, beside the 50px mark |
| **17** | 4, and `TextStyle::Heading` | the name of the thing on screen — a popup's title, the Inspector's subject |
| **16** | 2, and 2 more via `TABLE_PT` | *also* the name of the thing on screen (Open With), *also* an empty state's line, *and* the Measure table |
| **14** | 3 | the section-heading helper — and, typed inline in Create, one heading and one method row |
| **13** | 64 | the value you read (3 of them the icon step, `13.0 * ICON_SCALE`) |
| **12** | 34 | subordinate to the value beside it (1 the smaller icon step) |
| **11** | 2 | a hint and a badge in Create, and nothing else in the program |

Eight numbers, six jobs. The arithmetic of that gap is the whole section. One further `.size(14.0)`
is **not** in that count and is the reason the guard below needed a constant rather than an
exception: the status bar's `Spinner` takes the same method name for a diameter.

#### Three collisions — one role, two numbers, three times

None of these is a matter of taste. Each is a single role that two hands set differently, and each
was invisible precisely because no file stated what the role's size was:

| Role | Drawn at | Where |
| --- | --- | --- |
| the subject's name | **17** and **16** | Inspector ×4 and every `Heading` · Open With's app name, the table's empty state |
| a chooser row whose text is the popup's whole content | **16** and **14** | Measure's table · Create's method rows |
| a subordinate sentence under a heading | **13** and **11** | Bookmarks and Draft · Create's refusal line |

The second one is the one worth pausing on, because the smaller of the two had an *argued* number.
`measure.rs` carried its own `TABLE_PT = 16.0` under the heading **"Sixteen, and the number is the
point of this popup"** — the figures had been 11pt in a lane on a method row when the maker first
saw them, and setting them back at the body size would have moved the problem rather than fixed
it. That reasoning is right and it survives: *larger than a value, smaller than a title* is not a
number a popup needs to own, it is a level the window needs to have. It is `SECTION` now, one
point down, and the popup is still sized by its table rather than the other way round.

Create's method rows were the same shape at **14**, two points below the table they open, and the
`11` beneath them — the AES-256 badge, the refusal sentence — was not a level either. It was a
crowded popup getting quieter to fit.

#### The one value this round did not get to choose

Every size in the window was this round's to move except one. **CORE §6 argues from thirteen,
twice**, and both times it is an argument rather than a description:

- `CORE.md:394` — the icon scale rests on *"about nine points of ink next to a **thirteen-point**
  capital"*, which is why `ICON_SCALE` is 1.4 and not 1.
- `CORE.md:425` — file-type icons are refused because *"at `ICON_SCALE` a **13pt** glyph does not
  fit a 20px row"*.

Move the body size and both sentences stop being true, in a document that is the maker's to edit
and nobody else's (`CORE.md:3-5`). So `BODY` is 13 **because CORE says 13**, not because it
shipped that way — and that is now `core_s_icon_argument_is_the_reason_body_is_thirteen`, which
reads §6 for both phrases and fails from either end: a hand moving the constant, or a hand editing
the sentences without moving it.

**This is also the answer to a question the plan did not ask.** The plan lists no CORE draft for
2c, and the same plan undercounted the call sites twelvefold — so §6 was read rather than
inherited. It is not silent here. It pins `ICON_SCALE` at 1.4 in as many words (`CORE.md:392`,
*"An icon is drawn at 1.4× the size of the text it stands beside"*), which is why the icon step is
still **derived** — `BODY * ICON_SCALE`, `SMALL * ICON_SCALE` — and not a size of its own. No
draft is owed: nothing 2c changed contradicts a sentence in CORE. Everything CORE does say about
sizes, it now says twice, once in prose and once in a test.

#### The scale

| Constant | pt | Role | Moved |
| --- | --- | --- | --- |
| `WORDMARK` | 28 | the wordmark beside the 150px mark | — |
| `WORDMARK_SM` | 23 | the wordmark beside the 50px mark | — |
| `TITLE` | 17 | the name of the thing on screen | the two 16s join it |
| `SECTION` | 15 | the step above a value: a pane's heading, and a chooser row that is a popup's content | **14 → 15**; Measure's 16 → 15 |
| `BODY` | 13 | a value, a label, a button, a table cell, a table header | pinned by CORE |
| `SMALL` | 12 | subordinate to the value beside it | the two 11s join it |

`SECTION` is the one value chosen rather than inherited or unified, and the reason is the
Inspector's own history. CORE §5 records what was wrong with it before P13: *"ten fields in one
size, one weight and three greys, with nothing to say which mattered"* (`CORE.md:204`). A heading
at 14 over a body at 13 is one point — which is to say it was told from the text beneath it by
**weight alone**, and the count of levels had gone back up by one without the hierarchy going with
it. Fifteen gives it two points and a weight instead of a weight and a rounding error.

#### The guard, and the constant it cost

Naming six roles buys one clean afternoon on its own. The program already had five named sizes in
`install_spacing` and still drew eight, because a call site can always type a number, and a
hundred and five of them had. So the scale is held by
`every_drawn_size_comes_from_the_type_scale`, which walks `src/` **at test time** rather than
through `include_str!` — a file list pinned at compile time is the failure it is written against,
and it is how a module added next round is scanned the day it appears.

It matches `.size(` and `FontId::new(` only where a digit follows, skips comment lines because
prose is entitled to quote a number, and asserts the tree it walked is not implausibly small so it
cannot pass by finding nothing.

**It has no exceptions, and that cost a constant.** The status bar's spinner takes `.size()` too —
on an `egui::Spinner`, where it means a **diameter** — so the honest fix was to name it,
`SPINNER_D = 14.0`, beside `CONTROL_H` where lengths live. An allow-list would have been one line
shorter and is where a scale goes to die: the seventh size arrives as the second exception and
nobody re-reads why the first one was granted.

One more coupling made structural while here: 2b's `the_status_bar_row_fits_the_icon_it_was_grown_for`
asserted against a literal `13.0 * ICON_SCALE`. It reads `BODY * ICON_SCALE` now, so if the maker
ever does move the body size, `SB_ROW`'s test re-opens with it rather than silently continuing to
check a number the window no longer draws.

The third is the one that matters most, because it is the direction this project actually drifts:

#### The same paragraph went stale a second time

`install_visuals` carries the argument for why subpixel binning is off, and it turns on the

and recorded that it had been wrong — it said **"12 / 13 / 18"** while `install_spacing` had set

**2c made it wrong again, in a new way**: it said *"the three sizes this window sets"*, and the
scale names six. The conclusion is untouched — 15, 23 and 28 give 8.789, 13.477 and 16.406 px and
not one of the six is integral — but the paragraph that exists to record having been re-checked
cannot be the paragraph nobody re-checks. It now reads six, lists all six, and says that this is
the second time the count was wrong.

It is worth naming as a pattern rather than a typo. Both times the number was **the count of
sizes**, both times it was stale because the scale lived nowhere, and both times it was found by
reading rather than by a test. The guard 2c adds would not have caught either: a comment is prose,
and the test skips prose on purpose. What the guard does is make the next one *findable* — the
sizes are in one place to be counted now.

### 2e. Movable popups — the maker's question, answered by moving one

The maker asked, in as many words: *"Can popups float and be moved by mouse freely?"* The answer
was **no, and not by accident** — but the reason is more specific than "nobody implemented it",
and the fix is not the one line the plan promised.

#### What was actually holding them

All eight `egui::Window` popups called `.anchor(egui::Align2::CENTER_CENTER, egui::Vec2::ZERO)`.
That call is not only a position. `Area::anchor` ends `self.movable(false)` (egui-0.36.1
`area.rs:333-336`), and its own doc says *"Anchoring also makes the window immovable"* in a
sentence directly above `"It is an error to set both an anchor and a position."` So the centring
and the immovability were one call, which is why they were never separated: nobody had asked for
one without the other.

The eight, re-checked against the tree rather than inherited from the plan — seven line numbers
still exact, `mod.rs` drifted `3964 → 3993` under 2b and 2c:

| popup | site |
| --- | --- |
| About · Keys · Settings · Extract | `about.rs:41` · `keys.rs:72` · `settings.rs:34` · `extract.rs:43` |
| Create · Open With · Pending tasks · Open archive | `newarchive.rs:42` · `openwith.rs:30` · `pending.rs:31` · `mod.rs:3993` |

Password (`password.rs:39`) and Measure (`measure.rs:53`) are `egui::Modal`, fixed by
construction and staying that way — CORE §4.10 rests on Measure being the one popup drawn *over*

#### The plan said one line each, and one line each is a regression

> **Making them movable is one line each — remove `.anchor()`.**

Removing it does make them movable. It also stops centring them. With no anchor and no default
position, `Area::begin` falls through to `automatic_area_position` (`area.rs:461`, `:702-719`),
which returns the constrain rect's **top-left plus 16** and then steps sideways once per window
already open. Every popup in the program would have opened in the corner, cascading.

This is not a reading of the source — it was **run**. With `default_pos` taken back out, the test
below reports the popup opening at centre `[300.0 200.5]` against a content centre of
`[600.0 400.0]`: the corner, exactly as the fall-through says.

So the anchor is *replaced*, not removed, by the two calls that say the same thing without the
third meaning — and both live in `theme.rs` as `theme::floating`, because eight identical
three-line incantations is the shape 2c had just finished deleting:

```rust
pub fn floating<'a>(ctx: &egui::Context, title: &'a str) -> egui::Window<'a> {
    egui::Window::new(title)
        .default_pos(ctx.content_rect().center())
        .pivot(egui::Align2::CENTER_CENTER)
}
```

**The rect is `content_rect` because that is the rect the anchor was aligning within** —
`constrain_rect` defaults to `ctx.content_rect()` (`area.rs:439`) — so every popup opens at the
pixel it opened at before, and the change is invisible until someone drags one.

#### Where a popup opens the second time

The plan listed this as undecided. It is decided by egui and the decision is kept: `pivot_pos` is
filled through `get_or_insert_with` (`area.rs:459-462`), so `default_pos` is read **once** and a
popup that has been dragged reopens where it was left. That state lives in egui's memory, and
`eframe` is built here `default-features = false` with only `glow` and `wayland` — **no
`persistence`** — so it dies with the process.

**Moved within a run, centred again on the next launch.** No code makes that happen, which is
exactly why it is written into `floating`'s doc: the next hand to switch `persistence` on for some
unrelated reason will change this without noticing.

That paragraph was written from the source and shipped that way, which is the one thing this
round's gate says it does not do — *measured rather than argued*. So it was measured afterwards,
by closing the popup and opening it again: dragged from `[430 356]` to `[550 296]`, hidden for
three frames, **reopened at `[550 296]`** — the same pixel, not a pixel near it.

#### And the thing that finding drags in behind it

#### What the measurement withdrew

Black at the popup's own `from_black_alpha(120)` composites to **ΔE 6.0 over `VOID`** — the same
order as Resonance's own `--spine`/`--bg` step (6.1). A shadow there is *perceptible*. The premise
was simply false.

**And that 6.0 is itself only good to about half a point**, which is worth noticing before any
weight is put on a modelled figure. It is the number for `#0C0209`, the composite taken with
truncation; round the same composite instead and it is `#0D020A` at **ΔE 5.5**. One byte per
channel, 9% of the answer — because L\* is steep near black, which is where every figure in this
section lives. The *conclusion* survives it, since 5.5 and 6.0 are the same answer to "is it
perceptible". An **alpha** would not have survived it, and that is the section below in miniature.

**What is true is narrower, and it is geometry rather than colour.** `Shadow::margin` in epaint
0.36 is `spread + blur/2 ± offset` per side, so the popup's `blur: 20, offset: [0, 8]` reaches
**18px** below its caster — into a `GUTTER` of 8, applied as half per side. Four pixels of room for
a twenty-pixel blur. That is the whole of the "leak" the old comment described, and it was recorded
as a fact about shadows when it was a fact about two numbers.

At `blur: 8, offset: [0, 2]` the reach is **6 below, 2 above, 4 to each side** — every one under the
8 between two zones. `a_zone_s_cast_stays_in_its_own_gutter` asserts that off epaint's own
`margin()` rather than restating the formula, so an epaint that changed the geometry would be
caught rather than assumed away.

#### The colour, and why it is not `WARNING`

The research the maker asked for came back agreeing with his guess. The grounds are a disciplined
single hue — `VOID`, `WINDOW`, `PANEL` and `CONTROL` all at **318°** — and the curators' answer for
aubergine is green, yellow and gold, which is where that hue's triad lands (78°). Material's
dark-theme guidance arrives from the other end: elevation on dark is carried by a *lighter* surface,
and a tinted shadow should be a tint of the surface rather than black.

So `GLOW`, amber `#E8A33D`. **Not `WARNING`**, though the palette already owns a gold: `CORE.md:368`
forbids it in its own words — *"It is not an accent and never decorates"* — and a cast that borrowed
it would put the wrong-password colour under every zone in the window. It is **not a ground**
either; the five-rung ladder and its test do not know about it and should not.

**Option 1 was kept and not spent here.** The 318° ramp can rise about **+6 lightness points**
before `TEXT_MUTED` on `PANEL` falls through AA 4.5 (5.68 → 4.72 at +6, 4.39 at +8). `TEXT` never
binds — 12.85 at +6. So *"brighter by a wide margin"* means re-deriving the text ramp as well as the
grounds, plus every ink test, both screenshots and §6's palette table, and the measurement says that
still would not be the thing that makes a cast read. Its own round, not this one.

#### The alpha was sampled, and the model was wrong about it

**This is the part the plan was most insistent about, and it earned the insistence.** egui
multiplies alpha in **sRGB byte space**, not linear space, so a modelled composite and the painted
pixel disagree — the round that learned this modelled an orange wash at `#963323` and measured
`#712322`. The modelled table put the alpha at roughly **0.05–0.08**. The screen disagreed:

| `GLOW_A` | strongest gutter pixel | ΔE against `VOID` | |
| --- | --- | --- | --- |
| 18 (α 0.07, the model's answer) | `#1F0A14` | **3.5** | far under the floor |
| 41 (α 0.16) | `#270F15` | **8.0** | in band, at its very edge |
| **52 (α 0.20)** | **`#2B1316`** | **10.1** | the middle of the band |

The reason the model missed is worth keeping: **the strongest gutter pixel receives only about 45%
of the nominal alpha**, because it sits one pixel *out* from the caster rather than at the shadow's
centre, and the blur has already begun falling off. Nothing in the modelled table knew that, because
a table of composites has no geometry in it.

Method, so it can be repeated: build, launch, `spectacle -a` (client area), then the gutter read
pixel by pixel with `magick … txt:`. The profile across the 8px gutter between the sidebar and the
entry table runs **9.5 · 7.1 · 4.1 · 1.1 · 1.4 · 4.3 · 7.4 · 9.5** — symmetric, because both zones
cast into the gutter they share, and near-zero in the middle where neither reaches.

**That peak is 9.5 and the table above says 10.1, and the two are not in conflict.** The table reads
the strongest gutter pixel *anywhere* on the scan line, and it lands in the 4px margin at the
window's own edge rather than in the 8px gutter between two zones — six-tenths of a point apart,
which is where the frame's rect happens to fall on the pixel grid. `CAST_SAMPLED` is that strongest
pixel, so the test measures the loudest the cast ever gets. Both figures are inside the band, which
is the argument for the band being a band rather than a number.

**The instrument was calibrated before it was trusted.** The same script reproduces `PANEL` vs
`VOID` at **21.4** and `WINDOW` vs `VOID` at **15.4** — both figures already on this round's record —
and amber at α 0.25 at **27.35** against the modelled table's 27.4. An instrument that agrees with
three numbers it did not produce is one worth reading a fourth from.

#### Two tests, and neither is sufficient alone

A sampled figure is a photograph: it is evidence of a window that existed once, and it goes stale in
silence. The arrangement is deliberate.

- **`the_cast_lands_in_the_band_core_six_gives_it`** parses the band **out of `CORE.md`** rather than
  restating it — the first doc-as-test in this crate to read a *range*. It is the maker's number and
  it lives in one place. It then checks the sampled pixel is `GLOW` over `VOID` at **one consistent
  alpha across all three channels**, so a screenshot of some other window, or a `GLOW` whose hue
  moved after the sample was taken, cannot pass it.
- **`a_zone_s_cast_stays_in_its_own_gutter`** asserts the reach, and pins **every input a re-sample
  would depend on** — blur, offset, spread and `GLOW_A`. Move one and it fails with an instruction
  to go and measure again, rather than leaving the other test quietly measuring the past.

## Stage 3, prepared — the roster for the walk against v2.3

**The walk is the maker's and this section does not run it.** What it does is answer the question
he would otherwise have to answer by reading the whole plan: *which of the 158 steps does the
redesign put back in play.*

### The generator has nothing to say this time, and that is the finding

PXX's roster was derived mechanically — every step row in `git show 71c7357:build/docs/TESTPLAN.md`
compared against HEAD with `make-checksheet.py`'s own `STEP_RE` — and it found eight steps whose
text had changed. **Run the same comparison from `v2.2` to HEAD and it returns nothing at all:**

```
v2.2: 158 steps   HEAD: 158 steps
added: none   removed: none   changed: none
```

`TESTPLAN.md` has not been touched by this round, because a redesign changes what a step *shows*
without changing what it *asks*. So where PXX's roster was 19 not-green rows plus six silent
stale-greens, **v2.3's roster is silent stale-greens and nothing else** — the sheet will show the
maker a wall of ticks and not one of them is evidence about the window he is about to open. The
regeneration that preserves stored answers, which is the feature that stops 130 approvals having to
be re-earned every time a step is reworded, is here working entirely against him.

### One row that has to be written before the walk, not after

Round 13's four steps check the window at three scales. 2e changed where a popup opens on its

without a note on the step it reads as a placement bug rather than as the documented consequence of
a fix. That note is owed to round 13 before it is walked, and it is the one edit `TESTPLAN.md`
needs for this round.
