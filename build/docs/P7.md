# P7 — Tell them apart, and answer the hand

*Implements CORE.md §6's look — rewritten by the six edits §6 of this file orders — §4's
status bar, the dress of §4's popups, and the one real bug P6's own Deviations left standing.
When this file and CORE.md disagree, CORE.md wins.*

**Goal in one sentence:** every zone in the window is visibly a separate thing, every control
answers the pointer, every popup is unmistakably above what it covers, every heading looks
like a heading, the status bar stops hiding what INDIUM says, and a cancelled copy-out stops
offering half a selection — tagged **`v1.0`**.

P6.md's last line reads *"There is no P7; the P-documents were the road to `v1.0`, and the road
ends here."* It was wrong by one milestone, and saying so is cheaper than quietly numbering
past it. P6 finished the packages, the README and the hardening, and then **the tag was held**:
the maker looked at the program those packages would install and listed five things about the
way it looks, one bug, and the README. Every one of the five turned out to have arithmetic
behind it — §1 is that arithmetic — and shipping `v1.0` before answering them would have meant
packaging a window that had never been measured.

**Not in P7:** hex view (V1.1); the yazi plugin (V1.2); headless subcommands (V1.3); CI as a
**gate** on every push (V1.4 — P6's release workflow stands and P7 adds nothing to it); the
live estimator (V2.0). No new formats, no new popups, no second theme.

## 1. Six grounds, two lines, three radii — and the arithmetic that made them necessary

P7 opened by measuring the five complaints instead of interpreting them. Each one is a number.

| The maker said | What it measured |
| --- | --- |
| *"section borders are not obvious… floating in their domain"* | Adjacent grounds sat **1.06–1.10:1** apart and the hairline between them **1.23:1**. INDIUM separated one zone from the next with a step of fill and an 8%-white line, and neither is strong enough to separate anything |
| *"popup window colors are the same with the main window"* | Literally true. Every popup was `PANEL #3D0D2E` — the identical ground as the sidebar and the Inspector — and every title bar was `#2D2D2D` neutral grey, because `widgets.open` was the one widget state `install_visuals` never set |
| *"triple the height of status bar… 3rd row reserved for progress"* | One content-driven row that **moved** about a pixel when work started, and which drew the progress bar *instead of* `app.status` — which is why P6's four "already running" refusals were never readable |
| *"buttons… clicks doesnt feel anything"* | Press feedback was **one pixel of corner radius**. Hover and press shared a fill and a stroke; `has_focus()` also maps to Active, so a button stayed lit after the click; disabled buttons reproduced the invisible-box bug P5 fixed; and **seven** hand-rolled clickables had zero hover paint, three of them with no cursor change either |
| *"title texts also need to separate themselves"* | Headings rendered at **12.0**, *smaller* than the 13.0 body beneath them, told from content by weight alone, with no rule under any of them. Three helpers drew them and two were byte-identical copies |

`theme.rs`'s own comment on the Base block states the conclusion in one sentence, and the rest
of this section is that sentence expanded:

> P7 measured the old three and found the arithmetic behind every complaint the maker made
> about the look […] The ladder is now the quiet voice that says *which way is up*; the gap and
> the 2px edge do the separating.

### The ladder

Six grounds, each about one and a half times the **linear** luminance of the one below, all on
hue 318–319° — the same family as Canonical Aubergine's 328°, which is the reason CORE §6 gives
for `WINDOW` in the first place.

| Token | Value | What it is |
| --- | --- | --- |
| `VOID` | `#180412` | The gutter every zone floats in. Not a surface — the absence of one |
| `STATUS_BAR` | `#24071B` | Darker than the window, so it reads as a floor |
| `WINDOW` | `#300A24` | **The wells** — the entry table, every text field, the progress track. Anything you look *into* rather than *at* |
| `PANEL` | `#3D0D2E` | The raised zones: sidebar, Inspector, tray |
| `POPUP` | `#4A1038` | A popup covers every zone, so it is lighter than every zone (§3) |
| `CONTROL` | `#571342` | The resting face of every button, and the lightest resting surface in the window |

`CONTROL` being the top of the ladder is what lets a button read the same on the status bar, on
a panel and inside a popup **without knowing which one it is standing on** — three grounds and
one control colour, rather than three control colours to keep in step.

`AUBERGINE #772953` sits above the ladder at **2.13× `CONTROL`** in linear luminance, and that
step is what makes hover felt rather than inferred.

### Two line weights, and the rule that had to change

The old rule is CORE §6's, verbatim: *"1px hairlines at 8% white. Nothing thicker, anywhere."*
The whole of *"section borders are not obvious"* is that sentence being obeyed. So P7 orders its
replacement (§6, edit 3) and the code implements two weights and no third:

| Token | Weight | Against the six grounds |
| --- | --- | --- |
| `HAIRLINE` | 1px at 8% white | 1.23:1 — every rule *inside* a zone: beneath a heading, above a footer |
| `EDGE` | 2px at 22% white | **1.89–1.96:1** — every boundary *around* a zone, a popup or a control |
| `EDGE_HOT` | 2px at 40% white | **2.81–3.73:1** — the same boundary under the pointer, or while held |

`widgets.noninteractive.bg_stroke` stays a hairline and must: it is what every `ui.separator()`
in the program paints with, and those are all rules *inside* a zone. The 2px border is applied
per-frame by `zone()` instead. Putting it in the visuals would have thickened all nine internal
rules and flattened the hierarchy this milestone exists to build.

### The gutter, and square corners

`zone()` is one frame shared by all five of CORE §4's zones: a fill, `EDGE` all round, square
corners, `PAD` of inner margin, and half a `GUTTER` of `VOID` outside it.

- **`GUTTER` is 8 and is spent as `outer_margin` of 4 on every side**, because two neighbours
  each contribute half. The window's own rim is therefore half a gutter, there being nothing on
  the other side of it.
- **`PAD` is 12, and the edge costs 2px per side on top of it.** This milestone got that wrong
  first and shipped the wrong sentence into `theme.rs`'s own doc comment: that
  `StrokeKind::Inside` meant the border was free. It is not. `Frame::total_margin()` is
  `inner_margin + stroke.width + outer_margin`, so a zone consumes `inner + 2 + 4` on every
  side, and any panel given an `exact_size` has to budget all three.

  It was found the only way it could be — by looking. The status bar was sized at 96 by
  arithmetic that omitted the stroke, and on screen its gutter came out at roughly four pixels
  where every other gutter was nine, with the window's bottom rim gone entirely. **`Panel`
  clamps the rect it *reports* to `exact_size` and paints the overflow anyway**, so nothing in
  the panel's own response could have said so. The height is 100, and
  `the_status_bar_is_as_tall_as_it_says` now asserts `content + total_margin == SB_HEIGHT`
  rather than trusting a sum written by hand.
- **Every panel using it also calls `.show_separator_line(false)`.** egui draws its own hairline
  between panels and it would stack with the card's edge: two lines a pixel apart, which is
  worse than either alone.
- **`clear_color` becomes `VOID`.** It was `WINDOW`, which made the gutter the same colour as
  the entry table's well — so the cards had nothing to float above. What shows *between* the
  zones is whatever eframe cleared the framebuffer to, and nothing else.

**`R_ZONE` is 0, and that is a decision rather than an omission.** `egui::Frame` does **not**
clip its children: it builds one `RectShape` and paints it *behind* the content. A rounded table
card would let the header row — and a selected first or last row's full-bleed orange fill —
overhang the arc. Square corners make that impossible, they suit a monospace window, and the
gutter plus the 2px edge do all the floating.

Three radii, declared, where the window previously mixed five that were written down nowhere —
0, 2, 3, 6 and a 9px progress pill:

| Token | Value | Where |
| --- | --- | --- |
| `R_ZONE` | 0 | The five zones |
| `R_CTRL` | 3 | Buttons, chips, hand-rolled rows, the progress track |
| `R_POPUP` | 10 | Popups, menus, the modal, and the title band |

### The zones, one by one

Each panel keeps the reading width it had; the gutter is taken from the panel's declared size
rather than from its content.

- **Sidebar** — `exact_size` 190 → **198**. Eight of those pixels are now the void the card
  floats in, and the content width is the 166 it always was.
- **Inspector** — `default_size` 330 → **338**, `min_size` 260 → **268**, for the same eight.
  The pane CORE §1 calls the main event gives up nothing.
- **Tray** — `zone(PANEL)`, inner margin `symmetric(10, 6)`.
- **Status bar** — `zone(STATUS_BAR)`, and §5 for the rest of it.
- **Entry table** — `zone(WINDOW)`, because the table is a *well* and the other three are raised.

**The one thing it costs, said plainly: the entry table gives up about 16 pixels of width, and
every pixel comes out of the Name column.** The table's inner margin is 4 — not 0 and not 2,
because at either of those the scrollbar and the first row's full-bleed selection fill would sit
on the rim of the edge `StrokeKind::Inside` draws. Half a gutter plus a 4px margin on each side
is ~16px, and Name is the only `Column::remainder()` in the table; Size, Packed and Method are
all `Column::exact`, so the remainder absorbs the whole loss. That is the accepted price of the
floating-card treatment, it is the only thing in this milestone that takes something away, and
it is worth checking by eye before the tag (§8).

### Spacing, declared

`install_spacing` had never been called before P5 and P5 wrote down four values; P7 writes down
the rest, and moves the ones that were hand-tuned at call sites into constants:

| Constant | Value | What it decides |
| --- | --- | --- |
| `GUTTER` | 8 | The gap between two zones |
| `PAD` | 12 | A zone's inner margin |
| `SB_ROW` | 20.0 | One status-bar row — the same 20.0 the entry table uses for a row |
| `SB_GAP` | 4.0 | Between status-bar rows |
| `SECTION_ABOVE` | 14.0 | Above a section heading |

`SECTION_ABOVE` is the one that deletes code: `settings.rs` hand-tuned the gap three times,
`inspector.rs` four, and `newarchive.rs` twice, each with its own `add_space` before a heading.
`theme::section` carries the space itself, so the gap is declared once and the `add_space` calls
are removed rather than doubled.

`style.spacing.interact_size.y` becomes `SB_ROW`, so a button, a status-bar row and a table row
cannot disagree about how tall one line is.

## 2. Controls that answer the hand

*"buttons… clicks doesnt feel anything"* was four faults sharing a symptom.

### The four states

Before P7 the whole of the press feedback was **one pixel of corner radius**: hovered and held
shared a fill, a stroke and a text colour, and nothing moved. Now three channels change on every
transition and two of them are geometry, which is what a finger expects.

| State | Fill | Stroke | `expansion` |
| --- | --- | --- | --- |
| Rest | `CONTROL` | `EDGE` (22%) | 0 |
| Hover | `AUBERGINE` | `EDGE_HOT` (40%) | **+1** |
| Held | `AUBERGINE_LIT` | `EDGE_HOT` | **−1** |

Rest → hover the fill more than doubles in linear luminance, the rim goes from 22% to 40% white,
and the box grows a pixel on every side. Hover → held the fill brightens by half again and the
box contracts two pixels per side, ending a pixel *smaller* than at rest. A control that grows
under the pointer and sinks below its resting size while held is the ordinary physical grammar
of a button, which is why §6's fourth edit puts it in CORE §6's Motion sentence as functional
rather than decorative.

`expansion` is safe at this size, checked rather than assumed: `item_spacing` is (8, 5) and every
frame a button sits in has an inner margin of at least 6, so ±1 never reaches a neighbour.

**`AUBERGINE_LIT #8F3164`, and why pressed-as-darker was rejected on measurement.** The obvious
held state is a darker aubergine. The natural one, `#561D3C`, comes out at **1.038:1 against
`CONTROL`** — a pressed button would have been indistinguishable from a resting one. At this end
of the scale there is only room upward. So the held state is the same colour with the light on:
one meaning at two intensities, never two meanings, which is exactly what §6's second edit asks
CORE to say.

**The stroke is not orange, and this is the second time that has had to be said.** P5 §3 removed
an orange `widgets.active.bg_stroke` for the reason that `widgets.active` is the being-pressed
state of *every* widget, so an orange rim there put CORE §6's accent around Cancel, Discard,
Clear list and the checkbox — orange as a generic press affordance, which is decoration, which
the comment on `ORANGE` forbids in its own words. `EDGE_HOT` is the answer both times.

### Focus, and why a button was still lit a minute later

egui maps `has_focus() || clicked()` to the *active* state and offers no `widgets.focused` to
separate them, so a clicked button stayed lit until something else took focus. INDIUM has no Tab
navigation — CORE §4's keyboard table is all bare keys — so a button has no business keeping
focus. `theme::button` surrenders it on click, which costs nothing and fixes it exactly.

### The disabled ghost

`disable()` multiplies the painter's opacity, and at egui's default of 0.5 an inactive fill over
a popup blended away to nothing: **the invisible-box bug P5 fixed, recurring in the one state
nobody looks at.** Two changes, and the second is the one that matters:

- `disabled_alpha` is **0.85**, not 0.5.
- The disabled arm of `theme::button` is an **outlined ghost** — transparent fill, 1px `EDGE`
  outline, `TEXT_MUTED` label — rather than a filled box. A fill at any alpha blends toward
  whatever is behind it, which is how the bug got in the first time. An outline says "off" by
  weight instead of by opacity, and measures **1.73:1** on its rim and **4.07:1** on its label.

Every disabled control in the program goes through this: `Add` in Settings and in New Archive,
`Create` while there is no name and no directory, and `OK` in the password modal.

### The seven hand-rolled clickables

Seven kinds of clickable row were hand-rolled across the program and **not one of them read its
own `Response`**, so the fill was a function of application state only and hovering painted
nothing. Three had no cursor change either.

| Where | What it did before |
| --- | --- |
| Sidebar sections and actions | Fill from `active` alone; a trailing `ui.interact` for the click |
| The staging tray strip | *"The strip itself is a button"* (CORE §4) and it was one only in the sense that a click reached it |
| New Archive method rows | Fill from `app.new_method` alone — and the unselected fill was `PANEL`, which *was the popup's own ground*, so an unselected row was a box you could not see |
| Open With candidate rows | No fill in any state and no cursor at all — a list built to be clicked, giving no sign that it could be |
| Recent-files rows | `ui.interact` over a plain frame |
| Bookmark rows | The same |
| Pending-task rows | The same |

`theme::row` replaces all seven: `active` → `AUBERGINE`, held → `AUBERGINE_LIT`, hovered →
`CONTROL`, otherwise transparent, `R_CTRL` corners, and a pointing hand.

**It is built on `UiBuilder::sense`, and that is what keeps the inner `×` buttons working.** The
row's sense registers *below* everything added inside it — egui's `Ui::new_child` says so in as
many words: *"Register in the widget stack early, to ensure we are behind all widgets we
contain"* — and the hit test hands a click to the topmost sensing widget under the pointer. So a
`×` inside a task row takes its own click and the row does not also fire, and the tray's
`if !apply && !discard` guard is deleted with nothing replacing it: Apply and Discard are real
`Button`s and beat the strip by construction rather than by a bool the next edit could forget to
update.

**Two consequences that are not obvious and are both load-bearing.**

- **`selectable_labels` goes off inside a row.** egui's default is `true`, which makes every
  plain `ui.label` allocate its rect with `Sense::click_and_drag()` so its text can be selected —
  which out-ranks the row beneath it. A selectable label would have swallowed every click that
  landed on the words *"Recent files"*, leaving only the padding around them working. Nothing in
  a row is text anyone wants to select, and the `Ui`'s style is clone-on-write, so the flag dies
  with the row.
- **An unavailable sidebar section is not a control and does not become one.** `theme::row` has
  exactly one mode — *this is clickable* — so the disabled arm keeps a plain frame: muted ink, no
  hover fill, no pointing hand, and a response that can never report a click. `ROW_PAD` is shared
  between the two arms so they cannot drift apart in height. That is the behaviour P1 gave it,
  preserved rather than restyled.

### The table's own rows

The entry table does **not** use `theme::row`, and its hover wash is `ROW_HOVER` — 7% white —
rather than Aubergine. Aubergine means *the active item*, and a full-height table where every row
you pass turns Aubergine means nothing at all. Against the orange selection fill `ROW_HOVER`
measures **1.40:1**, so a hovered row and the row cursor never read as the same thing, and
passing the pointer over the table cannot obscure where the selection is.

### The caret

egui's default text cursor is a 2px `#C0DEFF` pale blue — off-palette, and the one stroke in the
program that broke CORE §6's line rule *before* P7 rewrote it. Only the colour changes: a 1px
caret renders as a grey smear on a 1× display, so the weight stays at 2 and it takes `TEXT`.

## 3. Popups that are not the window

*"popup window colors are the same with the main window"* was literally true, in two ways at once.

**One line fixes the ground for all eight.** `Frame::window` and `Frame::popup` both read
`window_fill`, and `Modal` and the context menu resolve to `Frame::popup` — so `v.window_fill =
POPUP` in `install_visuals` is the whole of it: every popup, the password modal and the
right-click menu, with no per-file work. `window_stroke` takes `edge()` and
`window_corner_radius` and `menu_corner_radius` take `R_POPUP`.

**Raised, not recessed, and the choice was made rather than defaulted.** A darker popup was
considered. The window already teaches *lighter is closer* with `WINDOW → PANEL`, so a recessed
popup would have to un-teach it, and it would cost contrast on the pane CORE §1 calls the main
event. `POPUP #4A1038` is lighter than every zone because a popup covers every zone.

**The title bar, and the one widget state nobody had set.** egui fills a window's header with
`widgets.open.weak_bg_fill` when that window is the topmost layer, and `Visuals::dark()`'s value
is `#2D2D2D` — flat neutral grey, in a program with no neutral grey anywhere else. That is the
entire reason every popup wore a grey band: `install_visuals` set `noninteractive`, `inactive`,
`hovered` and `active`, and never `open`.

It takes **Aubergine**, which is CORE §6's existing meaning used exactly — *this is the active
item*. And **the fact that egui lights the band only on the top layer is a feature, kept
deliberately**: when the password modal opens over New Archive, New Archive's band drops back to
plain `POPUP` and the modal is unmistakably the thing holding the keyboard. Nothing had to be
written to get that; it had to be noticed and not fought.

**A popup is the only thing that casts.** `window_shadow` and `popup_shadow` are both an
offset-8, blur-20, `from_black_alpha(120)` drop. P5 turned both off without recording a reason,
which reads as part of its "write the defaults down" sweep rather than a decision. Zones cast
nothing, and that is the decision: a zone sits *in* the gutter, not above it, and a shadow there
would leak onto its neighbour — which is decoration, and CORE §6 forbids it. A popup genuinely is
above something else, so it is the only thing in INDIUM that gets one.

**The scrim.** egui's modal backdrop is `from_black_alpha(100)`, and pure black over an aubergine
window pulls the whole thing grey at the exact moment the user is being asked for a secret.
`SCRIM` is `VOID` at 78% — the window stays in its own family, and the dimming is nearly twice as
deep, which is what *"everything else is unavailable"* should look like. It is written
premultiplied because `from_rgba_unmultiplied` is not a `const fn`: `VOID`'s channels each scaled
by 200/255, which is the same colour written the way a `const` can hold it.

## 4. Headings that look like headings

*"title texts also need to separate themselves"*, and the measurement is the whole complaint: a
heading rendered at **12.0** against a **13.0** body. It was smaller than the text it introduced,
and the only thing telling it from content was weight.

**The type scale, four roles and not ten sizes.** egui's defaults had quietly owned the two most
prominent sizes in the program — 13.0 for every unstyled label and button, 18.0 for every popup
title — neither of which appeared anywhere in the source:

| Role | Size | What it is |
| --- | --- | --- |
| `Heading` | 17.0 | A popup title, which egui resolves for us |
| `Body` | 13.0 | The value you read |
| `Button` | 13.0 | Matched to body, so a button never shouts |
| `Small` | 12.0 | A label or a hint |
| `Monospace` | 13.0 | The table, the Inspector |

A section heading is **14.0 bold in `TEXT`** — above the body it opens, which is the arithmetic
the complaint was pointing at.

**Three helpers drew headings and two were byte-identical.** `inspector.rs::section_label`,
`newarchive.rs::group` and `table.rs::header`. The first two were the same twelve lines twice
over; the third drew 17.0 unbolded with no rule at all, which is a *value's* size used as a
heading. All three are deleted and two functions replace them.

**The rule: a heading takes a rule when it opens a list of siblings, and none when it names a
single object.** The rule *is* the top edge of the group; where there is no group there is no
edge to draw.

- `theme::section` — the heading and a `Separator` beneath it. Checksum, Times, Ownership and
  Other in the Inspector; PRESET and METHOD in New Archive; Extract, Bookmarks and Recent files
  in Settings and the two list views.
- `theme::section_bare` — the same heading where the container already draws the boundary. A
  popup's own title bar; *"The licence, in full"* in About, because a licence is one document and
  not a list; a card whose name is a value rather than a label.

**The password modal is the exception, and it is one deliberately.** A `Modal` draws no title
bar, so its first label *is* the title and it takes the `Heading` style every other popup's title
is drawn in — not `section_bare`, which is 14.0 with a gap above it and would give the one popup
that cannot draw its own title bar the smallest title in the program.

One thing that had to be checked rather than assumed while doing this: `RichText::strong()` is
not a weight change. `strong_text_color()` resolves to `widgets.active`'s colour, which this
theme sets to the same `TEXT` that `override_text_color` already forces — so `.strong()` renders
identically to ordinary text, and always did. Bold is `theme::bold()`, the second embedded face,
and nothing else.

## 5. The status bar: three rows that never move

*"triple the height of status bar… 3rd row reserved for progress"* is the one complaint that
names its own fix, and it also hides the milestone's most useful bug.

**The old bar moved.** It was one row, content-driven. A `Cancel` button and a progress bar are
taller than a label, so the floor of the window rose by about a pixel the instant work started
and dropped back when it finished, taking every zone above it with it. The panel is now
`exact_size(96.0)` and `resizable(false)`: 3 × `SB_ROW`(20) + 2 × `SB_GAP`(4) + 10 + 10 of inner
margin = 88, plus the 4 + 4 of `zone()`'s outer gutter = 96. `exact_size` counts the frame's
margins, so that number is the whole panel including the gutter it floats in. Idle, listing and
rebuilding are now identical heights, and this is a checklist item because it is the kind of
thing only measurement or a screenshot catches.

**The bar is shown before the sidebar, and the ordering is the whole of it.** egui gives an
earlier panel priority over the space, so the bar now spans the full window and the sidebar stops
on top of it rather than running past it to the bottom edge. Row 3 is the *program's* progress —
a rebuild is not the table's work and neither is a copy-out — so the zone that carries it has no
business being inset under one of the four it reports on. A floor that reaches both walls is also
what makes the other four read as cards standing on something.

**Three rows answer three questions and never each other's.**

1. **What is open.** The archive's name on the left, because that is the answer to *"which window
   is this"*; its format and filter beside it; the directory on the right, truncated rather than
   wrapped, because it is the longest thing in the bar and the least urgent, so it is what gives
   way when the window narrows. A second line has nowhere to go in a lane of fixed height, and a
   path elided at the end still says which tree the archive lives in. **This also closes P6
   Deviation 21** — the long-name overlap that photographing the program found — because the name
   and the directory are no longer competing for one row.
2. **The numbers, and the voice.** Entry count, real → packed with ratio, the selection count,
   and `app.status` right-aligned and **drawn unconditionally**.
3. **Progress, and nothing else.**

**Row 2 is the bug fix, and it is worth naming as one.** Until P7 the status text lived in the
`else` of a branch that `progress.is_some()` pre-empted, so every sentence INDIUM says *while
something is running* was written to a field nothing drew. P6 Deviation 16 recorded this as
known and unfixed — *"All four 'already running' sentences are written while a progress bar is on
screen, and the status bar draws the bar instead of the status text"* — and judged redesigning
the bar larger than the change it was ordered inside. The redesign is this milestone, so the
refusals become readable as a side effect of the maker's third complaint. Nothing in row 2 may
consult `progress`; that is row 3's job and only row 3's.

**Row 3, and three details that each cost a line.**

- **The track is `VOID`.** `extreme_bg_color` is `WINDOW`, which is *lighter* than the floor this
  bar paints — and a rail lighter than the surface it lies on reads as raised, which is exactly
  backwards for a groove that fills up. `VOID` is the only ground darker than `STATUS_BAR`. The
  override is scoped to the row: every text field in the program wants the lighter well.
- **No `.text(...)` on the `ProgressBar`.** It paints its label with `override_text_color`, which
  this theme sets to `TEXT` — **2.4:1 on Ubuntu Orange**, and unfixable from outside the widget.
  The phase and the count are drawn as ordinary labels on either side of the bar, where they are
  read against the bar's own ground. This is the measurement §6's fifth edit puts into CORE §4,
  because it is the reason the bar's shape is what it is.
- **Idle draws a hairline down the middle of the empty lane.** A row that is simply blank reads
  as a layout mistake; the emptiness is the answer, and a rule says so. CORE §6 — 1px, inside a
  zone.

The lane is laid out right-to-left so Cancel and the count take their space from the right edge
first and the bar fills whatever is left, which is what lets it be as wide as the window rather
than the fixed 160px stub it was. `progress` is consulted before `listing`, as the old bar did:
`E` works while a listing is still streaming in, and when both are true the Cancel has to reach
the worker that is writing files.

Two spacing values are set inside the panel and both are arithmetic, not taste. `item_spacing.y`
becomes `SB_GAP`, because egui's 5.0 makes three rows 70 tall in a lane that is 68 — and the
third row is the one that gets clipped. `button_padding.y` becomes 1.0, because `interact_size.y`
is `SB_ROW` and the theme's 3px of vertical padding would push Cancel to 23 and take the row with
it, in a panel that can no longer grow to absorb it.

## 7. A cancelled copy-out offered half a selection

The one real bug, recorded as known in P6 Deviation 16 and fixed here.

`arch::extract` returns `Ok(written)` when the cancellation flag is set — a partial count, from a
function whose success and whose interruption are the same variant. The completion arm therefore
could not tell "finished" from "stopped halfway" by the result alone, so P6 §6.9 made it read
`self.cancel` instead. **That field is replaced by `open_archive` before the message arrives**,
and by the next `spawn_extract` as well, so the read answers for whichever operation is newest
rather than for the one that just landed. Cancel a copy-out by opening another archive and the
arm reads *"not cancelled"* and puts half a selection on the clipboard as though it were whole.

**Apply was always immune, and the reason is the fix.** `tasks::apply`'s worker decides with its
own owned `Arc` — the one moved into the closure, which nothing can swap — and reports
`ApplyMsg::Cancelled` in band. `tasks.rs` names the defect on the other side in the doc comment
over that very enum, while it still stood:

> `Cancelled` is a variant of its own, unlike `ExtractMsg`, where its absence means a cancelled
> extraction is indistinguishable from a finished one. An Apply that stopped early must never
> look like an Apply that succeeded.

So the fix is not a new mechanism. It is the one already in the file, applied to the other half.

- **`ExtractMsg` gains `Cancelled { written }`.** The doc comment on the variant cites the
  `ApplyMsg` comment above as its precedent, because that is where it came from.
- **The worker decides, with the `Arc` it owns.** The closure already holds its own clone; it
  reads that and sends `Cancelled` or `Done`, and the UI reads no flag at all.
- **`ExtractMsg::Done` now means done.** The arm loses its `cancelled` read and its `_ if
  cancelled` guard, and runs its post-step unconditionally.
- **The `Cancelled` arm drops the post-step rather than running it.** Half a selection is not what
  `Ctrl+C` asked for, and half a file is not what Open With would hand an application — and
  neither can tell, because a partial extraction leaves whole files on disk beside the missing
  ones. What was *asked for* decides what the sentence can honestly say: `"Cancelled. Nothing was
  extracted."` when nothing was written; `"Cancelled after N entries. Nothing was offered."` when
  the result was going somewhere; `"Cancelled after N entries; what came out is still in the
  destination."` for a plain extract, where the files the user asked for are where the user asked
  for them and saying otherwise would be a different lie.

**And `open_archive` stops being a rug-pull.** It is reached from seven places — the command
line, a drop, `Ctrl+O`, a click or `Enter` on a recent, the password prompt's List resume, and
Apply's own re-open — and it checked nothing at all. Its first two lines raise the old flag and
hand the window a new one, which stops a running extraction dead in the middle and leaves the
user with a directory of half a selection under a status line about a different archive. It now
asks `work_running()` **first, before anything is cleared**: a refusal that has already wiped the
selection, the cwd and the entry list is a rug-pull with an apology attached.

Two boundaries drawn deliberately while doing that:

- **A listing is not work in this sense** and is still cancelled without ceremony. Nothing has
  been written, CORE §1 gives the window one archive, and opening the next one is the whole of
  what the user asked for.
- **The refusal is only useful because of §5.** `work_running`'s two sentences are set at exactly
  the moments row 2 of the old bar was hiding. The fix and the redesign are one change wearing
  two names, and neither is worth much without the other.

## 8. Fixtures and tests

**No new fixtures.** P7 adds no format work.

`theme.rs` gained **eight unit tests**, and each is named after the bug it prevents rather than
the property it checks — a test called `contrast_is_adequate` tells the next reader nothing about
why anyone bothered.

| Test | What it pins |
| --- | --- |
| `the_ground_ladder_only_ever_goes_up` | The six grounds are strictly increasing in luminance, and `CONTROL < AUBERGINE < AUBERGINE_LIT` above them. The ladder is the thing that says which way is up; an inversion anywhere in it would say the opposite in one place and nowhere else |
| `no_two_grounds_are_the_same_colour` | **The regression that would recreate P5's invisible button** — a surface the same colour as the thing behind it. It is a pairwise inequality over all six, not a check of the two that happen to be adjacent, because the bug was a *popup* the colour of a *panel* |
| `text_is_legible_on_every_ground` | `TEXT` ≥ 7.0:1 and `TEXT_MUTED` ≥ 4.5:1 against all six. Adding a seventh ground later is exactly when this stops being obvious |
| `the_four_control_states_are_four_colours` | *"clicks doesnt feel anything"*, pinned: the three interactive fills are pairwise distinct, hover expands and held contracts. The old theme would have failed on the fills alone |
| `the_popup_title_bar_is_not_egui_grey` | Named after the bug — `widgets.open.weak_bg_fill` is neither `Visuals::dark()`'s `#2D2D2D` nor `window_fill`. The first assertion catches the state going unset again; the second catches it being set to the popup's own ground, which would be invisible rather than wrong-coloured |
| `no_stroke_is_thicker_than_two_pixels` | CORE §6's rewritten Lines rule, over all ten widget strokes plus `window_stroke`, `selection.stroke` and `text_cursor.stroke`. The caret is in that list because the caret is what broke the old rule |
| `only_three_corner_radii_exist` | Five undeclared radii became three declared ones, and every corner is one of them — and is the same on all four corners |
| `orange_has_not_spread_into_the_widget_states` | P5 §3 and P6 §6.6's invariant, pinned at last: orange reaches no widget fill and no widget stroke, and `selection.stroke` still *is* orange. Both halves matter — the point is not that orange is rare, it is that orange is exactly where CORE §6 put it |

The arithmetic they rest on is ten lines of WCAG relative luminance written in the test module.
CORE §2 would not admit a crate for arithmetic that small, and `util.rs` writes its own CRC32
table for the same reason.

**`tests/cancel_path.rs` is new, for §7's fix**, taking its shape and its precedent from
`write_path.rs`'s `a_cancelled_apply_leaves_the_original_untouched_and_says_so` — the test that
pins the half of this mechanism which was already right.

It gets its own file rather than a case in `read_path.rs` because it is not about reading. It is
about one contract on `arch::extract`, and **the honesty note at the top of the file is the
reason there are four tests and not one**: `ExtractMsg::Cancelled` is never constructed inside
`arch::extract` at all. The only place that builds it is `spawn_extract`, which calls `extract`,
gets back `Ok(written)`, and *then* decides by reading its own cloned `Arc` — UI-thread code with
no window to run it against. So rather than assert a message the library cannot send, the file
pins the fact the variant exists to paper over, and the disk state that fact is about:

- `an_uncancelled_extraction_writes_every_selected_entry` — the control. Without it the three
  below could all pass against a function that never writes anything
- `a_precancelled_extraction_writes_nothing_and_sends_no_progress` — the flag is honoured before
  the first member, and no progress message is sent for work that did not happen
- `ok_zero_alone_cannot_tell_a_cancelled_extraction_from_an_empty_selection` — **the test that is
  the bug.** Two runs, one cancelled and one asked for nothing, produce the identical `Ok(0)`.
  That ambiguity is not a defect in `extract`; it is the reason the decision has to live where
  the flag is owned. If `extract` ever learns to report cancellation itself, this is the test
  that fails and says so
- `a_cancellation_landing_mid_run_never_leaves_a_truncated_file_and_its_count_matches_disk` — what
  a cancelled run leaves behind is complete files only, never a half-written one, and the count it
  returns matches what is actually on disk. §7's third sentence — *"what came out is still in the
  destination"* — is only true because of this, and a sentence in the status bar that rests on an
  unchecked property is the failure this project names as unforgivable

## 9. The release ritual

```
cargo fmt
cargo clippy -- -D warnings
cargo test
cargo build --release
./build/check-deps.sh
git add -A
git commit -m "P7: the README, photographed again"
git push

# The workflow is proven before the tag exists. Dispatch release.yml by hand on
# master and confirm the bookworm build, make-deb.sh and verify.sh all go green.
# The first run of a release workflow must never be the release — and P6
# Deviation 19, where exactly that happened, is why the sentence survives into
# a milestone that touches no workflow at all.

git tag v1.0
git push origin v1.0

# Arch. makepkg builds from the pushed tag, so the tag comes first — this is not
# packaging the working tree, and a dirty tree cannot leak into a release.
( cd build/package && makepkg -f )

# Debian. The binary comes from the workflow's debian:bookworm container, because
# the Arch build machine's own binary imports GLIBC_2.43 and bookworm has 2.36.
# make-deb.sh assembles the package from whatever binary it is given, anywhere —
# which is what lets the local .deb below exist to fail the raised gate.
./build/package/make-deb.sh target/release/indium         # the local one, to prove the gate

# Both artefacts, proved without installing either.
DEB_TARGET_GLIBC=2.43 ./build/package/verify.sh   # the local .deb, gate raised
./build/package/verify.sh                         # the CI .deb, gate at 2.36
cargo test -- --ignored

tar czf indium-1.0-x86_64.tar.gz -C target/release indium
```

**`Cargo.toml` moves nowhere.** It has read `1.0.0` since P6's first commit, for the reason P6 §9
gives — the packaging scripts read the version out of it — and P7 is the milestone that finally
pushes the tag it was moved for. Every P before P6 changed the version; this one changes it least
of all, by changing nothing.

GitHub release on `v1.0`, with `indium-1.0.0-1-x86_64.pkg.tar.zst`, `indium_1.0.0-1_amd64.deb`
and `indium-1.0-x86_64.tar.gz` attached.

**Not a pre-release**, and P6 §9's argument stands word for word: `v0.2` through `v0.5` were
pre-releases because each shipped a program CORE §7 said was not finished yet. CORE §7 calls that
table *"the road to v1.0"* and — after §6's sixth edit — ends it on P7's row. Marking the end of
the road "pre-" would say the road is not finished, contradicting the document that defines when
it is. If something is not ready to be called 1.0, the honest move is not to tag 1.0; it is not
to tag it and disclaim it.

Notes in the house voice: what changed about the way the program looks and why each change is a
number rather than a preference; the two packages and where each runs; the glibc floor of every
artefact stated plainly; RAR's deliberate absence; and the sentence that the tag was held for one
milestone because the program did not yet look like `v1.0`.
