# P15 — the audit's open ledger

*No feature in it. Five defects that were open — four written down somewhere and left, one that
nobody had found — a line in the record that was false, and V1.4's gate brought forward.*

## Why this round and not the next one

`v1.0.0-4` shipped green and its release note names the condition for leaving beta: *"the `1.0`
line stays one until the design work it is named for has been in real hands."* That gate is a
testing round, and a testing round is the maker's to run, not this document's.

What makes a build worth handing to real hands is not another feature. It is an empty ledger and
a record that is true, and INDIUM had neither. The hex view and the table's icons are both good
rounds and both still there afterwards; they would have been built on top of a milestone document
that said something untrue about itself, which is the one kind of debt this project cannot carry,
because the documents are the whole of its authority.

## What was fixed

1. **The Preview survived Apply, and so the Inspector lied.** The one nobody had found.
   `ApplyMsg::Done` re-opens the archive in this window on purpose, and its own comment gives the
   reason: *"the Inspector is the point of this program, and it must not describe a file that no
   longer exists."* But `open_archive` clears nine things and `forget_preview` was not among them,
   and `request_preview` returns early when the path it is asked for is the path it is already
   showing. So: preview a file, stage a replacement of that same file, Apply — and the Preview
   goes on showing the bytes the rebuild threw away. The image texture, keyed by archive path and
   entry path, was never forgotten either, so a replaced picture stayed on screen out of egui's
   cache. **The half of the Inspector that the re-open exists to protect was the half it missed.**
   `crc_of` was already being cleared on that line; the preview is cleared beside it now, because
   a computed checksum and a previewed body go stale together and there is no case where one is
   current and the other is not.

   The reach is exactly one path and worth naming: `window::destination` keeps `open_archive` in
   this window only when the path resolves to the one already open, which is the Apply reload and
   the password retry. Every other open is a second window per §1, and a second process has no
   preview to be stale.

2. **Two points of popup ground under every foot.** `PAD` is 12, `window_margin` read 14, and
   `foot` pulls its band back by `PAD` — so the band fell two points short on the left, the right
   and the bottom of all nine popups. A band with a gutter down both sides is a panel, which is
   the thing `foot`'s doc comment exists to say it is not. P13's audit found it and wrote it at
   the code site rather than spend it in a milestone that had been asked to stop moving; that was
   the right call, and this is the milestone it was deferred into. The two are one number again.

3. **The numbers hold their columns.** CORE §4 has asked for it since P7 gave the status bar its
   hierarchy — *"Sizes, counts and ratios are right-aligned to fixed positions and do not move as
   their digits change; a number that jumps as it counts cannot be read while it counts."* P12
   recorded that the code did not do it. P13 said it had written that down where the code is. P15
   is where it was done, and where the claim was straightened.

   The mechanism is worse than it sounds: `aggregate` is recomputed every frame from the entries
   that have arrived, so during a listing the count and the real size **both** grow, and the ratio
   walked a cell to the right on every tenth entry — a number nobody could read while it counted,
   which is the exact sentence CORE wrote. The fields are padded rather than measured, because
   §6's face is the `Mono` cut and a character there *is* a column.

   One thing the lanes taught: `format_bytes` is widest at `1023.9 KiB` — ten — and **not** at the
   top of its ladder, where one would look for it. A value only ever reaches four digits before
   the unit changes beneath it, so every rung above KiB is the same width or narrower, and
   `u64::MAX` itself is merely `16.0 EiB`, which is eight. The first draft of the test asserted the
   opposite and failed, which is why the lane is now pinned by a sweep across every rung and both
   sides of every boundary instead of by an argument that sounded right.

   **Said plainly, because it is a visible consequence and not an accident:** the count is
   right-aligned in its lane like everything else, so a small archive reads with a few cells of
   space before its first digit while the word *entries* holds still. That is what the document
   asks for in the words it asks for it in. If it reads wrong at the window, that is a design note
   for a later round — not a licence to reinterpret the line into something easier.

4. **A comment that was true, and then was not.** `MIN_W` told the reader that the sidebar
   *"scrolls against a track that is always drawn."* Fifty lines away, `sidebar.rs` says
   `AlwaysVisible` was tried, worked, and was rejected for leaving a track down a zone with
   nothing to scroll — and sets `ScrollStyle::floating()` on the next line. P14 wrote both.

   This is precisely the class of defect that `b0baa52` — *"nineteen things the rollback and its
   ancestors left untrue"* — was written to eliminate, reintroduced one milestone later by the
   same hand that eliminated it. Worth keeping for that reason alone: **a sweep is not a habit.**
   Nineteen comments were made true once; nothing about doing that made the twentieth true.

5. **`lock_name_for` was not injective.** Every character outside `[A-Za-z0-9._-]` became a bare
   `%`, which threw away the thing it was escaping: `açık.zip` and `aşık.zip` in one directory both
   came out `a%%k.zip.lock`, so one window told the other it was rebuilding an archive it had never
   opened. Recorded since P11 and carried as low severity, correctly — nothing is lost and nothing
   is corrupted, a person is merely told something false and stopped from working.

   Now `%XX` per UTF-8 byte. It costs two characters and buys the only property a lock name needs.
   `%` is itself outside the set and becomes `%25`, or the escape would be ambiguous with a
   literal. The output is ASCII by construction, so the 180-byte tail cut cannot land inside a
   character; it can land inside an escape, which costs nothing the cut did not already cost —
   two paths alike in everything but their first bytes shared a lock under the old scheme too.

   *One upgrade note:* lock filenames change shape between `-4` and `-5`. The lock is transient
   and lives in the per-user runtime directory, so this matters only if both builds are running
   against one archive at the same moment — a window as long as it takes to replace a binary.

6. **CI is a gate, which is V1.4 arriving early.** Brought forward by the maker's decision, and
   it adds **not one new assertion**. `cargo fmt --check`, `cargo clippy --all-targets -D
   warnings`, `cargo build --release`, `cargo test` and `check-deps.sh` have every one of them
   been running inside `release.yml`'s `deb` job since v1.0. They simply never ran on a commit, so
   an ordinary push got no answer at all and a mistake could sit on master until a release found
   it. `check-deps.sh` has said this about itself since it was written: *"What V1.4 adds is the
   rest of it: CI on every push, with this script as a gate on a merge."*

   Three choices in that file are decisions rather than defaults, and are written into it:
   **it never builds a package** — README §3 promises the artefacts come from containers, from the
   tag, and nowhere else, and a gate that built one would be producing something nobody may ship
   out of a PKGBUILD whose `source=` still names an older tag; **no cargo cache** — a cache is a
   variable and that file exists to remove variables; **branches only, not tags** — a tag already
   starts `release.yml`, which runs all five steps itself, and two builds of one commit racing for
   a runner is not a gate, it is noise.

## The record, straightened

Four places where a document said something that was not so:

| Where | What it said | What is true |
| --- | --- | --- |
| `P13.md` §7 | *"Both are written down where the code is."* | Only `theme.rs` got its note. `80ab69c` touched that file and `P13.md`, and nothing else — `sb_the_numbers` never received one, so the second defect lived behind a sentence claiming it had been recorded. |
| `P13.md` §6 | The window floors are 900×680. | They are **560×400**. `e465492` took them to 640×480 inside P13 itself; P14 took them the rest of the way. The paragraph was never amended. |
| `P12.md` | *"A testing round against a built binary"* and *"Released"*, both unticked. | Both were true before anybody read them again: P13 and P14 each ran their round, and `v1.0.0-4` shipped on 2026-08-10. |
| `P9.md` | *"all fifteen still open"* on the CORE edits. | P12 applied the standing backlog entire — *"The eighteen ordered CORE operations are applied, and verified applied."* |

The first of those is the one that mattered, and it is worth saying why rather than only fixing
it. **A false line in the record costs more than the defect it covers.** The defect was still on
the screen, where somebody would eventually run into it again; the sentence was the only thing
standing between the two, and it was pointed the wrong way.

CORE is the maker's document and changes to it are his hand. Two, both in §7, both recorded here
so they can be read rather than discovered:

2. **The V1.4 line under *After v1.0* records that it shipped early**, in P15, by the maker's

already there and is simply true now.

## What is out, and why

Recorded so they are not reproposed as discoveries:

- **The Keys popup is still typed twice.** CORE §4 asks for it to be generated from the bindings.
  It is not: the bindings are a `match`, the table is `ROWS`. The mitigation is deliberate and
  defended — `the_popup_and_core_agree_about_the_keys` reads `CORE.md` through `include_str!` at
  test time, so drift cannot be silent, only manual.
- **A failed overwrite still counts as an extracted entry.** A target left by an earlier
  extraction cannot be told from one written a moment ago without comparing timestamps, which
  costs more than the case is worth. Stated at the code site since P12.
- **A clipboard offering only `text/uri-list` is still missed on paste.** Fixing it means reaching
  past egui for raw winit events, which is a change to how the program receives input.
- **The winit fractional-scale pixel skip.** P14 settled it: not ours, unconditional for every
  eframe 0.36 application on a fractional-scale Wayland display, and must not be chased again.
- **Per-file-type icons in the entry table.** P13 named it as deserving its own round and it still
  does. That is the round after this one.

## Deviations

1. **The lane widths are characters, not measured pixels.** Measuring would be the general answer
   and would also be the wrong one here: §6 admits exactly one face, in the `Mono` cut, so a
   character is already a column, and a measured lane would recompute every frame to arrive at the
   number a `usize` constant states once. If a second face ever entered the window this would
   break — and CORE §6's dated refusals say one never will.
2. **The count's lane indents small archives.** Item 3 above; the honest cost of the rule as the
   document words it, taken deliberately rather than designed around.
3. **`check-deps.sh` runs in CI against a runner-built binary, not a container-built one.** The
   toolkit assertion is about what the source links, which does not vary between the two; the
   glibc floor, which does, is still measured only where it must be — inside `debian:bookworm`, by
   `make-deb.sh`, on the binary that actually ships.

open rather than quietly assumed: a box that belongs to nobody is a box that stays empty long

*A last thing the release found.* The README's Debian-package badge read **6.5 MB**, which is the
size of the `v1.0` package and has been wrong since `v1.0.0-3` — three releases during which the
file grew by 700 KB and the badge did not move. It is 7.2 MB now, measured off the artefact this
tag actually published. Nothing reads that badge but a person, which is exactly why nothing caught
it: every number in this project that a *test* can reach has been right for fifteen milestones.

## The ritual

CORE §8: *"Every P-document ends with the full ritual spelled out."*

1. `cargo fmt --check` · `cargo clippy --all-targets -- -D warnings` · `cargo test` ·
   `cargo build --release` · `./build/check-deps.sh`. All five by hand before anything leaves the
   machine, and all five again in CI on the push that follows.
2. Commit in the house voice, from **sudo-megas** and no other account, with no AI attribution of
   any kind — no trailer, no generated-by line, nothing in a file, a document or a release note.
3. Push `master`. **The new `ci.yml` going green on that push is its own acceptance test**, and
   the first thing in this milestone that cannot be proven locally.
4. `gh workflow run release` — the dispatch, before the tag, which is what that trigger exists
   for. Its `verify` job runs `verify.sh`'s ten checks and the eight `package_path` tests against
   artefacts it built. **Packaging is never proven on this machine**: the committed PKGBUILD pins
   `#tag=v1.0` and only `release.yml` rewrites that fragment, so a local `makepkg` would build the
   v1.0 tree and `verify.sh` would bless it under a 1.0.0-5 label.
5. Watch it green. Then tag `v1.0.0-5` and push the tag; `pkgrel=5` is what makes that the only
   tag the workflow will accept.
6. Watch the tag run green. Download its three artefacts.
7. `gh release create v1.0.0-5` — title **"INDIUM 1.0.0-5 — Beta 5"**, notes in the house voice,
   the three artefacts attached. `release.yml` uploads to the run and stops; the outward-facing
   act stays a separate human step, as CORE §8 requires.
