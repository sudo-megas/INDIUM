# P22 — the draft, and the file you can close

## Why this round

A story, told by the maker after v2.0 shipped:

> I am a person and i just want a create an archive. what steps do i take in indium now?
> 1. Open indium from app launcher. 2. I press N. 3. There is a popup. but i haven't added my
> files yet, so i dont know which compression now? why would it be asking archive? pfff
> whatever just i press enter. 4. **Archive directory opens** okay now i will add my files.
> then i will pick how to create it... 5. Whatt??? why would i have to press N and see the
> same popup again??? what is the sense here??

He is right, and the root was one sentence: **`archive_path` was what unlocked adding files,
and the only two things that ever set it were opening an archive and pressing Create.** So
Create was the only door into the state where files could exist, and it sat *upstream* of the
compression choice. The recipe had to be committed before the bytes it described could exist.
Pressing `N` twice was not clumsiness; it was the program admitting that.

v2.0 made it sharp rather than causing it — `build/docs/P21.md` records the collision already:
*"D5 says the estimator measures staged files, and files arrive after the popup closes."* P21
chose to make re-entry safe. **This round reorders the flow so there is nothing to re-enter**,
and takes the phantom with it: after Create, `has_archive()` was true for a file that had never
been written, and fourteen call sites inherited the lie.

The outcome: **one `N`, pressed last.** Add files to a draft, then Create, then Apply. Measure
is live from the popup's first frame because there are real bytes to weigh. And an archive
became a thing you can *close*, which this program had never allowed.

## What the plan got wrong about the tree

The plan as first drafted misdescribed the code in five places, and three parallel surveys
found them before a line was written. They are recorded because the *kind* of error repeats:
every one was a claim about the tree that reasoning about the design had produced.

| Was written | Actually |
| --- | --- |
| `Section::File` exists | It was **`Section::Archive`**. Renaming it was part of the round, compiler-caught at five match sites. |
| `has_archive()` has 9 consumers | **14.** Several phantom symptoms never called it — the window title, status row 1, the Inspector card, Extract, `estimate_refusal` all read `archive_path` directly. Harmless in the end: `has_archive()` *is* `archive_path.is_some()`, so one field cleared both sets. |
| `stage_creation` clears the queue | **Only on first staging.** P21 deliberately made re-staging keep the adds. The two-targets collision was real but narrower. |
| `Kind` has 2 variants; each pull calls `begin` | **3 variants**, and `current` held exactly one live directory per kind. "A subdirectory per pull" did not fit that structure — see [`Scratch::ensure`](#the-scratch-kind-that-accumulates). |
| `the_modules_are_the_ones_core_lists` | No such test. It is **`the_architecture_table_names_every_module_and_nothing_else`**, comparing first cells as an order-free `BTreeSet`. |

And one thing the survey found that no draft had: `src/ui/keys.rs` hardcoded *"There is no key
for leaving an archive. One archive per window (CORE §1) — so closing the window is how you
leave it."* Ship a Close control and that sentence is a lie on screen. Nothing pinned it.

## The design

### The draft is a basket, not a queue

The staging `Queue` holds mutations **to the archive that is open** — add, remove, rename — and
`plan()` folds them toward **one** target. *"Rename inside photos.zip"* and *"build backup.7z
out of these"* are two targets and cannot share it. So the draft is not a second queue: it is a
plain list of `(source, dest)`, holding no mutation of anything and folding nothing.

It lives in **`src/tasks.rs`** beside `Queue` and `Recipe` — not a new module, so CORE §3 needed
no new row and `src/lib.rs`'s architecture gate was untouched.

**One item per `dest`.** Adding a colliding name replaces the earlier item and the status line
says which — otherwise the fold silently drops one at Apply.

### The lifecycle — the rule this round turns on

Every naive answer to *"what does Create do to the basket?"* breaks. Empty it and the tray's
**Discard** destroys the draft; keep it and the queue goes stale behind it; sweep its scratch on
empty and Apply reads deleted files. One rule:

> **The draft is the source of truth until Apply succeeds. The queue's creation lane is a
> projection of it, rebuilt from empty at every Create press.**

| Event | Draft | Queue | Scratch |
| --- | --- | --- | --- |
| **Create** pressed | untouched | rebuilt: one `Create`, then one `Add` per draft item | untouched |
| **Discard** from the tray | **stands** | cleared | **stands** |
| **Close** the archive | **stands** | mutations cleared, a **creation stands** | **stands** |
| **Apply** succeeds on a creation | emptied | cleared | `discard(Kind::Draft)` |
| Window dies | — | — | Drop guard |

Discard leaving the draft standing is the same shape as the release design that shipped in P21:
**the human artefact outlives the machinery.**

`Queue::set_creation` was deleted with its two tests. P21 needed the queue to keep its adds
across a second Create because the queue was the only place the file list lived. The draft holds
it now, and rebuilding from the draft preserves `Task::Create`'s *"only ever first, and only ever
one"* by construction instead of by careful mutation — and drops a file the draft has dropped
instead of keeping it.

**What Create does to the archive still open: nothing.** But that quietly removed a structural
guard — staging-after-Create used to be impossible because the first-staging branch cleared
`entries`, leaving no rows for `Del`/`F2` to act on. So the rule became explicit:
`staging_refusal` refuses a mutation while a creation is staged. **The asymmetry is deliberate:**
mutations-then-Create has F7's ruling (displace, and say so), Create-then-mutations gets a
refusal, because a rename cannot displace a creation.

**The phantom died as a side effect.** `stage_creation` stops setting `archive_path` and stops
setting the window title. Nothing adopts a path that does not exist: before Create you are in
the Draft, after Create you have a queue and a tray, and the window opens the result once Apply
has written it. `ApplyMsg::Done` had to change with it — it re-opened `archive_path`, which is no
longer the thing that was built, so the target comes from the queue's own recipe, read before the
queue is cleared.

### Close, and the open that closes for you

`window::destination` answered *"here or a second window?"*, and under F2 there is no second
window to answer with from inside the program. What it was really doing survives as
`already_open`, because the question that mattered was always the other one: two of
`open_archive`'s seven callers hand back the archive that is already open — Apply after a
rebuild, the password prompt after unlocking — and **neither is leaving anything.** Reading
either as a close would wipe the passphrase the prompt has just taken and re-empty a tray Apply
has already emptied.

**The order of `open_archive`'s two refusals inverted.** P8 put the destination first because a
second window replaced nothing, so a window busy extracting could open a different archive
beside itself rather than refuse. An in-program open *replaces what is here*, which is precisely
the rug-pull P7 §7 added `work_running` to stop. `work_running` goes first now, and Close
refuses on the same check for the same reason.

Leaving is one function rather than a preamble: `reset_view` is what opening and closing share,
and `leave_archive` adds the three things only leaving does — forget the passphrase (§9), drop
the listing in flight, and empty the tray.

**Except a creation, which stands.** It names an archive that does not exist yet and the closed
file was never its subject. F6 already ruled the draft survives untouched, and the queue's
creation lane is that draft projected — so discarding the projection while keeping the draft
would cost a person one `N` press to reach a state they were already in. The two cases cannot
overlap, because `staging_refusal` refuses a mutation while a creation is staged, which is what
lets this be a count rather than a filter, and what stops the sentence saying *"5 changes"* about
a number that included the `Task::Create` itself.

**F7's sentence could not be said where the loss happens.** `open_archive` sets *"Reading …"* and
`ListMsg::Done` overwrites it with the archive's name a few milliseconds later, so a sentence
said at the close would be gone before it was read. The two facts wait on `discarded_on_open`
and `Done` composes them onto the line that stays. A same-archive re-open leaves the carry
**standing** rather than clearing it, so an encrypted archive opened over a staged one still says
what that cost once the password lands: the resume is that open continued, not a second one.

### Bringing entries across

An entry inside an archive is not a file, and a draft holds files. So the one new capability of
the round is the thing that makes one: *Bring from archive* walks the route `copy_out` already
walks — subject entries, uncompressed total, the `work_running` gate, one worker, one post-step
— and hands what lands to the draft instead of to the clipboard.

What it makes are **copies**, deliberately. That is what makes F6's *"the draft survives"* true
rather than a promise the engine could not keep: the files exist on their own from the moment
they land, and closing, renaming or rebuilding the archive they came from does not touch them.

The dest a pull derives is the path the entry had **inside the archive**, where `add_to_draft`
takes a disk file's `file_name`. Not an inconsistency: a file on disk has an absolute path that
means nothing inside an archive, and an entry has one that means everything, so each keeps the
name it actually has. Pulling a *directory* needs no special case — the extraction expanded it
and the prefix strip recovers `docs/notes.txt` for a file never named in the selection.

`PendingAction::Draft` carries nothing because it needs nothing: a password prompt does not
change what is selected, so the resume is the first press repeated. Its **prompt sentence needed
its own arm all the same** — the dispatch is exhaustive and the compiler catches it, the prompt
has a `_` catch-all and could only have said *"extract"*.

### The scratch kind that accumulates

`Kind::Draft` is the odd one of the four, and every rule that reads `Kind` now reads it for this.
The other three are momentary and each supersedes the last, which is what `begin` is for. A draft
accumulates — many pulls, surviving a Close, outliving Discard — so a `begin` per pull would
delete the files the draft's own items point at, leaving rows naming sources that are not there
and an Apply that fails on them.

`Scratch::ensure` opens the directory once and hands back the same one after. The invariant lives
in `scratch.rs` beside the Drop guard rather than in UI code, so a refactor that "simplifies" it
back fails a test instead of eating a draft. Pulls are kept apart inside it, a numbered
subdirectory each, because two archives can both hold `docs/notes.txt`.

**It goes to disk whatever it weighs, and not as a preference.** `route` weighs a selection
*once*, and for a directory opened once and added to for a whole draft's life that answer would
be about the first pull and no other — a 10 MB first pull followed by an 8 GB second would put
eight gigabytes in tmpfs having decided nothing about them. Per-size routing is meaningless for a
total that keeps growing. `Kind::on_disk_always` says so in a line, rather than the routing being
defeated by handing `begin` a total it does not have; a faked total would also have owed P3 §1's
*"over 1 GiB"* notice about a three-file pull.

**`owner()` had to learn `"dr"` in the same breath**, and that is the sharp edge of the above:
cache root is the one root nothing but `sweep_stale` ever clears, and a prefix it does not
recognise is a `Stranger` — never removed, whatever else is true of it. Forcing the draft there
while the sweep could not read its name would have created the leak the routing exists to
prevent.

### The sections and the sidebar

`Section::Archive` → `File`, plus `Draft`. The layout is wordmark · *File* `1` *Draft* `2`
*Create* `N` · rule · *Open file* `O` *Recent files* `3` *Bookmarks* `4` · (bottom) *Settings*
`,` *About* `A`.

`src/ui/sidebar.rs` had 370 lines, eight hand-written call sites and **no test module**, while
CORE §4's sidebar paragraph was pinned by nothing — two hand-copies with nothing between them, in
the one round that rewrites both. It got a `ROWS` const table and the round's new gate.

## What building it found, that reasoning about it did not

### 1. A commit that would not have compiled standing alone

`414ac1f` omitted `src/ui/newarchive.rs`, which carried part of the `Section::Archive` →
`Section::File` rename. The suite was green because the *tree* was green; the commit was not.
Found by stashing the working tree and running `cargo check` against `HEAD` alone, which is the
only thing that asks the question. Amended to `ff1069b`.

### 2. The new sidebar gate was verified by breaking it

A gate that has never failed is a gate nobody has read. It was broken two ways before the commit
landed: a drifted label gave `row 1: CORE says "Draft", the sidebar draws "Basket"`, and a moved
group gave `Create is drawn in group 3 and CORE §4 puts it elsewhere`.

### 3. Close during a listing would have lost its own sentence

The open preamble's cancel-and-swap leaves `list_rx` alive. A Close with a cancelled lister still
in flight gets a late `Done` that overwrites *"Closed photos.zip · …"* with the archive's name.
`leave_archive` drops the receiver and the flag together.

### 4. The draft can go stale under a staged creation, silently

The round's own hole, and the last thing closed. The projection is recomputed when *Create* is
pressed and at no other time — which is what lets the draft be edited without the queue moving
underneath it — but a file added after a Create is in the draft and **not** in the creation the
tray is offering to build. Apply would have succeeded and the archive would simply not have held
it. Every route that changes the draft now says so and names the key that restages it. A sentence
rather than an automatic restage, because CORE §4 says the projection is made on a press, and a
queue that rebuilt itself under a staged recipe would make that false.

### 5. `LZMA2:19` had been copied down twice, not once

Fixing §4.1's figure was one line, and the survey said the error survived because the test that
names it hardcodes. Making that test read the document turned up the second copy: `recipe_sentence`'s
own docstring, which had quoted §4.1 including the typo since P4. A hand-copy of a hand-copy is
what a doc-as-test is for, and this one is now the only place either figure is written.
