# P11 — The round that was actually run

*Repairs what a real testing round found: the half of P10 that was not fixed, four defects in
the window that had shipped since P2, a dev-machine script that could only be run from one
directory — and, found while proving the first of those, the worst defect this program has
ever had. When this file and CORE.md disagree, CORE.md wins.*

**Goal in one sentence:** every filename survives being read, `Ctrl+V` stages files for real
this time, and adding a file to an archive no longer depends on a toolkit having got something
right — released as **`v1.0.0-3`**.

P10 closed by saying two features that had never worked now worked, and proved it by pressing
the keys. It proved one of them. The maker installed `v1.0.0-2` on a wiped machine, worked
through the eight rounds of the test plan, and wrote down what happened — twenty-five
observations, of which the flattest was *"cannot add files to archive as dragging or ctrl+v are
not working."* P10's `Ctrl+V` fix was written against a reading of egui-winit that is half
right, and half was not enough.

Then, while proving the repair against a real file manager's clipboard, an archive with four
files copied three of them out. The fourth was called `köpek.txt`. **Every name outside ASCII,
in every archive, has been silently dropped by every extraction and copy-out since P1** — and no
test in eight milestones could have seen it, because every fixture in the repository is pure
ASCII. §2 is that, and it is the reason this milestone exists at the size it does.

**Not in P11:** the seven things the same round asked for that CORE has to decide first — the
sidebar's order, an `F1` keys popup, the status bar's readability, capsules and density at
1080p, the row cursor's visibility. Not one is a defect; every one changes what §4 or §6 says
the window *is*, and CORE is the maker's hand alone. They are tabled at the foot of the standing
apply-list so P12 starts from a decision rather than a memory.

## 1. The chord is read on the way up

P10 found that `egui-winit` converts a clipboard chord into a clipboard *event* and returns
before emitting the key, so `i.key_pressed(egui::Key::C)` is permanently false. That is true and
it is why `Ctrl+C` had never worked. P10's answer was to read `Event::Copy` and `Event::Paste`
instead.

For copy that is correct. For paste it is not, and the difference is four lines:

```rust
// egui-winit-0.36.1/src/lib.rs
} else if is_paste_command(self.modifiers, active_key) {
    if let Some(contents) = self.clipboard.get() {
        let contents = contents.replace("\r\n", "\n");
        if !contents.is_empty() {
            self.egui_input.events.push(egui::Event::Paste(contents));
        }
    }
    return;          // <- outside the `if let`
}
```

`clipboard.get()` returns **text**, or nothing. Copying a *file* in a file manager puts no text
on the clipboard at all — measured, not assumed:

```
$ wl-paste --list-types          # after copying three files in Dolphin
text/uri-list
application/x-kde4-urilist
application/vnd.portal.filetransfer
application/x-kde-source-id
```

No `text/plain` of any kind. So `get()` returns `None`, **no event whatsoever is pushed**, and
the `Key::V` beside it is swallowed on the way past by that unconditional `return`. There is
nothing left in the frame to notice. P10 also added a speculative `Key` arm against the day egui
stopped swallowing the chord; it could never have fired, because the early return is precisely
what stops that key existing.

What survives is the **release**. The whole interception sits inside `if pressed`, so
`Key { key: V, pressed: false }` is emitted normally, in every clipboard state there is:

```rust
fn clipboard_chords(events: &[egui::Event]) -> (bool, bool) {
    for ev in events {
        let egui::Event::Key { key, pressed: false, modifiers, .. } = ev else { continue };
        …
    }
}
```

One signal, one per chord, no dependence on what the clipboard happens to hold. `Event::Copy`
and `Event::Paste` are deliberately **not** also accepted: answering a press-form and a
release-form together stages the same paste twice whenever the clipboard *does* carry text, and
`paste_rx.is_some()` is no guard — the read finishes long before a human lifts a key. The one
case this cannot see is `Ctrl` released before the letter, which is the opposite of how a chord
is normally let go.

**Proved against Dolphin, not against a test.** Three files copied in Dolphin, `Ctrl+V` in
INDIUM, and the tray reads *"3 changes — add dropped.txt as dropped.txt, …"*. With a clipboard
that also carries text, the same chord stages **once**.

### The regression P10 shipped, too

P10's `Ctrl+C` guard was `ctx.memory(|m| m.focused().is_some())`, which is true of a `TextEdit`
and of nothing else. A **label** with a live text selection never takes focus — so selecting a
path in the status bar and pressing `Ctrl+C` started an extraction underneath someone who had
asked for four words. egui is already copying that selection itself; all INDIUM has to do is not
also copy the archive out. The label selection is asked about separately, and guards `Ctrl+C`
alone: widening `typing` would switch off every bare-letter shortcut in §4's table for as long
as a selection existed anywhere in the window, which is a second bug wearing the first one's
clothes.

## 2. The name libarchive could not say

`photos.zip` holds four files. `Ctrl+A`, `Ctrl+C`, and three arrive on the clipboard. The
missing one is `photos/2026/summer/köpek.txt`. `bsdtar` — the same libarchive, the same archive —
extracts all four.

INDIUM's own reader, asked directly:

```
raw="photos/2026/summer/" path="photos/2026/summer" is_dir=true  size=0
raw=""                    path=""                   is_dir=false size=26   <- köpek.txt
raw="photos/2026/summer/beach day.jpg"  …
```

**libarchive converts a stored name into the *current locale's* charset while it reads the
header.** A C program enables that by calling `setlocale` on the way in; `bsdtar` does, which is
the entire difference. **A Rust program never calls `setlocale` at all** — so INDIUM has sat in
the `C` locale for the whole of its life, the target charset is ASCII, and a name with any byte
outside it cannot be converted. libarchive's answer to a conversion it cannot do is to store
nothing, so `archive_entry_pathname` hands back **NULL**.

`cstr_to_string(NULL).unwrap_or_default()` turned that into an empty name. An empty name matches
no selection. And `extract`'s

```rust
if !selection_matches(&entry.path, wanted) { reader.skip_data(); continue; }
```

then dropped the entry using the same line it uses to skip a file nobody asked for. The two are
indistinguishable from inside that loop and mean opposite things. Every `köpek.txt`,
`résumé.pdf` and `日本語.txt` in every archive listed as a nameless row and was silently left
behind — by extraction, copy-out, preview and CRC alike, in every binary this project has
shipped.

`archive_entry_pathname_utf8` is **not** the fix, though it looks like one and was tried first:
the conversion has already failed by then, and re-encoding nothing gives nothing. It was swapped
in, and `köpek.txt` was still nameless. It is kept as a second line, and the write side now uses
`archive_entry_set_pathname_utf8` so a zip gets its UTF-8 flag set rather than raw bytes under a
flag left clear.

The fix is `setlocale`, and both its category and its argument are chosen as carefully as its
existence.

**`LC_CTYPE` and not `LC_ALL`.** `LC_CTYPE` is the only category libarchive's charset conversion
consults; `LC_ALL` would also adopt the user's `LC_NUMERIC`, which on the machine this was found
on is `tr_TR.UTF-8` — where the decimal separator is a comma. Every C library in the process, the
GL stack included, would start parsing and printing numbers differently as a side effect of
naming a file.

**And not the user's locale alone**, which is what P11 wrote first and the release rehearsal
rejected. The `debian:bookworm` container the `.deb` is built in has no UTF-8 locale configured
at all, so `setlocale(LC_CTYPE, "")` lands straight back on `C` and every name is empty again.
The three new tests failed there while passing on Arch — the first time in this project's life
that a test has caught a defect on one distribution and not the other, and exactly what those
tests are for. The same hole is open on any machine started under `LC_ALL=C`, which is most of
them once INDIUM is launched by something other than a desktop session.

So the user's locale is tried first, because it is theirs, and kept only if
`nl_langinfo(CODESET)` says it can carry the names. Otherwise a UTF-8 locale is forced —
`C.UTF-8` is built into glibc from 2.35 and needs no locale generation, which is what makes it
usable in a container that has none. This is not overriding a preference: `Entry::raw_path` is a
Rust `String` and therefore UTF-8 whatever the locale says, so a non-UTF-8 `LC_CTYPE` cannot
round-trip a name through this program even when it manages to convert one. UTF-8 is the only
setting under which INDIUM is correct.

It lives in `arch` behind a `Once` rather than in `main`, because the library is driven directly
by the tests in `tests/` and a fix a caller has to remember is a fix that goes missing.

**And the silence is fixed separately from the cause.** An archive INDIUM cannot name every
member of is now one it refuses to extract at all, before a byte is written, rather than one it
extracts almost all of and reports success for. `ensure_ctype_locale` should mean that line is
never reached; it exists so that the next thing to go wrong here cannot go wrong quietly.

## 3. Four defects in the window

**One cursor was doing three jobs.** `self.cursor` was clamped every frame against
`rows.len()` — the *archive's* rows — whatever section was on screen. With a two-row archive
open, a third bookmark could be clicked but never stayed lit, and `Enter` on a recent opened the
wrong row or none at all. That last is P8 Deviation 10, left open by P10 on the grounds that a
revision should not quietly pick up unrelated fixes; it is the same line as the other two, so
fixing either fixes all three. There is now a cursor per section, and switching sections no
longer throws the position away.

**A recent needed a double click.** Single clicks appeared to do nothing, so the list read as
broken rather than as wanting a second click — *"I clicked on them 10 times… then I clicked one
of them uncounted fast times. it opens randomly. SO VOLATILE!"* That is a double-click threshold
being met by accident. A row here names one archive and has exactly one thing it can do; one
click opens it.

**Three popups asked for focus every frame.** `resp.request_focus()` outside any condition, for
as long as the popup was open, so no *second* field in any of them could hold focus for longer
than one frame. The confirm box in the Password popup bounced straight back to the box above it,
which meant a new encrypted archive could not be given a password at all; the Open-With filter
had the same grip on its own popup, so `↑`/`↓` could never reach the list of applications. A
popup now takes focus once, keyed on *which* popup was focused rather than a flag per popup, so
opening one arms it without help from the twenty-odd places that assign `self.popup`. Open-With
gained a keyboard cursor while its list was finally reachable.

**Tab completion left the caret behind.** Assigning to the `String` behind a `TextEdit` changes
what is drawn and nothing else — egui keeps the caret in `TextEditState`, so a caret at column 9
stayed at column 9 in a line now forty characters long. *"it kills the philosophy of it being a
life-hack."* Both completion fields are named now, so their state can be found, and the caret
follows the completion.

Beside them: a bookmark whose directory is gone says *missing*, as a recent has since P2; the
rebuild conflict names what to do next instead of stopping after *"nothing was written"*; and
the sidebar's foot reserves its space **before** the sections above are laid out. That last was
two layouts sharing one rect and measuring from opposite edges, which agree only while the rect
is taller than both — shorten the window past that and they draw over one another, wordmark
through buttons. KWin was observed handing INDIUM a 540pt client area against a declared minimum
of 600, so a declared minimum is not a guarantee; a panel plus a scroll area is.

## 4. A way in that is not a chord

`Ctrl+V` works now. It is still a chord nobody is told about, and it was one of only two routes
into an archive. The other is a drop, and **a drop cannot work here at all**:
`winit-0.30.13` emits `WindowEvent::DroppedFile` from exactly one place —
`platform_impl/linux/x11/event_processor.rs` — and its Wayland backend contains no data-device
code whatsoever. CORE §1 names Wayland first and CORE §4's keyboard table promises *"`Ctrl+V` /
drop files"*. On the platform this program is for, half that promise has never been deliverable.
The drop path stays wired, because it works on X11; §5 orders the edit that stops the document
claiming otherwise.

So there is a third route, and it belongs to the desktop rather than to INDIUM:
`xdg-desktop-portal`, through `ashpd`. Two buttons, no new key:

- **Browse…** inside the `Ctrl+O` popup. `Ctrl+O` keeps opening exactly what §4's keyboard table
  says it opens — a path field with tab completion — because rebinding a documented chord to add
  a button's worth of convenience is not a trade worth making.
- **Add files…** at the far end of the breadcrumb row. Not the tray, which §4 keeps hidden until
  something is already staged: a control for making the first change cannot live in a zone that
  only exists after it. The breadcrumb already names the directory an add lands in, so the button
  adds *to where it says you are*.

The portal rather than a dialog of INDIUM's own because the picker belongs to the user — it is
the one they have already chosen, it honours their places and their recent files, it survives a
sandbox, and CORE §6 has no vocabulary for a file dialog. It costs thirty-seven crates, which is
the largest single dependency addition since libarchive and is recorded as such in §5 and in the
deviations.

## 6. Tests

`tests/fixtures/utf8.zip` is the first fixture in this repository whose names are not ASCII:
`köpek.txt`, `日本語.txt`, and `Ünlü/naïve.txt` beneath a directory whose own name is outside
ASCII, so a selection has to match a non-ASCII prefix. Three tests in `tests/read_path.rs` cover
the three ways the defect showed: the names survive the read, extraction writes all of them
rather than the ASCII ones, and selecting the directory takes the file under it.

They were checked the only way a regression test can honestly be checked — the one `setlocale`
call was commented out and all three failed; it was restored and all three passed.

`clipboard_chords`' four P10 tests are **rewritten, not extended**: they encoded press
semantics, which are now precisely what must not act. Five take their place, including one that
plays a whole chord in the order a window really receives it and asserts it acts exactly once,
and one that asserts the press-forms do nothing at all — the double-fire this design exists to
avoid. Two more in `platform::picker` pin the portal's URI shape, which is the same decoder P4
wrote for the clipboard and not a second one.

What no test covers, and what must be done by hand: the chord against a real file manager, the
picker against a real portal, and the sidebar at the window's floor. All three were, and the
captures are in the job's scratch directory rather than in the repository.

## 7. The release ritual

Same as P10's, and for the same reason — the gate derives the tag it will accept from `pkgrel`,
so the form is enforced rather than remembered.

1. `pkgrel=3` in the PKGBUILD, which is the one place the revision is written.
2. A `1.0.0-3` entry at the head of `changelog.Debian`.
3. Three artefact filenames and the version badge in `README.md`.
4. `cargo test`, `cargo clippy --all-targets -- -D warnings`, both clean.
5. `workflow_dispatch` rehearsal, green, **zero skips**.
6. `git tag v1.0.0-3 && git push origin v1.0.0-3` — the only form the gate accepts.
7. Watch the tag run green; `verify` judges both packages together.
8. Release from the sudo-megas account, three artefacts attached.
9. `cmp` the released tarball's binary against the one inside the `.deb`.

**And one thing P10 did not do:** amend `v1.0.0-2`'s release notes. They say `Ctrl+V` works. It
did not, and the page is public.

### One thing the round found that no step asked about

`tasks::lock_name_for` folds every character outside `[A-Za-z0-9._-]` to `%` — the same character
it uses for `/`. The runtime directory shows it plainly: `enkıripşığn.7z` took its lock as
`%home%megas%indium-test%enk%rip%%%n.7z.lock`. So two archives in one directory whose names
differ only in such characters share a lock file — `açık.zip` and `aşık.zip` both reduce to
`a%%k.zip` — and applying to one while the other is being rebuilt is refused with *"Another
INDIUM window is rebuilding this archive"* about a file nobody is touching. The lock is held
only across the rebuild (`tasks.rs:1187`), so the two applies have to overlap; nothing is lost
and nothing is corrupted, which is why this is written down rather than shipped as `1.0.0-4`.
It is the same ASCII-blindness §2 is about, in the one place §2 did not think to look.

## Deviations

1. **P10's claim was wrong, and this file says so in its first paragraph.** `v1.0.0-2` shipped
   notes and a P-document stating that `Ctrl+V` worked. Only `Ctrl+C` did. The notes are amended
   as part of this milestone rather than quietly left; a released page that claims a fix it did
   not ship is worse than one that claims nothing.

2. **P11 is much larger than a revision should be.** P10 argued that a revision picking up
   unrelated fixes is one nobody can reason about, and that is still true. This one carries a
   clipboard fix, a locale fix, four window defects, two shell scripts and a new dependency. The
   defence is that all of it came from one source — a single testing round, run once, against a
   released binary — and splitting it across three revisions would ship three binaries with known
   data loss in the first two.

3. **The worst defect in this milestone was found by accident.** §2 exists because a copy-out
   made while proving §1 produced three files where the Inspector said four. Nothing planned
   looked for it. That is not a process to be proud of, and the honest lesson is in §6: every
   fixture was ASCII, so every test agreed with the code instead of with the world.

4. **`_utf8` was tried first and did not work.** Recorded because it is the obvious fix, it is
   what the libarchive documentation appears to suggest, and the next person to read this will
   reach for it. The conversion fails at read time; there is nothing left to re-encode.

5. **A nameless entry now fails the whole extraction.** An archive with one unreadable name
   cannot be partly extracted any more, even for members that are fine. That is a deliberate
   trade in the direction P1 already chose for path traversal — refuse rather than half-do — and
   it costs an archive that would previously have *seemed* to work.

   It earned itself within the hour. When the first rehearsal ran with only
   `setlocale(LC_CTYPE, "")`, the Debian container had no UTF-8 locale, the names came back
   empty again, and the two extraction tests failed **loudly** with that exact sentence instead
   of quietly writing two files out of three. The guard was written on the argument that the
   next thing to go wrong here must not go wrong quietly, and the next thing to go wrong here
   was the fix itself.

10. **The first fix was half a fix, and CI found the other half.** `setlocale(LC_CTYPE, "")`
    respects the user's locale, which is right, and does nothing at all on a system that has no
    UTF-8 locale to respect — `debian:bookworm` being one, and `LC_ALL=C` being the same
    condition on any machine. Arch passed; Debian failed; the difference was invisible on the
    maker's own desktop. `nl_langinfo(CODESET)` now decides whether the user's locale can carry
    a name, and a UTF-8 one is forced when it cannot. **The `.deb` job is now the regression
    test for this**, and a better one than anything that could be written by hand: it runs in a
    container that genuinely has no UTF-8 locale, every time.

6. **`ashpd` costs thirty-seven crates**, against CORE §2's standing rule about not taking a
   dependency for twenty lines of work. A portal call is not twenty lines, and the alternative
   was drawing a file dialog that §6 has no vocabulary for. Recorded as the largest addition
   since libarchive so it is a decision on the record rather than a diff nobody read.

7. **Drag-and-drop is documented as broken rather than fixed.** It cannot be fixed from inside
   INDIUM: winit has no Wayland drag-and-drop. The alternative was talking `wl_data_device`
   directly on winit's surface, which duplicates work upstream will eventually do and is a large
   amount of fragile code for a feature two other routes already cover.

8. **The maker's own testing found things this file does not fix.** Seven of them, all CORE's to
   decide, tabled in the apply-list for P12. Two more are smaller and simply not done: the
   sidebar separator the maker called "so faded I can't distinguish it" is CORE §6's hairline
   rule and would need that rule changed, and the status bar's readability is a re-specification
   rather than a fix.

9. **The picker's selection path was verified by hand only in part.** The dialog opens, and a
   cancelled dialog returns empty and says nothing — both proven against the running program.
   Driving the dialog's *file list* by injected input failed for a reason that has nothing to do
   with INDIUM: the machine's keyboard layout is Turkish, and `ydotool type` sends US keycodes,
   so a typed path arrived as `.tmp.xx.photos.2026.summer.kpekçtxt`. The decode is covered by
   tests and shares its implementation with the clipboard path, which *was* proven end to end.
