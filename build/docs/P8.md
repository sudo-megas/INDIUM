# P8 — The second window

*Implements CORE.md §1's "Opening a second archive opens a second window", and repairs the
three things that sentence had been quietly breaking in the two files every window shares.
When this file and CORE.md disagree, CORE.md wins.*

**Goal in one sentence:** opening an archive while one is already open puts it in a window of
its own — a real window, closable on its own, that outlives every other — and the copy-outs,
bookmarks and recent files that two windows share stop overwriting each other, which they had
been doing since the day a second window became possible — tagged **`v1.0`**.

P7.md's last line reads *"**There is no P8.** The P-documents were the road to `v1.0`, P6 said so
one milestone early, and the road ends here."* P6 said it about P7 and was wrong by one
milestone; P7 quoted P6's mistake, repeated it in its own closing sentence, and was wrong by one
milestone in exactly the same way. Saying so is still cheaper than quietly numbering past it —
and the reason is the same one P7 gave: the code did what the document said, and the program was
still not the one CORE describes. CORE §1's second sentence had never been implemented at all.
The program answered a second archive by printing a sentence telling the *user* to go and open a
window by hand.

**Not in P8:** hex view (V1.1); the yazi plugin (V1.2); headless subcommands (V1.3); CI as a
**gate** on every push (V1.4); the live estimator (V2.0). No new formats, no new popups, no
second theme. And nothing that makes the windows aware of one another: no IPC, no single-instance
socket, no session restore, no watching the settings file for changes. Two INDIUMs are two
programs that happen to share two files, and P8's whole claim is that they now share them
politely.

## 1. A window is a process

CORE §1 has carried the rule since the first line of the first document: *"One archive per
window. Opening a second archive opens a second window. There are no tabs."* Every **consequence**
of that sentence was built years of milestones ago:

- P4 gave Apply an advisory lock keyed to the archive's path, living in `$XDG_RUNTIME_DIR`,
  deliberately *not* on the archive's inode, so that **two processes** cannot rebuild one file.
  Its refusal reads *"Another INDIUM window is rebuilding this archive."*
- P5 put the archive's name in the window title, *"so two windows can be told apart"*.
- P3 recorded that *"multiple windows on one archive are permitted and safe today"*.
- `tests/write_path.rs` takes the lock itself, *"exactly as a second window would"*.

**The one thing never built was the window.** A file lock in the session's runtime directory is
not a mechanism anyone reaches for to coordinate two halves of one address space; it is what you
build when the second window is a second process, and the program has been describing that
architecture in its own comments since P3 without ever being able to produce one.

### The alternative, and why it lost

eframe 0.36.1 *can* do it the other way. It is worth writing down that this was checked rather
than assumed, because "egui cannot open two windows" would be false. Read in the vendored source:
`winit_integration.rs:36-46` calls `set_embed_viewports(!IS_DESKTOP)`, which on Linux is `false`,
so `Context::show_viewport_deferred` takes the real branch at `context.rs:4071-4083` and
`glow_integration.rs:1248-1283` creates a genuine winit window and GL surface per viewport. On
Wayland these are true `xdg_toplevel`s. The glow backend supports it.

Three properties disqualify it, and not one of them is a matter of taste:

1. **The first window's close destroys every other window.** `glow_integration.rs:941-947` keys
   the event loop's exit on `ViewportId::ROOT` alone and never consults how many children are
   alive; `run.rs:153-157` then calls `save_and_destroy`, which drops the whole running context
   and with it every viewport's window. egui says so itself at `viewport.rs:17` — *"The root
   viewport is the original viewport, and cannot be closed without closing the application."*
   There is no promotion API. Open photos, open documents from Recent files, close photos first,
   and documents vanishes. Windows that die when their eldest sibling dies are not the peers CORE
   §1 describes — they are tabs wearing separate title bars, and CORE §1's third sentence is
   *"There are no tabs."*
2. **One archive per window would become several workers per process.** CORE §3 gives INDIUM
   *"the UI thread and one worker"*. A process per window keeps that sentence literally true, with
   no edit and no asterisk.
3. **A deferred viewport's callback may not borrow the app.** egui requires
   `Fn(&mut Ui, ViewportClass) + Send + Sync + 'static` (`context.rs:4059-4064`) and says outright
   at `context.rs:4044` that the state must be wrapped in an `Arc<Mutex<_>>`. Every field of a
   2,200-line window would move behind a lock, to buy windows that die together anyway.

**Spawning INDIUM is not the violation CORE §9 forbids.** The ban is on external *compressors* —
`7z`, `tar`, `unzip`, `zstd` — and its reason is stated in CORE §1: format work happens inside the
process, on every machine, whether or not any archive tool is installed. INDIUM is not a
compressor that INDIUM shells out to; the second window does its own format work in its own
address space with the same code linked into the same binary, which is that rule kept rather than
an exception to it. Nothing is added to CORE §2's dependency table, because nothing was added:
`std::process::Command` and `std::env::current_exe` are the standard library.

### Measured

The house rule from P4 §2 is that the interesting claim gets a probe rather than an argument.
Three windows, on the build machine, under KWin on Wayland:

```
indium basic.zip basic.tar.gz   -> 367171, 367172 (ppid 367171)   two windows, two titles
Recent files, Enter on the other -> 367617        (ppid 367172)   a third, from inside the app
kill 367171                      -> 367172 and 367617 still drawn  the peers survive
                                    367172 reparented to the session
defunct processes, at every step -> 0
```

The third line is the one that matters, and it is the exact case eframe's source says a deferred
viewport cannot survive.

## 2. Where an archive opens

`Indium::open_archive` is reached from seven places — the command line, a drop, `Ctrl+O`, a click
or `Enter` on a recent, the password prompt's List resume, and Apply's own re-open. **None of the
seven was touched.** They all already funnel through one function, so the rule goes in the
function, and CORE §1 does not acquire seven readings.

`platform::window::destination` is the whole rule:

| This window holds | The user asks for | Where it opens |
| --- | --- | --- |
| nothing | anything | here |
| `photos.7z` | `photos.7z` | here |
| `photos.7z` | `docs.zip` | a second window |

Two of the seven callers hand back the archive that is already open — the password prompt
re-opens it with the passphrase, and Apply re-opens it after the rebuild, because *"the Inspector
is the point of this program, and it must not describe a file that no longer exists."* **Neither
is written down as an exception.** They fall out of the middle row, because the archive they name
is the archive already there. An exception list with two entries on the first day is an exception
list with six on the last.

Paths are compared **canonicalised**, for the reason `tasks::lock_name_for` already gives for
doing the same: they arrive from `std::env::args`, from a drop, and from a hand-typed field, so
`./photos.7z` and `/home/megas/photos.7z` are the ordinary case and not the exotic one. A path
that cannot be canonicalised falls back to the name as given — correct, because nothing that does
not exist can be the archive this window already holds, and two archives that are both missing are
still two archives.

### The order of the two refusals is the load-bearing part

Until P8 the function began with `work_running`. P7 §7 put it there, and was right to: opening an
archive *replaced what was on screen*, so a user who clicked a recent while a copy-out was running
got a directory holding half a selection under a status line about a different archive.

**A second window replaces nothing.** So the destination is asked first, and a window busy
extracting will now open a different archive beside itself rather than refuse. The refusal was
never about the archive; it was about this window's own running work, and it still guards exactly
that — the middle row of the table above, where the archive asked for is the one already open, is
still subject to it. Asking `work_running` first would have made the busiest window the only one
that could not do the single thing that costs it nothing.

### Two smaller things that follow

**The command line.** `indium a.zip b.7z c.tar` opened `a.zip` and printed, for each of the
others, *"indium: one archive per window — ignoring b.7z / indium: open a second window for it
instead."* That is a program telling the user to run the command the program is already running.
Each further archive now gets its window, spawned before the first window is built so that five
archives arrive as five windows at once rather than one at a time behind the first one's listing.
A child that cannot start is named on the terminal they share and does not stop the others.

**No passphrase ever reaches a command line.** There is no argument for one and there will not be:
CORE §9 keeps passwords out of settings, recents *"and anywhere else"*, and a command line is
world-readable in `/proc`. The two callers that hold a `Secret` are the two that re-open the
archive already open, so they never reach the spawn — and `open_archive` drops the secret on the
spawning branch anyway, where `Secret`'s own `Drop` wipes it, so the rule is kept by the code
rather than by the argument that the code cannot get there.

**New Archive is not an open, and deliberately does not spawn.** `N` stages a `Task::Create` for
an archive that does not exist yet — P4 §1: *"New Archive writes nothing"* — so `stage_creation`
adopts the chosen path directly and never reaches `open_archive`. It is the one place a window's
archive changes without this section's rule being asked, and it must stay that way: a second
window receives its archive as a command-line path, and `main.rs` exits on a path that is not
there. **A window cannot be opened on a file nobody has written yet.** What the rule governs is
*opening* an archive; creating one is the other thing, and it keeps the window it was asked in
until Apply writes it.

**Zombies.** A spawned child that is never waited for sits in the process table as `<defunct>`
until its parent exits, and a first window is expected to outlive many children. Each spawn is
reaped by a thread that does nothing but block in `wait`. The alternative — a `try_wait` sweep
from the frame loop — would put a syscall per living child into the repaint path, and CORE §3's
*"an idle INDIUM repaints nothing and costs nothing"* is the sentence that decides between them.

## 3. What the second window was already breaking

CORE §1 has told users to open a second window since P1, and P3 recorded that doing so was "safe
today". **It was not.** Three bugs needed no bug report and no new code to exist — they needed
only a user who did what CORE §1 told them to. P8 makes the second window one click away, so all
three stop being theoretical on the same day.

### 3.1 Two windows, one scratch directory

P3 §1 numbers each window's scratch directories from one — `co-1`, `ow-1` — under a root shared by
every INDIUM on the machine. So **the first copy-out of every window is the same directory.**
`create_dir_all` succeeds silently on a directory that already exists, so a second window's
copy-out is written on top of the first window's files, and either window's next operation calls
`remove_dir_all` on a directory the other is still handing to a file manager.

The sweep was worse. P3's `sweep_stale` removes every `co-*` and `ow-*` it finds at launch, which
is right when only one INDIUM can be running and becomes **a deletion of a live window's files**
the moment a second one can: opening a second window deleted the first window's on-disk copy-out
while the user was looking at it.

Names now carry the process that made them — `co-<pid>-<n>` — and the sweep asks whether that
process is still running before removing anything. `/proc/<pid>` is the whole test; CORE §9 is
Linux only and the directory is there on every machine INDIUM runs on. The direction of the doubt
is deliberate and the two mistakes are not the same size: a process id the kernel has since handed
to another program reads as running and the directory is kept until a later launch, and that is
the small one. A name that cannot be parsed exactly — including a process id too large to be one —
is a stranger and is never touched, which is P3's own strictness kept word for word.

The old `co-<n>` form is still swept, unconditionally: nothing else will ever clear the cache root,
and no running window uses a name in that form.

### 3.2 Two windows, one settings file

Both TOML files are read **once, at startup**, and never re-read. Two windows are therefore two
divergent copies of one file, and each window wrote its whole copy back on every change. So the
second window to save undid everything the first had done since it started — one window opening an
archive was enough to drop a bookmark the other had just added — and nothing anywhere said so,
because from each window's side the write succeeded.

What travels to the file is now the **change**, applied to what is on disk, and the window's copy
becomes what was actually written. `Store::change_recents` and `Store::change_settings` own it;
`Indium::change_recents` and `Indium::change_settings` keep the startup latch and the status
sentence and nothing else. Ten call sites moved; none of them grew a merge.

**A merge is what was rejected**, and it is worth saying why, because it is the obvious answer.
Merging two lists makes every removal temporary: the window that had not seen the removal puts the
entry back the next time it saves anything at all, so forgetting a recent file would work until
the other window opened an archive. Carrying the operation rather than the snapshot is what makes
a removal survive. It has one consequence the callers must respect: **a change expressed as an
index is a change to a list this window has not seen**, so bookmarks are removed by identity.

Two honest limits. The race is narrowed, not closed — two windows can still read, change and write
across each other inside the same few milliseconds, and P4's lock is deliberately not taken for
this, because it guards a rebuild that runs for minutes and a lock file per bookmark would cost
more than the entry it saves. And a file that has *become* unparseable since startup needs no new
latch: every change re-reads it, so every change refuses again on its own.

### 3.3 Two windows, one temporary file

P2's `atomic_write` wrote through `settings.toml.tmp` — one name for every INDIUM on the machine.
Two windows saving in the same instant both truncate it, both write into it, and the two
serialisations interleave before either rename. The rename was always atomic; what it committed
was not necessarily either window's file. The scratch name now carries the writer's process id.
The rename is exactly as atomic as it was.

## 6. The release ritual

```
git add -A
git commit -m "P8: the README, photographed again"
git push

# The rehearsal. Dispatch release.yml by hand on master and watch all three jobs
# go green. The first run of a release workflow must never be the release — P6
# Deviation 19 is why the sentence survives into a third milestone — and the
# rehearsal is now worth more than it was: the arch job rewrites the PKGBUILD's
# source fragment to the dispatched commit, so makepkg, build(), check() and
# package() are exercised in full on a run where nothing is at stake.

git tag v1.0
git push origin v1.0

# The tag push runs the same workflow again, and this time the arch job builds
# from the tag rather than from a commit. Nothing is built by hand. When it is
# green, take the three artefacts down and attach them:
gh run download --name indium-deb --name indium-pkg --name indium-tar
```

**Nothing a release ships is built on the maker's machine.** This is the change P8 makes to the
ritual it inherited, and it is the maker's own instruction rather than this document's idea. Until
now the `.deb` came from a `debian:bookworm` container and the Arch package came from `makepkg` on
the Arch machine the maker sits at — which is the right machine for an Arch package and still the
wrong kind of thing to be, because a machine is a variable and a container is a written-down
constant. `release.yml` now builds all three artefacts, and the workflow file is the whole
provenance of every byte that ships. The gates moved with them: `cargo fmt --check` and
`cargo clippy -D warnings` are steps in the `deb` job now, or "built in CI" would quietly have
meant "built in CI, formatted wherever".

The third job is the one worth the trouble. `verify.sh` has carried `INDIUM_PKG` and `INDIUM_DEB`
overrides since P6 for artefacts built somewhere other than the tree, and until this workflow there
was nowhere the two packages were ever present at the same moment — so its strongest assertions,
the ones `tests/package_path.rs` makes with INDIUM's own reader, could only be run by hand on a
machine that had downloaded the other package. **The claim that both packages put identical files
under `usr/`, differing only where Arch and Debian each command their own paperwork, is now checked
on every release and on every rehearsal of one**, rather than being a thing the maker remembered to
check once.

**`Cargo.toml` moves nowhere.** It has read `1.0.0` since P6's first commit, for the reason P6 §9
gives, and P8 is now the milestone that pushes the tag it was moved for.

GitHub release on `v1.0`, with `indium-1.0.0-1-x86_64.pkg.tar.zst`, `indium_1.0.0-1_amd64.deb`
and `indium-1.0-x86_64.tar.gz` attached.

**Not a pre-release**, and P6 §9's argument stands word for word, as it did through P7: `v0.2`
through `v0.5` were pre-releases because each shipped a program CORE §7 said was not finished yet.
CORE §7 calls that table *"the road to v1.0"* and — after §4's second edit — ends it on P8's row.

Notes in the house voice: that one archive per window is now something the program does rather
than something it asks the user to do; that a window is a process, and what that buys — any window
closes without touching the others, and a hostile archive that takes one window down takes only
that one; that two windows no longer overwrite each other's bookmarks, recent files or copy-outs,
with the plain admission that they used to; the glibc floor of every artefact stated plainly; and
RAR's deliberate absence.

1. **The implementation was written before this document existed.** Third milestone running: P6

   afterwards. The ordering was still the wrong way round, and a ledger that omits the deviation
   its own author made is worth nothing.

2. **P8 narrowed a refusal P7 had just added, which is a previous milestone's decision changed
   rather than extended.** P7 §7 made `open_archive` refuse outright while work was running, and
   §2 above moves the destination check in front of it so that a busy window will now open a
   *different* archive in a new window instead of refusing. P7's reasoning is untouched for the
   case it was written about — the same archive, opened into the same window, mid-copy-out — but
   the sentence P7 wrote covered both cases and now covers one. Recorded because "a later
   milestone made an earlier one's guard narrower" is exactly the kind of change that should not
   be discoverable only by reading the diff.

3. **Renaming the temporary file nearly voided two tests that were watching it by name.** Both
   `settings_round_trip_and_leave_no_tmp` and `atomic_write_replaces_content_completely` asserted
   the absence of `settings.toml.tmp`, so §3.3's rename would have left them asserting the absence
   of a file the program had stopped writing — green for ever, testing nothing. It was caught
   before it landed and both now ask by prefix. Recorded because it was luck rather than process:
   nothing in the suite would have failed, and the next person to change a filename should know
   that two tests name it.

4. **The four screenshots took two attempts, and the first one photographed the wrong window.**
   The first try ran `spectacle -a` — *capture the active window* — while the machine was in use,
   so it captured whatever held focus rather than INDIUM, and the image went straight to
   `build/screenshot.png`, a path the repository ships. It was discarded and the committed file
   restored within the minute, and nothing was committed; but the fault was not bad luck. It was
   two decisions: trusting *active* to mean *the one I want*, and writing a capture directly to a
   deliverable path so that a wrong one overwrites a right one before anybody looks at it.

   The second attempt fixed both and was only made after the maker said the machine was free.
   KWin is scripted to make INDIUM active before every capture, so the shot has one possible
   subject; captures land in a scratch directory and are looked at before anything is promoted
   into `build/`. Three further choices are worth naming, because each changes what the pictures
   claim:

   - **They are of the binary CI built**, unpacked from `indium-1.0-x86_64.tar.gz` and verified
     byte-identical to the one inside the `.deb`. The pictures are of the shipped artefact, not
     of a local build resembling it.
   - **Decorations are excluded.** The title bar is drawn by the maker's desktop, which is on a
     light colour scheme, and a light title bar above an aubergine window is a photograph of
     somebody's Plasma settings rather than of this program. The same purity argument as §6's,
     one layer up.
   - **A throwaway `XDG_CONFIG_HOME` holds three bookmarks**, because the Extract popup's caption
     promises "Bookmarks sit underneath" and the maker's real `settings.toml` has none. Seeding a
     scratch config shows the feature the caption describes without editing anybody's settings.

   The window was also resized before shooting: the popups size themselves against
   `ctx.content_rect()`, so the first captures caught a New Archive whose method list had room
   for one entry, and a screenshot of a cramped popup misrepresents the program.

5. **The in-app path was driven with `ydotool` rather than by hand.** The build machine's
   compositor does not implement the virtual-keyboard protocol `wtype` needs, so the third window
   in §1's probe was opened by injecting `1`, `Down` and `Enter` through `ydotoold` at the
   uinput layer. It is the same key sequence a user's fingers make and the program cannot tell the
   difference, but it is not a person at a keyboard, and §5's manual checklist exists because that
   distinction is real.

6. **§6's ritual was rewritten after §6 was written, and it is a previous decision reversed rather
   than extended.** P6 decided that the Arch package is built by `makepkg` on the maker's Arch
   machine and wrote that sentence into `release.yml`'s header, into `build/package/README.md` and
   into every ritual since; P8 shipped with it intact and then the maker asked for the release to
   be built in CI instead, *"to make it pure rather than my machine"*. So `release.yml` grew an
   `arch` job and a `verify` job, the two documents that asserted the old arrangement were
   corrected, and the ritual above no longer builds anything locally. The reversal is sound —
   `makepkg` in `archlinux:base-devel` is the same `makepkg` — but it is a reversal, and the
   argument P6 made for the old arrangement was never wrong, only outgrown. Recorded because the
   PKGBUILD's own comments still describe a package built by a person, and they are still right
   about *how*; only *where* moved.

7. **The rehearsal builds a commit and the release builds a tag, and the PKGBUILD is edited in
   flight to say so.** `source=` is nailed to `#tag=v1.0` precisely so that a package cannot be
   built from a working tree, which leaves a dispatched run with nothing to build, since the whole
   point of dispatching is that the tag does not exist yet. The `arch` job therefore rewrites the
   fragment — `#commit=$GITHUB_SHA` on a dispatch, `#tag=$GITHUB_REF_NAME` on a tag — and prints
   the result. Both are immutable names for exact content and both are fetched from GitHub, so the
   rehearsal is honest; but a workflow that edits the file it is building from is the kind of thing
   that should be written down rather than found.

8. **The release date moved from 2026-08-08 to 2026-08-09.** P8's work ran past midnight, and the
   date is a compiled-in constant that the About popup shows and one of the four screenshots
   photographs. Moving it after the pictures were taken would have meant retaking them, so it moved
   first: `src/ui/about.rs`, the README's badge, and the Debian changelog's trailer, which is the
   packaging date and had no business claiming a day the package was not made on.

9. **The compositor takes synthetic keys but not a synthetic pointer, so two boxes could not be
   reached.** `ydotoold` at the uinput layer drives the keyboard fine — every keystroke in the
   checklist above landed — but `ydotool click` produced nothing at any of three coordinate
   mappings (physical, logical, and relative-from-corner), and `spectacle -p` draws no cursor to
   aim by either. Pinning a bookmark and staging-then-applying both need a button pressed, so
   those two boxes are recorded as not reached rather than ticked. This is the second time this
   machine's compositor has refused an input path — P6 Deviation 22 recorded `wtype` finding no
   virtual-keyboard protocol — and it is the concrete reason §5 says these boxes are the maker's.

10. **The keyboard cursor is shared across three sections but bounded by only one of them, and
    `Enter` on a recent silently does nothing when it is out of range.** `handle_keys` is handed
    `rows`, which is always `self.rows()` — *the archive table's* rows (`src/ui/mod.rs:1564`) —
    and clamps `self.cursor` to that length. `Section::Recents` then indexes a different list:
    `self.recents.sorted().get(self.cursor)`. Open a four-entry archive, move down twice, switch
    to Recent files with two entries, press Enter: `get(2)` is `None` and nothing happens, with no
    status line to say why. Found by this checklist, reproduced deliberately, and then confirmed
    from the other side — pressing `Home` first put the cursor in range and the recent opened in a
    new window immediately. Arrow keys in the Recents section also move the *archive* table's
    cursor, which is the same fault seen from the front. Not a multi-window bug and older than P8;
    it is written here because this is the run that found it.

11. **`Ctrl+C` and `Ctrl+V` do nothing in v1.0, and the release shipped with them dead.** Both are
    documented in CORE §4's key table and advertised in the README — *"Copy out (extract to
    runtime dir, URIs to clipboard)"* and *"Stage an add"*. Neither fires.

    The cause is not in this repository's logic but in the layer under it.
    `egui-winit-0.36.1/src/lib.rs:1019-1034` intercepts the clipboard chords before it emits a key
    event, and **returns**:

    ```rust
    } else if is_copy_command(self.modifiers, active_key) {
        self.egui_input.events.push(egui::Event::Copy);
        return;                       // the Event::Key is never pushed
    }
    ```

    `is_copy_command` is `modifiers.command && key == Key::C`; `is_paste_command` is the same for
    `V`. So while Ctrl is held, `Key::C` and `Key::V` never reach `egui::Context::input` at all —
    and `handle_keys` asks for exactly that (`i.modifiers.ctrl && i.key_pressed(egui::Key::C)`,
    `src/ui/mod.rs:1650-1651`). Nothing in the tree handles `Event::Copy` or `Event::Paste`.

    Observed before it was explained: `Ctrl+A` selected all three entries, `Ctrl+C` then produced
    no status line, no scratch directory under either root, and no clipboard offer, twice; and
    `Ctrl+V` with a `text/uri-list` on the clipboard staged nothing. `Ctrl+A`, `Ctrl+F` and
    `Ctrl+O` all work, because egui-winit special-cases only cut, copy and paste.

    **The fix is small** — read the events rather than the keys:

    ```rust
    let (ctrl_c, ctrl_v) = ctx.input(|i| (
        i.events.iter().any(|e| matches!(e, egui::Event::Copy)),
        i.events.iter().any(|e| matches!(e, egui::Event::Paste(_))),
    ));
    ```

    with the existing `!typing` guard still deciding whether the chord belongs to a focused
    `TextEdit` or to the table. It is not applied here: v1.0 is tagged and released, and a fix
    belongs to the milestone that ships it rather than to the ledger of the one that found it.

    This is what §5's checklist is for, and it is the argument for the checklist in one line: two
    advertised features were broken through P3, P4, P5, P6, P7 and P8, no automated test could
    have caught them — none of them can open a window — and the first time anybody actually
    pressed the keys, both fell over.
