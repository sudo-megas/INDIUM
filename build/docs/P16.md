# P16 — the hex view

*V1.1, and the first two-numeral tag since v1.0. One feature, two false lines, and a round that
was nominated and then not taken.*

## The round this was going to be

P13 named per-file-type icons in the entry table as deserving their own round, and P15 repeated
it in the plainest words available: *"That is the round after this one."* So this round began by
investigating icons, and found something neither document had:

> **An icon replaces a word; it never garnishes one.** … A folder glyph beside a path that
> already looks like a path is decoration, and §6 has no room for decoration; a glyph *instead
> of* a label is what the sidebar and the status bar use it for.
> — CORE §6

A type glyph beside `photo.png` is a glyph beside a name that already says `png`. That is very
close to the sentence's own example, and the sentence is a rule in the authoritative document
while the nomination is a note in two milestone records — so the nomination did not settle it.
It was put to the maker with the case for both readings, and he chose to leave the question open
and take the hex view instead.

**The icons round is still nominated and still undecided.** Nothing here forecloses it: no glyph
was added, `theme::icon::ALL` is untouched, and `ROW_HEIGHT` is still 20. When it is taken up it
begins with a §6 ruling, not with code.

The hex view has no such problem, because CORE asks for it twice — §4 by name, and
`inspector.rs` in a sentence the reader could see:

> *"Neither text nor an image INDIUM decodes. A hex view arrives in V1.1; until then there is
> nothing truthful to show here."*

A promise printed in the window is a debt. This round pays it.

## What was built

**`util::hex_offset` and `util::hex_body`** — pure, dependency-free, six tests, in the file whose
header says nothing in it may grow a dependency. Three decisions, each written at the code site:

1. **Sixteen bytes to a row, fixed, not fitted to the pane.** The obvious design is to compute
   the column count from the available width, and P13 already built that idea once — in the
   sidebar's header — and rolled it back, because *"a first launch and a one-pixel drag could
   show two different layouts."* Here the layout **is** the data: a dump that reflows as the
   Inspector is dragged puts the same byte at a different offset depending on the width of a
   pane, which is worse than the same mistake in a header. Sixteen is also what `xxd` and
   `hexdump` print, so an offset read here names the byte an offset read anywhere else does.
2. **Uppercase, eight-digit offsets.** Uppercase because the Inspector already prints its CRC as
   `{v:08X}` and two hex conventions in one pane is one too many. Eight digits is two more than
   this can ever need — the cap is 8 MiB, so the largest possible last row is `007FFFF0` — and
   eight anyway, because that is the width of the tools a reader is comparing against.
3. **A short last row pads its hex columns.** This is the case a naive implementation gets wrong:
   without the padding the printable gutter walks left on the final row and stops being a column.
   It has a test of its own, which checks the gutter's position for every length from nought to
   sixteen rather than for the one length that happened to be tried by hand.

**The view** replaces the `Content::Binary` arm. Two properties, both forced by arithmetic:

- **Virtualised.** 8 MiB at sixteen bytes a row is **524,288 rows**, so the text arm's idiom one
  match-arm above — a single `Label` holding the whole blob — is precisely what must not be
  copied. `show_rows` builds only what is on screen, and takes its row height from the font
  rather than from a literal, because a literal that disagreed with what is painted would drift
  a row out of true for every row scrolled.
- **Scrolls sideways.** A row is about 78 cells; the Inspector's content is 306 points at rest
  and 236 at its narrowest. The line does not fit and is not made to fit — `ScrollArea::both` is
  the image arm's idiom one zone over, and the pane is resizable for a reader who wants the whole
  width at once.

No new key, no new control, no third tab. CORE §4 fixes the Inspector at two tabs and the
keyboard at the table it prints, and hex needed neither: it is simply what `Binary` shows now.

## Deviations

1. **A selection cannot run past the rows that exist.** The body of each row is selectable, as
   the text arm's is, but half a million rows are not all built — so a drag selects within what
   is drawn and stops there. The alternative is not virtualising, which is not an alternative.
2. **A truncated image still gets its sentence, not a dump.** `Content::Image(_) if truncated`
   was left exactly as it was. It could fall back to hex, and deliberately does not: a reader who
   asked for a picture is better served by being told why there isn't one than by being handed
   the bytes of a picture they cannot see.
3. **The gutter cannot distinguish a full stop from an unprintable byte.** Both draw as `.`. That
   is what every hex dump has always done, and the hex columns beside it are the ground truth;
   the gutter is for finding your place, not for reading.
4. **The offset column is eight digits wide for a value that never exceeds seven.** Convention
   beat economy, and the two wasted cells are in a pane that already scrolls sideways.

## The record, straightened

Two more false lines, both found by this round's sweep, both the class P15 was written to close:

| Where | What it said | What is true |
| --- | --- | --- |
| `P14.md` §4 | *"Only **Name** is resizable now."* | **No column is resizable.** `table.rs` sets `.resizable(false)` on the builder and no column overrides it — `8886934` *removed* the per-column calls rather than adding one. The true claim is the weaker one that item was really about: *Name* is the only `Column::remainder`, so it is the only column that **tracks the window**. |
| `CORE.md` §6 | Icons are drawn at *"twice the size of the text"*. | **1.4×.** `ICON_SCALE` has said so since P13, whose own doc records the rollback: *"It was 2× for an afternoon and that was too much."* CORE was never brought along. |

**The thing worth noticing is why P15 missed them.** That round audited what earlier documents had
already flagged — it worked from the ledger, and a ledger only contains what somebody thought to
write down. Neither of these was on it. A record can be internally consistent and still be wrong
about the code, and the only thing that finds that is reading the code with the document open.
P16's verification step makes that sweep a step rather than an accident.

## The CORE operations

Four, all factual rather than rule changes, and none of them touching §9:

1. **§4** — Preview's sentence now describes hex, since it now draws it, including the fixed
   column count and the sideways scroll, which are the two things a reader would otherwise file
   as bugs.
2. **§6** — *"twice the size"* becomes 1.4×, with the P13 rollback recorded beside it so the
   number is not quietly restored by somebody reading the old sentence.
3. **§7 road table** — a P16 row, at `v1.1`.
4. **§7 *After v1.0*** — V1.1 records that hex shipped, and that **PDF was not taken up with it**:
   the condition was a pure-Rust GPL-3.0-compatible renderer, none was viable, and the three
   refusals stand unchanged.

## P16 is done when

- [x] A binary entry draws as hex instead of a sentence about a hex view.
- [x] The dump is virtualised, and half a million rows cost what twenty cost.
- [x] Every row is the same width, and the short last row keeps its gutter — held by a test.
- [x] An offset in this pane names the same byte as an offset in `xxd`.
- [x] No new key, no new control, no third tab, no new dependency.
- [x] Both false lines are corrected where they stand.
- [ ] Checked at the window, by a person, at both 125% and 100%.
- [ ] Released as `v1.1`.

The first of those is the maker's, and it is left standing open for the reason P12 taught: a box
that belongs to nobody is a box that stays empty long after the thing it asks for has happened.

## The ritual

CORE §8: *"Every P-document ends with the full ritual spelled out."* **This one is a version and
not a revision**, which is the first time since v1.0 that has been true, and it changes three of
the steps:

1. `cargo fmt --check` · `cargo clippy --all-targets -- -D warnings` · `cargo test` ·
   `cargo build --release` · `./build/check-deps.sh`, all five by hand, all five again in CI.
2. **`Cargo.toml` goes to `1.1.0`, and `pkgrel` goes back to `1`.** Those two together are what
   make the tag two-numeral: `release.yml` reads `if [ "$REL" = 1 ]; then EXPECT="v${VER%.*}"`,
   so the only tag it will accept is **`v1.1`**, exactly as CORE §7 requires. The rule is
   enforced rather than remembered, which is the whole reason it was written that way.
3. `changelog.Debian` gains a stanza reading exactly `indium (1.1.0-1) unstable; urgency=medium`,
   the string `verify.sh` check 9 asserts.
4. `README.md`: the badges, the artefact filenames — which change shape to `1.1.0-1` — and §4's
   Inspector row, which said Preview shows text and images.
5. Commits in the house voice, from **sudo-megas**, with no AI attribution anywhere.
6. Push. `ci.yml` green on that push. Then `gh workflow run release` — the dispatch before the
   tag, because packaging is never proven on this machine: the committed PKGBUILD pins its own
   `source=` fragment and only the workflow rewrites it.
7. Dispatch green → tag `v1.1` → tag run green → download its three artefacts →
   `gh release create v1.1`, titled **"INDIUM 1.1 — the hex view"**, notes in the house voice.
   The *"Still a beta"* line stays: the gate for dropping it is a testing round in real hands,
   and that has not happened yet.
