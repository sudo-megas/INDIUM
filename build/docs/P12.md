# P12 — The design round

*The half of the testing round that could not be fixed without a decision: the sidebar's order,
a keys popup, a status bar nobody could read, capsules, a row cursor nobody could see — and,
underneath all of it, six milestones of CORE edits that had been ordered and never applied. When
this file and CORE.md disagree, CORE.md wins.*

**Goal in one sentence:** make CORE true, then change it — and build the window the second
testing round asked for.

P11 shipped `v1.0.0-3` and the maker worked all eight rounds of the test plan against it:
**forty-one steps, every one passing.** What that left was the list P11 had deliberately not
touched, because every item on it changes what §4 or §6 says the window *is*.

Two things unblocked it. **CORE.md became mine to edit** — the maker lifted the hand-only rule —
and the standing apply-list turned out to be exactly executable: eighteen operations, every
anchor matching CORE.md at `HEAD` once and only once, nothing drifted in the six milestones
since they were ordered.

**Not in P12: density.** The maker's call, in his words — *"Realistically a laptop screen is
physically small, thats not enough for the core and code change."* No type scale, no spacing
change, no `pixels_per_point`. The 15" 1080p complaint is closed as *won't fix*, on the record.

---

## 1. The backlog, applied

Eighteen operations across §2, §3, §4, §5, §6 and §7, ordered by P6 through P11 and never
landed. They were applied by a script that **asserts each *Find* text matches exactly once
before replacing it**, so a drifted anchor halts the run instead of quietly doing the wrong
thing; the three insertions carry hand-checked anchors.

Three defects in the apply-list itself surfaced only in the doing, and all three were the same
mistake — **a markdown table row is one line**:

- **Op 16** gave a two-cell row for a three-column table. §2's *Direct crates* table is
  `Crate | Enters at | Its sentence`, so the row would have landed a column short. `P11` is the
  missing cell.
- **Ops 1 and 18** wrapped their rows for readability, which markdown reads as a broken table.
- **Op 1** also carried a literal `|` inside `libarchive13t64 | libarchive13`, which markdown
  reads as a column break. It is escaped now.

The record was corrected rather than the document quietly patched: `check-apply.py` re-runs the
verification and prints one line per operation, and the apply-list carries the note.

### The code the edits falsified

A document that changes underneath its own quotations leaves the code lying. **Nineteen comments
and tests were made false** by the eighteen operations — found by a parallel sweep, one agent per
operation, each finding then verified by a second agent told to refute it. Six more were proposed
and refuted, which is the half of the method that matters.

They range from the mechanical — `theme.rs`'s *"CORE §6's fourth colour"* became the fifth when
the Popup row landed above it — to the substantive: `platform/mod.rs` quoted §3's grant as a
complete four-item list and then argued that P8's second window sat *outside* it, in almost the
words Op 2 was about to move *into* it.

Two sequencing rules were followed rather than the obvious order:

- **The six count-bearing comments landed on nine, not eight.** Op 3 raises §4's popup count to
  eight; §2 below raises it to nine. Fixing them in between would have written a number that was
  wrong twice.
- **`P6.md`, `P7.md` and `P8.md` got addenda, not rewrites.** Each describes the road table as it
  stood when it shipped, and each was wrong about where the road ended — P6 said it ended on P6's
  row, P7 on P7's, and the tag was held both times. The house precedent is P10's *"Addendum,
  written by P11"*: the original stands and the correction is appended. A milestone record that
  is edited to have been right is not a record.

## 2. What the window became

### The sidebar, in the order a person reads it

*"Archive must be 1. Recent Files must be 3. As a person's first focus usually the archive
he/she in."* So: **Open file** `O`, **Archive** `1`, a rule, **Bookmarks** `2`, **Recent files**
`3`.

The order is four coordinated edits and not one, which is worth writing down: the numbers beside
the labels are string literals per call in `sidebar.rs`, the keys are a separate `match` in
`mod.rs`, the module doc quotes the order in prose, and CORE §4 states it a fourth time. A key
that disagrees with the label beside it is worse than no key.

**Open file** is an action sitting with the sections rather than with *New* / *Settings* /
*About* at the foot, because it is about the archive you are about to be in. It raises the
desktop's own picker through the machinery P11 already built, on the same channel the
breadcrumb's *Add files…* uses — one path, not a second one.

**Then it did not fit.** Adding a row and a rule pushed *Recent files* out of its own scroll
area, which the first screenshot showed and no test could: a sidebar that scrolls is working as
designed, and a section you cannot see is not. The mark came down from 84pt to 58 and the row
padding from 6 to 5. That is the whole of the density work in this milestone, and it is here
because a zone that does not fit its own contents is a defect rather than a preference.

### Keys, on `F1`

*"I didnt know 'Ctrl+O' opens a file. and still dont know how to exit from the archive."*

A program whose whole interface is bare keypresses owes the reader the list. CORE §4 says the
popup is *"generated from the bindings, never typed twice"*, which is a hard thing to mean
literally — the bindings are a `match` over `egui::Key`, and a `match` is not iterable. So the
rule is enforced from the other end: `the_popup_and_core_agree_about_the_keys` **reads CORE §4's
keyboard table out of `CORE.md` at test time** and fails if the popup and the document differ by
a row. The document is the source; the popup is a copy that cannot drift silently.

The second half of that note has no key at all, so the popup says so in as many words: there is
no way to leave an archive because CORE §1 gives one archive per window, and you close the
window.

### The cursor is a line, not a colour

The old cursor was the filename turning Orange and nothing else. But moving the cursor also sets
the selection, and the selection is Orange at 35% — so the cursor was **orange ink on an orange
wash at 2.06:1**, which the round reported not as faint but as absent: *"dont know what orange
row cursor you talk about. i see none orange thing."*

It is now the 2px edge at 40% white, drawn around the row. Orange keeps its three meanings and
gains no fourth. The mechanism matters: `egui_extras` paints striped → selected → hovered →
content and has **no cursor layer**, so a stroke drawn inside a cell is painted over by the next
cell's fill. The ring is painted after the table from the row response's rect, expanded to
`egui_extras`' own `gapless_rect` so it sits exactly on the selection fill, and square because
that fill is square.

A line and a wash occupy different pixels, which is the whole argument: they cannot hide each
other, where two washes must.

**And the cursor is kept on screen.** There was no `scroll_to_row` anywhere in the tree, so
arrowing past the viewport left the cursor invisible by a second route. It scrolls now, on a
one-shot flag set only by the keyboard — a standing "always show the cursor" would yank the view
back every time somebody scrolled away to read something.

### Rules that can be seen

*"The separator staying on the 'New' button is so faded. cant distinguish it"*, and the same
complaint again about the middle panel. Both are the same 1px line at 8% white, which composites
to **1.18–1.27:1** — not faint, absent.

It is 20% now: **1.68:1 on the worst ground it is drawn on**, and that floor is a test
(`a_rule_can_be_seen`) rather than an intention, because 8% and 20% look identical in a hex
literal and nothing alike on a screen. It stays under the 2px edge's 22% so *two weights and no
third* remains two weights rather than one weight at two thicknesses — which is its own test.

One constant, seven call sites, both complaints.

### Controls are capsules

*"All clickable buttons must have capsules in my honest opinion."*

Radius 10, which is **the number `R_POPUP` already held** — a control's height floor is
`interact_size.y` = 20, so half of it is 10, and epaint clamps a radius to half its rect, so the
same 10 is still a pill on a shorter `small()` button. The vocabulary stays at three values and
`only_three_corner_radii_exist` passes unchanged.

**It is set at the control, never in `install_visuals`.** `widgets.inactive`, `.hovered` and
`.active` are also what a `TextEdit`, a checkbox and the progress track draw through; moving the
constant there would have turned the path field into a lozenge. Rows keep their 3px: a list is
read as a column, and a stack of pills is read as a pile of separate objects.

### A status bar with a hierarchy

*"very poor layout, readability and font formatting. it looks like a mess. Cant really track
whats going on there."*

It was right, and the arithmetic says why: ten fields, one size, one weight, three greys, no
rules, no alignment. Every sentence the program has ever said — `Removed bookmark photos.` and
`Could not create /home/megas/x: permission denied` — rendered identically.

Three fixed rows stay, because the floor of the window must not move and `SB_HEIGHT` is asserted
by a test. What changed is hierarchy: **one subject per row, and it is bold** — the archive's
name, the entry count, the phase; **a rule between the rows**, because they are three statements
and not one paragraph in three pieces; and **a failure is `#FFD800`**.

The rules are **painted into the gaps, never allocated into them**. `ui.separator()` allocates
6pt of its own, and the lane is exactly `3 × SB_ROW + 2 × SB_GAP` in a panel that is
`exact_size` and cannot grow — so a separator between the rows would have pushed row 3 out of the
window. A line down the middle of a gap that already exists costs nothing.

### The failure colour is a state change, not ink

This is the one part of the status bar that is not cosmetic, and it is worth its own paragraph.
`status` was a bare `String` assigned in fifty-six places with no notion of severity, so *"a
failure is yellow"* could not be done in the bar at all.

The severity now rides **with** the sentence, in the value:

```rust
pub struct Status { pub text: String, pub bad: bool }
impl From<String> for Status { /* bad: false */ }
impl Status { pub fn bad(text: impl Into<String>) -> Self { /* bad: true */ } }
```

A separate flag beside the string would have been smaller and wrong: a flag is a thing you can
forget to clear, so a failure followed by an ordinary confirmation would have printed the
confirmation in yellow. Carrying it in the value makes that unrepresentable — every plain
assignment goes through `From`, which clears it by construction. **Thirty-eight sites are failures
or refusals** (CORE §4: *"A refusal is a failure; a confirmation is not"*); the rest are not.

Changing the field's type rather than adding a setter is what made the sweep safe: the compiler
named every one of the fifty-six sites, so none could be missed by a grep that was slightly
wrong.

The count above reads thirty-eight and not thirty-one because the first pass got seven of them
wrong, and the sentence just written is the reason it could: the compiler names every site, and
then a person has to say which are failures. It named them; the grading missed seven, and the one
that mattered was `ExtractMsg::Failed` — every extraction failure the program can report, printed
in the ordinary grey. The other six were `on_list_failure`'s fall-through, which is every archive
that cannot be opened for a reason other than a password, and where the branch two lines above it
had been graded right; the preview error; the second-window error; the refusal to overwrite a
`settings.toml` that would not parse; and both `staging_refusal` sites. A type change makes a
sweep exhaustive. It does not make it correct.

### Fira Mono

The face is **Fira Mono Nerd Font Mono**, regular and bold, at the maker's request.

Three things were checked rather than assumed. The files are **OTF with CFF outlines** where the
old face was TrueType — fine, because egui 0.36 rasterizes through Fontations (`skrifa`,
`read-fonts`, `harfrust`), which reads CFF natively. Fira Mono carries **no ligatures at all**,
which retires the reason the old face was the `NL` cut: a face that cannot form `->` cannot get
it wrong. And both `cmap` tables were read and compared rather than trusted.

**What the swap costs, measured:** 12 132 codepoints against 12 121, so the totals are near
identical and the sets are not. 524 codepoints are lost, of which the ones that could turn up in
a real filename are **Vietnamese** (89 in Latin Extended Additional), **`ə`/`Ə`, the schwa** —
Azerbaijani, the neighbour language most likely to appear beside Turkish — and `ẞ`, `ơ`, `ư`.
The whole Turkish set is present, and so are Greek, Cyrillic, box drawing and the arrows.

A glyph the face cannot draw is not a name INDIUM has lost: since P11 the reading of a name does
not depend on the drawing of it, and a missing glyph is tofu rather than a vanished file. That is
a legibility cost and not a data one — but it is a cost, and `assets/fonts/README.md` states it
rather than leaving it to be discovered.

## 3. What was checked, and how

`cargo test` — 227 across the suite, including two new ones in `theme.rs` and the CORE-parsing
test in `ui::keys`. `cargo clippy --all-targets -- -D warnings` clean. `cargo fmt` clean.
`build/check-deps.sh` still reports **OK: toolkit-free** after the font swap, which was the point
of checking: `ashpd` talks to `xdg-desktop-portal` over D-Bus in Rust and links nothing, so §9's
rule survives — and §9 now says *linkage* is the word and means it.

**And the window was run and looked at**, which is the only test that could have caught what it
caught: the sidebar not fitting. Three screenshots, three builds. A test suite that passes while
a section is scrolled out of its own zone is a test suite measuring the wrong thing, and P10's
whole lesson was about believing a checklist over a window.

## 4. Deviations

1. **CORE.md was edited by me, not by the maker's hand.** Every milestone from P6 to P11 ordered
   its CORE changes into an apply-list and waited. The maker lifted that rule at the top of this
   milestone — *"You can modify CORE.md according to our journey so far and future"* — and the
   backlog it had accumulated is the argument for why: eighteen operations across six milestones,
   with nineteen code comments quietly going false behind them.

2. **§9 was touched, and §9 says it is the maker's alone.** *"This list is authored by the maker,
   not derived. Items enter and leave only by his hand."* No item entered or left. One got a
   clarifying clause, because §2 now names `ashpd` and a reader meeting *"No … portal linkage"*
   three sections later deserves to be told that linkage is the word, `ldd` is the test, and it
   stays clean. Flagged rather than buried.

3. **The keys popup is not generated from the bindings.** CORE §4 says *"never typed twice"* and
   this is typed twice — once as a `match` in `handle_keys`, once as a table in `keys.rs`. The
   honest mitigation is a test that reads CORE.md itself, so the two cannot drift silently; the
   dishonest one would have been to weaken §4's sentence to match what was built.

4. **The sidebar's mark shrank, in a milestone that ruled density out of scope.** 84pt to 58, and
   the row padding with it. This is not the density work the maker declined — that was about
   fitting a 15" screen better. This is a zone that stopped fitting its own contents the moment a
   row was added to it, which is a defect in this milestone's own work.

5. **The status-bar sweep damaged three lines before it was finished.** The script that appended
   `.into()` to every `status` assignment scanned to the next `;` at paren depth zero, which runs
   straight past a `,`-terminated match arm — so it produced `return false.into()`, a
   `return.into()`, and an `.into()` on a `collect()`. Two of the three compiled. Recorded because
   a mechanical sweep that mostly works is the kind that ships a bug: what caught them was reading
   the diff for `.into()` outside status assignments, not the compiler.

6. **Numbers are not column-aligned.** CORE §4 now says *"Numbers hold their columns... a number
   that jumps as it counts cannot be read while it counts."* The bar is monospace, so digits align
   within a field, but the fields still shift as the text left of them changes width. The document
   is ahead of the code here, deliberately: it is the right rule and the wrong milestone to
   rebuild the row's layout in.

## 5. What the round found that no step asked about

The testing round began with the status bar, and the first thing tried was a failure: an entry
extracted into `/boot`, which on this machine is a vfat ESP mounted `drwx------ root root`. The
bar answered **"Extracted 1 entry."** in ordinary grey, and `/boot` held nothing new.

Two defects, stacked, and only the second belongs to P12.

**The colour was the smaller one.** `ExtractMsg::Failed` assigned through `From` rather than
`Status::bad`, so every extraction failure the program can report printed grey. Graded wrong in
this milestone's own sweep; six more like it are named in §*The failure colour is a state change*
above.

**The count was the real one.** `arch::extract` accepted `ARCHIVE_WARN` from
`archive_read_extract` as success. libarchive uses that one code for two opposite outcomes: a
file it wrote but could not finish stamping — `EXTRACT_PERM` against vfat, an everyday case that
must not fail — and a file it could not create at all. A destination the process cannot write
answers `-20` with `Can't create '<path>'` and leaves nothing behind, and INDIUM counted it.
Reproduced against a `0500` directory before anything was changed: `Ok(1)` returned, zero files
on disk.

The fix does not read libarchive's English. On `ARCHIVE_WARN` it asks the filesystem whether the
target exists — `symlink_metadata`, so an entry that is a symlink pointing nowhere still counts —
and fails the extraction if it does not. One case is left open deliberately and said so in the
code: a target left by an earlier extraction cannot be told from one written a moment ago, so a
failed overwrite still counts. Closing it means comparing timestamps, which costs more than the
case is worth.

`tests/write_path.rs` holds the floor now, and was checked the only way a regression test can be:
it fails against the old `arch.rs` and passes against the new one. It skips itself if the
directory it just closed turns out to be writable anyway, because root ignores mode bits and a
test that fails for that reason guards nothing.

This is the second time a testing round has found something no step listed — P11's was
`lock_name_for` — and both times it was found in the first ten minutes, by a person doing the
obvious wrong thing on purpose. That is the argument for the two boxes below staying unticked
until someone does it again.
