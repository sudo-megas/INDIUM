# P6 — Install, explain, and mean it

*Implements CORE.md §8's packages, the README CORE §7 assigns to this milestone, and the
hardening pass that closes what the first five left open. When this file and CORE.md
disagree, CORE.md wins.*

**Goal in one sentence:** INDIUM installs on Arch and on Debian from packages that say
truthfully what they need, explains itself to someone who has never seen it, and stops doing
three things it was doing wrong — tagged **`v1.0`**.

**Not in P6:** hex view (V1.1); the yazi plugin (V1.2); headless subcommands (V1.3); CI as a
**gate** on every push (V1.4 — P6 adds a release workflow only, and §5 draws that line

## 1. The glibc floor, and what it decided

P6 opened by trying to build a `.deb` on the machine INDIUM is developed on, and discovering
that it cannot honestly be done.

```
$ readelf -W --dyn-syms target/release/indium | grep GLIBC_2.43
    38: FUNC GLOBAL DEFAULT UND atan2f@GLIBC_2.43
    48: FUNC GLOBAL DEFAULT UND acosf@GLIBC_2.43
```

Two **GLOBAL** undefined symbols at `GLIBC_2.43`. The build machine runs glibc 2.44; Debian
bookworm ships 2.36, trixie 2.41, Ubuntu 24.04 2.39. A `.deb` wrapping this binary would
install cleanly on any of them and then die at exec with `version 'GLIBC_2.43' not found` —
which is this project's unforgivable failure, in package form: an artefact that says it works
and does not.

The `pidfd_getpid@GLIBC_2.39` and `pidfd_spawnp@GLIBC_2.39` imports beside them are **WEAK**.
They resolve to NULL on an older glibc and cost nothing, so they are not part of the floor.
Every place P6 computes the floor excludes weak symbols deliberately, because counting them
would overstate it by three releases and refuse a package that would have run.

Three consequences, and they shape the whole milestone:

- **`make-deb.sh` takes the binary as an argument.** It never assumes it is running on the
  machine that compiled, because in the working case it is not.
- **The floor is computed from the binary being packaged, never hardcoded.** Built here it
  writes `libc6 (>= 2.43)` and is honest; built on bookworm it writes `>= 2.36` and is
  shippable. A hardcoded floor would be a guess printed as a fact.
- **`verify.sh` fails when the computed floor exceeds its target.** That one gate is what
  makes it impossible to ship a `.deb` that installs and does not run. On the Arch machine,
  against the default target of 2.36, it fails — and that failure is the proof the gate works,
  not a broken step.

The binary the shippable `.deb` wraps therefore comes from Debian. §5 says how.

**The plain tarball shares the Arch floor.** `indium-1.0-x86_64.tar.gz` is built here and needs
glibc 2.43 like everything else built here. It would be dishonest to state the `.deb`'s floor
carefully and let the tarball's go unsaid, so the README and the release notes state both.

## 2. The payload in one place

`build/install-desktop.sh:3` said, from P3 until now, *"Packages redo this system-wide in P6."*
They do not redo it.

Copying the ten-size icon loop into a PKGBUILD and again into a `.deb` script would create
three places for one list to drift, and the first symptom of drift would be a package missing
an icon size nobody noticed. So the payload is factored out once:

```sh
./build/install-payload.sh ROOT [BINARY]
```

`ROOT` is the directory that will hold `bin/` and `share/` — `"$pkgdir/usr"` for makepkg,
`"$work/data/usr"` for the `.deb`, `"$HOME/.local"` for the dev machine. The paths line up
exactly: `$HOME/.local/share/icons/hicolor/…` and `/usr/share/icons/hicolor/…` differ only in
`ROOT`, which is why one script can serve all three.

`BINARY` installs to `ROOT/bin/indium` **only when given**. A package owns `/usr/bin`; cargo
owns `target/release`; the dev-machine install passes none.

P3 §4 made the missing-icon tolerance deliberate — a partial set installs what exists rather
than failing — and it stays. But a *package* missing a size is a different thing from a
developer's tree missing one, so **the tolerance ends at `verify.sh`**, which counts all ten
and fails the release if any is absent. Forgiving where a person is experimenting, strict
where an artefact goes out of the door.

## 3. The Arch package

`build/package/PKGBUILD`, in its own directory because `makepkg` writes `src/`, `pkg/` and the
finished package beside it.

A **source** PKGBUILD, building from the pushed tag rather than packaging the working tree —
`source=("indium::git+$url.git#tag=v1.0")` with `sha256sums=('SKIP')`. Two reasons for the git
source: GitHub's autogenerated tag tarballs are not byte-stable, so a checksum committed today
can stop matching a file nobody edited; and a checksum for a tag cannot exist in a commit that
predates the tag. `SKIP` is ordinary and correct for a VCS source, because the tag is what pins
the content. A dirty working tree cannot leak into a release this way, which is worth more than
the convenience of packaging what is on disk.

**`depends` is not an `ldd` transcript, and that is the point.**

| Entry | Why |
| --- | --- |
| `libarchive` | The one `NEEDED` beyond the floor. `build.rs` emits exactly one `rustc-link-lib`, and CORE §2 already wrote this dependency's sentence |
| `wayland` | Owns `libwayland-client.so.0` and `libwayland-egl.so.1` |
| `libxkbcommon` | Owns `libxkbcommon.so.0` |
| `libglvnd` | Owns `libEGL.so.1` |
| `glibc`, `libgcc` | The floor, listed rather than assumed from `base` |

The middle three **do not appear in `ldd` output at all** — winit and glutin `dlopen` them by
name at runtime, and `strings` on the binary is where the sonames are. CORE §2's system-library
table already names all three as what *"the compositor session already provides"*; a package
still has to say so, because a `depends` array derived from `ldd` would ship a program that
installs perfectly and then cannot open a window.

`check()` runs `cargo test` **and `./build/check-deps.sh`**, so a package can never be built
from a binary that grew a toolkit. CORE §2's gate belongs inside the packaging, not beside it.

`options=('!debug' '!lto')` because `Cargo.toml`'s `[profile.release]` already sets `strip` and
`lto`: makepkg's `debug` would split an empty debug package out of an already-stripped binary,
and its `lto` only ever touched C flags. Both are on in the stock `/etc/makepkg.conf`, which is
why they are turned off explicitly rather than assumed off.

**No `.install` file.** Arch already ships
`/usr/share/libalpm/hooks/update-desktop-database.hook` and
`/usr/share/libalpm/hooks/gtk-update-icon-cache.hook`, triggering on exactly the two paths this
package writes. A maintainer script calling those binaries would duplicate a hook that is
already there.

Licences go to `/usr/share/licenses/indium/` — both of them. GPL-3.0-only is a common licence
on Arch and shipping its text costs 35 KB; OFL-1.1 is not common and must ship regardless, so
shipping both removes an argument for the price of one file.

## 4. The `.deb`, written by hand

`dpkg-deb` is not installed on the development machine, and nothing was installed to make this
work. CORE §2 admits a dependency only when it does genuine work *for the program*; `cargo-deb`
and `dpkg` do work for the maker and cannot fill in that sentence. The precedent is already
written down in `tests/fixtures/README.md`: build-machine tooling is a different category from
a linked dependency, and the fixtures were made with whatever was convenient.

So the format is written out directly. A `.deb` is an `ar` archive of exactly three members in
exactly this order — `debian-binary` holding `2.0\n`, `control.tar.xz`, `data.tar.xz` — and an
`ar` member header is six fixed-width text fields totalling sixty bytes followed by a two-byte
magic. Both are written by hand, then read back with `ar t` from binutils as the cheapest
possible proof the headers are well formed. This is the same posture as the hand-written CRC32
table and the hand-written libarchive FFI: the thing is small, the specification is public, and
writing it removes a question rather than adding one.

Two choices inside that worth stating:

- **`xz` for both members.** `zstd` data members need dpkg ≥ 1.21.18 and would exclude bookworm
  for no gain; `xz` has been accepted for `data.tar` since dpkg 1.15.6 and `control.tar` since
  1.17.6, and is what `dpkg-deb` itself produces.
- **`--format=gnutar`, never bsdtar's default.** bsdtar defaults to restricted pax and emits
  `x`-type extended headers whenever it feels the need — a sub-second mtime will do it. dpkg's
  tar reader handles ustar and GNU extensions; a pax extended header is not a thing to bet a
  release on.

Ownership is set with `--uid 0 --gid 0 --uname root --gname root`, so **no `fakeroot`**. Every
mtime in both tarballs and every `ar` header takes `SOURCE_DATE_EPOCH` or the commit date, and
the changelog is gzipped with `-9n` so the gzip header carries no name and no timestamp: the
same input gives the same bytes.

`Depends: libc6 (>= X), libgcc-s1 (>= Y), libarchive13t64 | libarchive13, libwayland-client0,
libxkbcommon0, libegl1` — `X` and `Y` computed per §1, the last three dlopened and invisible to
`ldd` exactly as on the Arch side.

**The alternation is a CORE edit this milestone orders.** CORE §2's system-library table says
*"on Debian the package declares `libarchive13`."* That was true when it was written. Debian's
time64 transition renamed the package to `libarchive13t64` in trixie, where plain `libarchive13`
is not available at all. `libarchive13t64 | libarchive13` is correct on both suites, but the
sentence in CORE is now half-true, and correcting a sentence in CORE is the maker's hand.

Also shipped, because Debian expects them and each costs almost nothing:
`/usr/share/doc/indium/copyright` in DEP-5 form, referencing
`/usr/share/common-licenses/GPL-3` as Policy 12.5 requires rather than duplicating the text,
with OFL-1.1 inlined because it is not a common licence; a gzipped `changelog.Debian`; and
`md5sums`.

**No `postinst` or `postrm`.** Debian has dpkg triggers for both caches — `desktop-file-utils`
declares interest in `/usr/share/applications`, and the GTK library packages in
`/usr/share/icons/hicolor`. A maintainer script calling either would duplicate an existing
trigger. The symmetry is worth naming: **both distributions already own these two caches, and
INDIUM does not need to touch either.**

## 5. The release workflow, and what it is not

CORE §7 puts CI at **V1.4**: *"build, test, `check-deps.sh` as a gate."* P6 adds a GitHub
Actions workflow, and it is important to be exact about which half that is.

What P6 adds is a **release** workflow, and it exists for one reason: §1's floor. The Debian
binary is built inside a `debian:bookworm` container, so it links against glibc 2.36 **by
construction rather than by promise** — no assertion about the build machine has to be trusted,
because the build machine is the oldest supported target. This machine physically cannot produce
that binary, and the alternative was to ship a `.deb` nobody had built on Debian.

What P6 does **not** add, and what remains V1.4: CI on every push, `check-deps.sh` as a required
check, a red build blocking a merge. The workflow here runs on a tag and on a hand dispatch, and
gates nothing.

**It triggers on `workflow_dispatch` as well as on `v*` tags, and the manual trigger is not a
convenience.** Without it, the workflow's first ever run would be on the `v1.0` tag — and a
mistyped package name or a rustup step that does not work under that container would burn a tag
that only gets used once. It is dispatched by hand on `master` and proven green **before the tag
exists**. The first run of a release workflow must never be the release.

`permissions: contents: read`, explicitly and minimally. The workflow uploads the `.deb` as an
artifact and stops; it does not create or edit a release. Creating the release stays one
deliberate human step, with all three artefacts attached at once.

Two footnotes the workflow owes anyone reading it: bookworm's packaged `rustc` is 1.63 and
cannot build `eframe` 0.36, so the container installs rustup; and `libarchive-dev` is required
to link, because `build.rs` asks for `-larchive`.

## 6. Hardening

Nine items. The order matters — each lands on a tree the previous one made safe, and §6.9 lands
last because it is the only one that could break something that currently works.

### 6.1 `Ctrl+C` was stealing the chord from every text field

`Ctrl+A` is guarded on `typing`. `Ctrl+V` is guarded on `typing` and carries a comment saying
why. `Ctrl+C` was guarded on neither, so with focus in the filter bar, the rename box, the
Extract path field or the `Ctrl+O` path field, the chord that copies text instead started a full
archive copy-out. `Ctrl+F` and `Ctrl+O` are correctly unguarded — they are not chords a
`TextEdit` claims.

Five characters, and the highest value per character in the milestone.

### 6.2 Three silent recents-save failures

`save_settings` is a proper method that reports both the broken-file refusal and the write
error. Recents had no equivalent: three call sites — `Del` on a recent, "Remove from list" in
the context menu, "Clear list" in Settings — each did `let _ = save_recents(…)` and dropped the
result on the floor. A settings file that would not parse spoke up; a recents file that would
not save did not.

`save_recents` is hoisted beside `save_settings` and shaped identically. **One ordering detail
decides whether the fix works:** every one of those sites saved and *then* overwrote the status
line with a success message. The success status is now set first and the save called last, so a
real error wins the line instead of being clobbered by a cheerful sentence about a write that
did not happen.

### 6.3 A dead branch in the recents list

Double-clicking a recent file that is no longer on disk assigned `None` to an
already-`None` `Option` and did nothing at all, silently. The sidebar already handles the same
case honestly — *"… is no longer there."* — so the table now does what the sidebar does.

### 6.4 About had no date, and CORE §4 says it does

CORE §4's sixth popup: *"The mark, the maker, **the version and date**, the source address and
the licence in full."* The About popup rendered Version, Maker, Licence and Source, and no date
anywhere. This is the failure this project names as unforgivable — a document describing
behaviour the code does not have — sitting inside CORE itself, in the one popup whose entire job
is telling the truth about the program.

A hand-maintained constant, updated by the maker at each tag, rather than a `build.rs`
timestamp: a build-time date makes the binary non-reproducible, and would then need
`SOURCE_DATE_EPOCH` handling to stop being a lie of a different kind. One line, deterministic,
and exactly how the licence text is already embedded.

### 6.5 There are eight popups, and CORE §4 numbers seven — a CORE edit, ordered

`Popup` has eight variants. `OpenPath` is a real window, opened by `Ctrl+O`, and it has existed
since P1. CORE §4 numbers seven popups and does not include it — **while CORE §4's keyboard
table already carries `Ctrl+O`.** CORE ordered the mechanism and forgot to number the window.

P4 §5 declined to *add* an eighth popup because it did not need one; this is the opposite
situation — the eighth already exists and has since `v0.1`. The honest fix is the edit, not a
quieter comment: a comment-only change would leave CORE saying seven while the program draws
eight, on the eve of `v1.0`.

**Ordered CORE edit:** §4's count becomes eight and the list gains

> 8. **Open** (`Ctrl+O`). A path field with `Enter` to open. The one popup that appears with no
>    archive loaded, because it is how an archive gets loaded.

The false doc comment in the source is corrected in the same milestone, paired with it.

### 6.6 One meaning, one colour — P5 Deviation 3, reopened

P5 recorded this and left it alone, deliberately, as the larger of two polish options. The maker
has reopened it for `v1.0`.

`selectable_label` painted CORE §6's orange on the Inspector tabs, the New Archive preset chips
and the Settings toggle, while the sidebar signalled the very same "this is active" state in
Aubergine. Two colours for one meaning, in one window.

CORE §6 assigns each its role. Aubergine is *"selection context, active sidebar item"*. Orange is
*"reserved for exactly three meanings: the current selection, staged changes, and
Apply/progress"*, and it means *something will happen*. A tab, a preset chip and a toggle are
**which mode is active** — nothing is about to happen because a tab is open. That is Aubergine's
work, and the sidebar was already doing it correctly.

The table's row cursor stays orange: it genuinely is *the current selection*, which is the first
of the three meanings §6 grants.

**The conflict was worse than P5 recorded, and in one case it was inside a single window.** The
New Archive popup paints its preset chips orange and, three rows below, paints the selected
*method* Aubergine by hand — the same "which one is chosen" meaning, two colours, one popup.
There are exactly four `selectable_label` sites in the program: the two Inspector tabs, the
preset chips, and the two Settings toggles. Everything else that signals "active" — the sidebar,
the method rows, the focused Recents and Bookmarks rows — was already hand-painting Aubergine
and always had been.

**The measurement, because P5's 1.74:1 finding deserves an answer rather than an assumption.**
That number was Aubergine as *ink*. This is Aubergine as *ground*, which is a different question
and comes out the other way:

| Pair | Ratio | |
| --- | --- | --- |
| `#EEEEEC` on Aubergine `#772953` | **8.12:1** | what the chips become — AAA at every size |
| `#EEEEEC` on the chip today | 4.90:1 | what they are now |
| Aubergine against the panel | 1.72:1 | reproduces P5's 1.74:1 for the same pair |
| The chip today against the panel | 2.85:1 | |

So the text gets **more** legible, not less. What gets fainter is the fill against the panel —
and that is the identical pair the sidebar has shipped as CORE §6's sanctioned "active item"
signal since P1. Rejecting it here would mean rejecting the sidebar.

Two consequences follow, and both are part of the change rather than notes about it:

- **The fill must not be the only cue.** The Inspector tabs already carry the state in ink as
  well — `TEXT` when open, `TEXT_MUTED` when not — and the preset chips and Settings toggles did
  not. They gain it, which is where the 8.12:1 against 3.30:1 does the real work.
- **Hover had to be answered in the same breath.** `widgets.hovered.weak_bg_fill` is Aubergine
  globally, so the moment the selected fill became Aubergine, a chip under the pointer painted
  exactly like the chosen one — and with four chips in a row the pointer is nearly always on one.
  A fill that means both *active* and *the mouse is here* means neither.

**The override is scoped, and that is not a stylistic preference.** egui resolves a
`selectable_label`'s selected fill from `Visuals::selection.bg_fill` — and that is the same field
`egui_extras` reads to paint the entry table's row cursor. Setting it in `install_visuals` would
have repainted the one thing §6 requires to stay orange. `visuals_mut` is clone-on-write per
`Ui`, and the three sites sit in `Ui` trees that are siblings of the table's rather than
ancestors, so the override cannot reach it.

### 6.7 CORE §5 does not list a format the program writes — a CORE edit, ordered

Found while writing the README, by checking every claim it made against the code rather than
against CORE.

CORE §5's write sentence reads: *"`tar` with the filters `gz`, `bz2`, `xz`, `zst`, `lz4`; `zip`
(Deflate); `7z` (LZMA2, via `sevenz-rust2`)."* Every entry is a *filter* over tar, and plain
uncompressed tar is not among them.

The program writes it. `Method::Store` is the first entry of `METHODS`, it maps to a tar
container with the extension `.tar`, and a test asserts the exact sentence the New Archive popup
shows for it: *"Building plain.tar — tar, Store."* CORE §5 even gives Store its own one-sentence
verdict in the method table two paragraphs below — *"No compression — instant, and as large as
the input."* — so §5 contradicts itself: its verdict table names a method its write list does
not permit.

This is the smallest of the three edits and the most embarrassing to leave, because the fault is
internal to a single section.

**Ordered CORE edit:** §5's write sentence names plain `tar` alongside the filtered forms.

### 6.8 Binary hardening: nothing to add, everything to record

Measured, not assumed:

| Property | State |
| --- | --- |
| PIE | yes — `Type: DYN` |
| Full RELRO | yes — `GNU_RELRO` + `BIND_NOW` + `FLAGS_1: NOW PIE` |
| NX stack | yes — `GNU_STACK` `RW`, no `E` |
| RPATH / RUNPATH | none |
| TEXTREL | none |
| Stripped | yes — `[profile.release] strip = true` |
| FORTIFY | not applicable |

The stock `x86_64-unknown-linux-gnu` release build already gives the first four. `_FORTIFY_SOURCE`
is a libc macro over C string and memory calls and has no Rust analogue; the only C in the
process is the distribution's own libarchive, hardened by whoever built it. Stack canaries need
a nightly flag and buy little against a language with bounds checks.

So P6 adds no flags. It **asserts** PIE and `BIND_NOW` in `check-deps.sh` — precisely *because*
they are defaults, since a toolchain that quietly stopped providing them would otherwise ship
without anyone noticing — and writes the table down here so nobody re-derives it at V1.1.

One honesty note that belongs in the open rather than in a footnote: `Cargo.lock` contains
`x11rb` and `x11rb-protocol`, pulled in through `arboard` on eframe's clipboard path. They are
pure Rust, and `strings` on the binary finds no `libX11` or `libxcb` soname, so `check-deps.sh`'s
gate is satisfied and truthful — CORE §9's *"No X11"* is about linkage, and INDIUM links none.
There is unreachable X11 *protocol* code compiled in. Better said once, plainly, than discovered
by someone who then wonders what else was not mentioned.

### 6.9 Nothing starts twice, and copy-out stops freezing the window

The largest change in the milestone, and the last to land.

**First, nothing may start twice.** `begin_extract` set the cancel flag and the receiver
unconditionally, and `begin_apply` did the same. Press `E` and Enter twice and the second run
replaced both: the first worker's send failed silently into a dropped channel, its completion
never arrived, its progress never cleared, and the Cancel button in the status bar reached only
the newer worker while the older one kept writing files with no way to stop it. Both now return
early with an honest sentence. The condition already existed; nothing had ever asked it.

This had to land first, because the second half multiplies the number of ways to start a second
extraction.

**Then, the extraction comes off the UI thread.** `copy_out` and `open_with` called
`arch::extract` inline, with no progress sender and a fresh local cancel flag that nothing else
could ever set — while `begin_extract`, twenty lines away, spawned a worker, passed the sender,
used the shared flag and requested a repaint. So `Ctrl+C` on a large selection froze the window,
the progress bar never moved, and the Cancel button was drawn but unreachable, because the UI
thread was inside libarchive.

Nothing new was needed to fix it. `drain_worker` already collected extraction messages and
handled progress, completion and failure, and already kept the repaint pump alive while work was
in flight. The password park-and-resume path already existed for both operations and did not
move. What was missing was a way to say *what to do once the bytes are on disk*, so the two
operations gained one — a `PostExtract` recorded before the worker is spawned and consumed when
it reports done. Everything that used to run after the inline call now runs there instead:
collecting the files and putting URIs on the clipboard, or scanning `.desktop` files and seeding
the picker. A failure clears it.

Three things had to be true, and each was checked rather than assumed:

- **The scratch directory must survive until the post-step reads it.** `Scratch::begin` discards
  the *previous* directory of its kind, so a second copy-out is exactly what would pull the rug
  out from under the first — which is what §6.9's first half prevents. The two halves are one
  change wearing two names.
- **The passphrase is cleared when the worker reports done**, so the post-step must not need it.
  Neither does; and the worker takes its own copy before returning, so the resume path in the
  password popup can still clear it immediately, as it always did.
- **The Open With picker must appear on the frame the extraction finishes**, not one frame later.
  The repaint request already in the completion path covers it.

## 8. Fixtures and tests

**No new fixtures.** P6 adds no format work, and its two new subjects are the packages
themselves.

`tests/package_path.rs` is new, and it is the pleasing part of the milestone: **INDIUM reads its
own packages.** `arch::Reader::open` already calls `archive_read_support_format_all` and
`archive_read_support_filter_all`, so libarchive reads a `.pkg.tar.zst` and reads a `.deb` — a
`.deb` being an `ar` archive, which is on CORE §5's supported list. `Entry` already carries
`mode`, `uid`, `gid`, `uname`, `gname` and `size`, which is everything a package check wants. No
test dependency enters; the hand-written `TempDir` is copied from `read_path.rs` exactly as
`write_path.rs` already copies it.

Every test is `#[ignore]`d, on the precedent of the clipboard test that needs a live Wayland
session. The artefacts do not exist during an ordinary `cargo test`, and a test that silently
passes when its subject is absent is worse than no test at all.

- the `.pkg.tar.zst` holds exactly the payload, ignoring pacman's own `.PKGINFO`, `.MTREE` and
  `.BUILDINFO`
- all ten hicolor sizes are present — the tolerance lives in `install-payload.sh`, the loudness
  lives here
- the packaged binary is root-owned and `0755`
- the `.deb` has three members in the right order
- the `.deb`'s `data.tar.xz` holds exactly the payload
- everything in it is root-owned with sane modes
- **the two packages ship the same payload** — and the exact claim needs care, because the two
  distributions forbid it being a plain set comparison. §3 sends both licences to
  `/usr/share/licenses/indium/` because that is Arch's convention; §4 writes
  `/usr/share/doc/indium/copyright` and `changelog.Debian.gz` because Debian Policy 12.5 and 12.7
  require it. Neither is removable — a package that obeyed only the other system's convention
  would be broken on its own. So the test compares `usr/` **minus the two paperwork prefixes**,
  and then asserts the exception in both directions: each package carries its own paperwork, and
  *nothing* under the other's. That is a stronger statement than set equality, not a weaker one —
  the packages differ exactly where their distributions command them to, and nowhere else. This
  is the test that makes §2 true and keeps it true
- neither package ships a RAR association — CORE §5 and §8's deliberate absence, checked in the
  shipped artefact rather than in the source that produced it

`build/package/verify.sh` does what a Rust test should not: `desktop-file-validate`, the
`MimeType=` list against CORE §8, the ELF facts of §6.7, **the glibc gate of §1**, the
`.PKGINFO` fields, `ar t`'s member order, every `control` field including the synopsis length,
`md5sums` re-verified against the extracted tree, and the changelog's gzip header.

Manual checklist before release — the maker's, because each touches his real system:

- [ ] `sudo pacman -U` the built package, then launch INDIUM from the desktop menu
- [ ] `--set-default`, then `xdg-open` an archive — it rewrites real MIME associations and has
      been his to run since P3 Deviation 7
- [ ] `Ctrl+C` on a large selection: the progress bar moves and Cancel works
- [ ] `Enter` on a large member: the same, and cancelling leaves no picker
- [ ] the Inspector tabs, the preset chips and the Settings toggle read as active without
      claiming something is about to happen
- [ ] the `.deb` from the workflow installs on a real Debian and runs

## 9. The release ritual

```
cargo fmt
cargo clippy -- -D warnings
cargo test
cargo build --release
./build/check-deps.sh
git add -A
git commit -m "P6: the README"
git push

# The workflow is proven before the tag exists. Dispatch release.yml by hand on
# master and confirm the bookworm build, make-deb.sh and verify.sh all go green.
# The first run of a release workflow must never be the release.

git tag v1.0
git push origin v1.0

# Arch. makepkg builds from the pushed tag, so the tag comes first — this is not
# packaging the working tree, and a dirty tree cannot leak into a release.
( cd build/package && makepkg -f )

# Debian. The binary comes from the workflow's debian:bookworm container, because
# the Arch build machine's own binary imports GLIBC_2.43 and bookworm has 2.36.
# make-deb.sh assembles the package from whatever binary it is given, anywhere.

# Both artefacts, proved without installing either.
DEB_TARGET_GLIBC=2.43 ./build/package/verify.sh   # the local .deb, gate raised
./build/package/verify.sh                         # the CI .deb, gate at 2.36
cargo test -- --ignored

tar czf indium-1.0-x86_64.tar.gz -C target/release indium
```

`Cargo.toml`'s version becomes `1.0.0` in P6's **first** commit rather than its last, which is a
departure from every milestone before it. The reason is mechanical: from the packaging commits
onward every script reads its version out of `Cargo.toml`, and a milestone that produced an
`indium-0.5.0-1` package during its own packaging work would be this project's unforgivable
failure in miniature.

GitHub release on `v1.0`, with `indium-1.0.0-1-x86_64.pkg.tar.zst`,
`indium_1.0.0-1_amd64.deb` and `indium-1.0-x86_64.tar.gz` attached.

**Not a pre-release.** `v0.2` through `v0.5` were pre-releases because they were pre-1.0, and the
flag was accurate every time: each shipped a program CORE §7 said was not finished yet. CORE §7
calls this table *"the road to v1.0"* and ends it here. Marking the end of the road "pre-" would
say the road is not finished, contradicting the document that defines when it is. If something is
not ready to be called 1.0, the honest move is not to tag 1.0 — not to tag it and disclaim it.

Notes in the house voice: the two packages and where each runs, **the glibc floor of every
artefact stated plainly**, RAR's deliberate absence, and the sentence that INDIUM verifies its own
packages by reading them with its own reader.

## Deviations

*(recorded during implementation; empty is a valid state)*

1. **A GitHub Actions workflow arrives in P6, and CORE §7 puts CI at V1.4.** Scope moved *into*
   `v1.0` rather than out of it, which CORE §7's sentence does not forbid — it fences only the
   other direction. It is here because §1 left no alternative: the development machine cannot
   produce a Debian binary, and the choice was a workflow or a `.deb` nobody had built on Debian.
   Only the release half arrived; the V1.4 gate on every push did not, and §5 says so in its own
   words. Whether CORE §7's V1.4 line should now be amended is the maker's call and is asked
   rather than assumed.

2. **The version moved to the milestone's first commit**, where every previous P moved it last.
   §9 gives the reason: the packaging scripts read it out of `Cargo.toml`, so it had to be right
   before they existed rather than after.

3. **CORE §5's write list turned out to omit a format the program ships**, and this was found by
   checking the README's claims against the code rather than against CORE. It is written up as
   §6.7 and ordered as the third CORE edit. Worth recording that it was found the same way P5 §1
   found what P4 left open: by not trusting the document.

4. **The `!debug` rationale in the PKGBUILD is not the one this milestone first wrote down.** The
   draft said makepkg's `debug` option cannot reach a Rust build. It can —
   `/usr/share/makepkg/buildenv/rust.sh` appends a `--remap-path-prefix` to `RUSTFLAGS`. The
   second reason given was that `strip = true` discards the debuginfo at link, so the split
   package would be empty and the remap would have nothing left to remap. **The first half of
   that is right and the second half is also wrong** — see Deviation 18, which is what a real
   `makepkg` run said about it. Two drafts of one comment, each confidently wrong in a
   different way, and only building the package settled it. `!lto` is as first written —
   makepkg's option only reaches CFLAGS, CXXFLAGS and LDFLAGS, which cargo never reads.

5. **`make-deb.sh` had a silent-corruption hole in its first draft, and the shape of the fix is
   worth keeping.** `bsdtar … | xz > out` under POSIX `sh` has no `pipefail`: a dead `bsdtar`
   leaves `xz` compressing nothing, `xz` exits 0, `set -e` sees success, and the `.deb` ships with
   an empty data member that `ar t` reports as perfectly well formed. The tar is now written to a
   file so `bsdtar` is the last command of its own pipeline, and the failure was reproduced with a
   deliberately failing `bsdtar` before and after. A package that is structurally valid and
   materially empty is exactly the failure this project exists to refuse.

6. **The release workflow's container needs three packages the specification did not list.**
   `libarchive-tools`, because Debian splits `bsdtar` out of the library package where Arch ships
   it inside; and `desktop-file-utils` and `file`, because `verify.sh` counts a missing tool as a
   *failed* check rather than a skipped one — deliberately, since a verifier that quietly stops
   verifying is worse than no verifier.

7. **`verify.sh`'s RAR check is scoped to the `MimeType` value and not to the whole file.** This
   project writes down what it deliberately omits, so the desktop entry carries a comment saying
   RAR is absent — and a whole-file grep would read that comment as RAR being present. Verified
   in both directions.

8. **Reconciling orange and Aubergine required moving the hover fill in the same change**, which
   §6.6 did not anticipate. `widgets.hovered.weak_bg_fill` is Aubergine program-wide, so the
   moment the *selected* fill became Aubergine, a chip under the pointer painted exactly like the
   chosen one. The helper moves both, and the reason is one sentence: a fill that means both
   "active" and "the mouse is here" means neither.

9. **The README ships without a screenshot.** The reference was written and then removed rather
   than left pointing at a file that does not exist — a README whose first image is broken is this
   milestone's own failure in miniature, on the front page. P5 Deviation 9's reasoning still
   stands: driving the window programmatically asks for standing input-device control, which is
   not a thing to accept on someone's behalf. A screenshot the maker takes with his own
   compositor is untouched by that, and adding it is one line and one file at
   `build/screenshot.png`.

10. **`indium-0.4-x86_64.tar.gz` left the index but not history.** `git rm --cached` and a
    `.gitignore` line stop it growing; the 6.3 MB already in history stays there. Rewriting
    history immediately before the `v1.0` tag was judged a worse trade than carrying it. Release
    artefacts belong on the release page, which is where `v1.0`'s go.

11. **`build/package/README.md` was committed with the files it describes rather than with the
    PKGBUILD it sits beside.** It names `make-deb.sh` and `verify.sh`, and a document that
    describes files not yet in the tree is the fault this project treats as unforgivable — even
    when the gap is one commit wide.

12. **§8 of this document asked for something §3 and §4 of it make impossible, and §8 is what
    changed.** It required the two packages to be set-identical under `usr/`. They cannot be:
    Arch puts licences at `/usr/share/licenses/indium/` and Debian Policy wants
    `/usr/share/doc/indium/copyright` and a changelog, and a package obeying only the other
    system's convention would be broken on its own. This surfaced while writing the test, which
    is the right way round — the test could not be made to pass without either weakening the
    claim or breaking a package, so the claim was wrong. It is now the payload minus each
    distribution's paperwork, plus an assertion in both directions that neither package carries
    any of the other's. Recorded because a specification that survives contact with its own
    implementation unchanged is usually one nobody checked.

13. **§6.9 uncovered a bug it was not looking for: a cancelled copy-out offered partial files.**
    `arch::extract` returns `Ok` with a partial count when the cancel flag is set, so the
    completion arm cannot tell "finished" from "stopped halfway" by its result alone. Inline, the
    question never arose because there was no working Cancel to press. Routing the operation
    through the worker gave the user a Cancel button and therefore gave the program a way to put
    a half-extracted selection on the clipboard as though it were whole. The completion arm now
    reads the flag and says *"Cancelled. Nothing was offered."* Plain extract keeps its existing
    sentence. Fixing a freeze created the opportunity for a quieter and worse fault, which is
    worth recording as the shape of that kind of change.

14. **The guards had to reach further than §6.9 first described.** Routing `Ctrl+C` and `Enter`
    through the worker made them share the cancel flag with Apply for the first time, which
    created two *new* reachable hazards rather than closing one: an Apply started during a
    copy-out silently cancelled it, and an extraction started during a rebuild left the rebuild's
    Cancel pointing at a flag nobody read. So the refusals go both ways — an extraction refuses
    while a rebuild is running and a rebuild refuses while an extraction is, each before it
    touches the flag. CORE §3 says "the UI thread and one worker", and this is that sentence
    enforced rather than assumed.

15. **`PostExtract::OpenWith` boxes its entry.** An `Entry` measures 288 bytes, so the unboxed
    variant tripped `clippy::large_enum_variant` under `-D warnings`, and adding an `#[allow]` to
    silence a lint is not a thing this repository does. `ListMsg::Entry` already boxes for the
    same reason, so the precedent was in the file.

16. **Three faults in the same family are known and not fixed, deliberately.**
    - **A refusal may never be seen.** All four "already running" sentences are written while a
      progress bar is on screen, and the status bar draws the bar *instead of* the status text.
      The refusal is correct and the work is genuinely prevented; the message is what may not
      arrive. Redesigning the status bar is a larger change than the one ordered.
    - **Opening another archive during a copy-out** still signals the shared cancel and installs
      a fresh flag, so the completion arm reads "not cancelled" and offers partial files. This is
      pre-existing — `open_archive` has always done it to a running extract — and §6.9 widened
      its reach rather than creating it. Closing it properly means the worker carrying its own
      flag and the completion arm checking *that*, which is a third mechanism.
    - **A password can be typed for an operation that is then refused.** The passphrase is
      cleared by the in-flight completion, so nothing outlives it.

    All three are recorded rather than quietly fixed because each wants a decision about
    mechanism, and CORE §3 belongs to the maker.

17. **The `src` work landed in two commits split by file rather than the three split by concern
    this milestone planned.** `settings.rs` carries one line of the colour change and one of the
    `save_recents` fix, and splitting a single file across two commits to make a narrative come
    out evenly would have produced a prettier log and a worse record. Colour goes first because
    the hardening commit's `settings.rs` calls `theme::active_fill`, so the other order would
    have left a commit that does not build — and a milestone about honest packaging should not
    ship history that cannot be checked out and compiled.

18. **The Arch package shipped the builder's home directory, and only a real `makepkg` run
    said so.** `makepkg --printsrcinfo` was clean, the syntax was clean, and every claim in the
    file had been checked against `pacman -Qoq` — and the package still came out carrying
    `/home/megas/…` inside the binary. `makepkg`'s own check caught one reference
    (*"Package contains reference to `$srcdir`"*, a generated `glutin_egl_sys` binding) and
    `strings` found 427 more pointing at the cargo registry, which nothing warns about.

    The cause was §3's own `!debug`. `rust.sh` adds `--remap-path-prefix` **only** when the
    `debug` option is on, so switching it off to avoid an empty debug package silently switched
    off the path remapping too. These are panic locations rather than debug information, so
    `strip = true` never touched them. `build()` now does the remap itself, for both `$srcdir`
    and the registry, and the comment on `!debug` — which had said the remap "has nothing left
    to remap" — is corrected, because it was wrong.

    Recorded at length because of how it was found: the milestone's own verification was a
    synthetic package that mirrored `package()` exactly and passed every test. It could not
    have caught this, because the fault was not in what `package()` installs but in how the
    binary was compiled. Building the real thing is what found it, and building the real thing
    before the tag existed required pointing the PKGBUILD at a local clone — which is now the
    reason this milestone can say the Arch package works rather than that it should.

19. **The release workflow's first run failed, which is the only reason §5 insists on the
    manual trigger.** `actions/checkout` writes the tree as a different uid than the steps run
    as, so git refused the repository — *"detected dubious ownership"* — and `make-deb.sh`,
    which asks git for the commit date behind its reproducible timestamps, exited 128. Every
    step before it passed: the container came up, all the apt package names resolved, rustup
    installed a usable toolchain, the release built, the tests passed and the toolkit gate held.
    The one thing that broke was the one thing no local run could have exercised.

    Had this arrived on the `v1.0` tag it would have burned a tag that gets pushed once. §5
    argued for `workflow_dispatch` in the abstract before any of this happened; it is recorded
    here because the argument turned out to be worth exactly what it claimed.

    Two fixes, because one would have been the wrong lesson. The workflow declares the checkout
    safe, which is the documented remedy and is true. And `make-deb.sh` no longer requires git
    to answer: it asks, tolerates refusal, and then **insists on being told** rather than
    falling back to the current time. A fallback would have made the package build and its
    reproducibility claim quietly stop being true, which is worse than the failure it replaced.

20. **The gate was measuring the right binary for the wrong reason, and only having two real
    `.deb`s at once showed it.** §1 claims the gate makes it impossible to ship a `.deb` that
    installs and does not run. It computed the floor from `target/release/indium` — which in CI
    is exactly the binary being packaged, so the claim held at the only moment it decides
    anything. But holding by coincidence is not the same as holding. Verifying the CI-built
    `.deb` on this machine measured the Arch binary beside it and reported 2.43 for an artefact
    whose real floor is 2.35: a number belonging to no shipped thing at all.

    The gate now takes its subject from inside the `.deb` when there is one, and says which
    binary it measured on every run. Two smaller faults surfaced while making that change and
    are worth naming because both would have been invisible: reassigning `$BIN` leaked into
    later checks and made one hint name a temporary file as the thing to rebuild; and the
    obvious guard, `have_deb`, is set by check 6 and would have been empty at check 4 — the
    fix would have compiled, run, passed, and done nothing.

    With both real artefacts present the script now reports **36 passed, 0 failed, 0 skipped**
    at the default target, and the CI `.deb`'s floor is **2.35** — below bookworm's 2.36,
    because `make-deb.sh` computes what the binary actually needs rather than what the
    container happens to ship.

21. **§6.9 had been implemented before it had been written down.** The section describing the
    largest change in the milestone was missing from the first draft of this document while the
    code was already in the tree — which is the exact fault §6.4 opens by naming, committed by
    the document that names it. It is written now. Recorded rather than silently repaired,
    because a deviations ledger that omits the deviation its own author made is worth nothing.
