# P10 — The chord that was not a key

*Repairs the two features CORE §4 promises and `v1.0` shipped with no reachable entry point at
all: copy-out and paste-to-stage. Then repairs the reason the repair could not have been
released — a version gate that permitted exactly one tag per version. When this file and CORE.md
disagree, CORE.md wins.*

**Goal in one sentence:** `Ctrl+C` copies entries out and `Ctrl+V` stages files in, because the
program now listens for what a clipboard chord actually is by the time it arrives — released as
**`v1.0.0-2`**, the first revision INDIUM has ever cut.

P9.md's closing left no claim about a P10, which was the right call twice over: P10 is not a
milestone anybody planned. It exists because P8 §5's manual checklist was finally run against a
released binary and two of its boxes would not tick — and the first thing that stopped them was
not a multi-window fault at all, but `Ctrl+C` doing nothing whatsoever. Every automated test in
this repository passed on the day that shipped, and passed for the same reason they had passed
for seven milestones: not one of them can open a window, and the fault lives entirely in the
half-inch between a key being pressed and the program being told about it.

**Not in P10:** everything. This is a revision, not a milestone. No new feature, no new popup,
no new format, no visual change, no change to the multi-window path. The second defect the same
checklist found — `self.cursor` clamped against the archive table's rows while indexing the
recents list, P8 Deviation 10 — is deliberately **not** fixed here; it is older, it is not what
the maker asked for, and a revision that quietly picks up a second unrelated fix is a revision
nobody can reason about. It stays open.

## 1. A clipboard chord is not a key

CORE §4's keyboard table has read `Ctrl+C | Copy out` since P3 and `Ctrl+V / drop files | Stage an
add` since P4. The README advertises both. Neither has ever worked in a released binary.

The code that shipped in `v1.0` asked the obvious question:

```rust
i.modifiers.ctrl && i.key_pressed(egui::Key::C)
```

and the answer is `false`. It has always been `false`. It is `false` for every `Ctrl+C` that has
ever been pressed at this program, on every machine, because of eleven lines in a dependency:

```rust
// egui-winit-0.36.1/src/lib.rs
if let Some(active_key) = logical_key.or(physical_key) {
    if pressed {
        if is_cut_command(self.modifiers, active_key) {
            self.egui_input.events.push(egui::Event::Cut);
            return;
        } else if is_copy_command(self.modifiers, active_key) {
            self.egui_input.events.push(egui::Event::Copy);
            return;
        } else if is_paste_command(self.modifiers, active_key) {
            …
            return;
        }
```

The three clipboard chords are matched *before* anything is emitted, converted into
`Event::Copy` / `Event::Cut` / `Event::Paste`, and the function **returns**. The `Key` event is
never produced. `Ctrl+A`, `Ctrl+F` and `Ctrl+O` all work perfectly, and they work for the same
reason these do not: egui-winit special-cases exactly three chords and lets everything else
through, so the surrounding code looks correct because it *is* correct — for every chord but
these.

**This is not a shortcut that stopped working. It is a feature with no entry point.** `copy_out`
has exactly two call sites in the whole tree: the dead chord, and `password.rs`, which resumes a
copy-out that has already begun and therefore can never begin one. CORE §9 forbids drag-out —
*"clipboard copy-out is the mechanism"* — so there is no menu item, no button and no second path
by design. From P3 until here, copying anything out of an archive was impossible. Paste lost the
same way, except that dropping files onto the window arrives through `dropped_files` on an
entirely different path and has worked throughout; the drop half of CORE §4's row was carrying
the whole row.

The fix is to ask for what arrives:

```rust
fn clipboard_chords(events: &[egui::Event]) -> (bool, bool)
```

read once per frame in `handle_keys`, feeding the same two `if` bodies behind the same two
guards. `has_archive()` and `!typing` are untouched, and the second is load-bearing: a focused
`TextEdit` answers `Event::Paste` itself, and `handle_keys` runs before any panel is shown, so
without the guard a `Ctrl+V` in the filter bar would both fill the field and stage an add.

Both spellings are accepted — the event, and a `Ctrl`-modified `Key::C`/`Key::V` — for a reason
worth stating: an egui that stopped swallowing the chord would kill this feature a second time in
exactly the same way, silently, and the cost of surviving that is four lines. The return type is
two `bool`s, so an egui that emits *both* forms still acts once. `Event::Cut` is deliberately not
answered: CORE §4 has no `Ctrl+X`, and an archive manager that cuts is one that deletes on a
paste that may never come.

### Why nothing caught it

Because nothing could. 223 automated tests pass and not one of them can open a window, so none
of them can press a key; the fault is entirely in the conversion of a keystroke into an event,
which is a thing only a running program on a real display does. The clipboard module itself is
exercised hard — thirteen tests over URI encoding, CRLF line endings, comment and foreign-scheme
handling, one of which wants a live Wayland session and is `#[ignore]`d for it — and every one of
them passes, because the clipboard layer was never broken. It was simply never called.

Two features were shipped broken through seven milestones. The first time anybody actually
pressed the keys, both fell over inside a minute. That is the argument for P8 §5's manual
checklist stated as plainly as it can be stated, and it is why P10's own checklist below is
short and about pressing keys.

## 2. The gate that made a second release impossible

The version bump uncovered a second fault, in the workflow, and it is the more interesting one
because nothing was wrong with it until the day it mattered.

`release.yml` derived the tag it would accept from Cargo.toml:

```sh
if [ "$GITHUB_REF_TYPE" = tag ] && [ "$GITHUB_REF_NAME" != "v${VER%.*}" ]; then
```

`${VER%.*}` strips the last component, so `1.0.0` gives `1.0` and the only acceptable tag is
`v1.0`. That is exactly right for a first release and exactly wrong for a second: `v1.0` had
already been pushed, and a tag is pushed once. With the version unchanged there was **no tag in
existence that this workflow would build.** Bumping Cargo.toml to `1.0.1` would not have helped
either — `${VER%.*}` gives `1.0` again.

A gate that permits one release per major.minor for ever is not a gate, and a fix that cannot be
released is not a fix. The rule now follows the revision, which is the number that actually
distinguishes one build of a version from another:

| `pkgrel` | Tag the workflow will accept |
| --- | --- |
| `1` | CORE §7's two-numeral form — `v1.0` |
| `>1` | The revision carried in the tag — `v1.0.0-2` |

This is **stricter** than what it replaced, not looser. Before, a tree with `pkgrel=2` tagged
`v1.0` would have built happily and produced a second, different set of artefacts under the first
release's name. Now it is refused by name in the log.

### One number, six readers

`pkgrel` becomes the single source of truth, and the reason is that the literal `1` had already
spread further than anybody would guess: `make-deb.sh` held its own `REVISION=1`,
`tests/package_path.rs` had two, and `verify.sh` had **five** — both default artefact paths, the
`.PKGINFO`'s expected `pkgver`, the `control` file's expected `Version:`, and the expected first
line of the changelog. Eight copies of a number that had never changed.

The day it changed, the failures would have been ugly in a specific way: `verify.sh`'s two
default paths would have pointed at artefacts that no longer existed, and every check that opens
a package would have gone to **SKIP**. A skipped check reads as "nothing wrong". P6 §5 already
argued that a verifier which quietly stops verifying is worse than no verifier; this is that
argument arriving in the post.

The eighth copy was not found by reading. See Deviation 7.

### The tarball would have shipped a lie

The tarball was named from the short version — `indium-1.0-x86_64.tar.gz` — which cannot express
a revision at all. A `1.0.0-2` build would therefore have produced a tarball with **byte-different
contents under exactly the filename `v1.0` already ships**, and GitHub namespaces assets per
release, so nothing would have complained. Two different binaries answering to one name is the
precise failure P8 spent a milestone arguing against, in the artefact with the least opportunity
to warn anybody, since a tarball declares no dependencies. It is now
`indium-<ver>-<rel>-x86_64.tar.gz`, which matches how both packages have always named themselves.

## 3. The CORE edits

CORE §4's keyboard table needs **nothing**, and that is worth writing down: it promised `Ctrl+C`
and `Ctrl+V` correctly for seven milestones while the program failed to deliver them. CORE was
right and the code was wrong, which is the direction this project is built to assume and the
first time it has been demonstrated at this cost.

### Edit 1 — §7, the tag rule

CORE §7 opens *"Tags are two-numeral: `v0.1`, `v0.2`, … `v1.0`, `v1.1`."* `v1.0.0-2` is not that,
and the maker chose it deliberately over `v1.0.1`. The document has to say so or the next reader
finds a tag the rules forbid.

**Find:**
```
Tags are two-numeral: `v0.1`, `v0.2`, … `v1.0`, `v1.1`.
```

**Replace with:**
```
Tags are two-numeral: `v0.1`, `v0.2`, … `v1.0`, `v1.1`. A tag that fixes a released
version without changing it carries the package revision instead of a third numeral —
`v1.0.0-2` — because the thing being distinguished is the build and not the version.
The release workflow derives which of the two forms it will accept from `pkgrel`, so
the rule is enforced rather than remembered.
```

### Edit 2 — §7, the road table

P10 is not on the road to v1.0; it comes after it. The table's last rows are P6 through P9 as
reconciled in the standing apply-list (Op 14), and this appends one more.

**Find (the last row, as it stands *after* the apply-list's Op 14 is applied):**

| P9 | The popup's own three grounds, and the popup that stopped outgrowing its window | **`v1.0`** |

**Replace with:**

## 4. Tests

No new fixtures, and no new integration test. What P10 pins is the shape of an event list, which
needs nothing on disk.

| Test | What it pins |
| --- | --- |
| `the_copy_chord_is_answered_when_it_arrives_without_its_key` | The bug itself: `[Event::Copy]` and no `Key` beside it, which is exactly what egui-winit produces |
| `the_paste_chord_is_answered_when_it_arrives_without_its_key` | The other half, and that the payload is ignored — `request_paste` does its own `text/uri-list` read |
| `either_spelling_of_the_chord_is_answered_exactly_once` | An egui that stops swallowing the chord must not kill the feature again, and one that emits both forms must not act twice |
| `nothing_else_is_mistaken_for_a_clipboard_chord` | `Event::Cut`, `Ctrl+X`, a bare `C` and an empty frame all do nothing |

Named after the bug and not the property, which is P7 §8's rule.

These four are worth exactly as much as their limits admit. They prove that *given* the events
egui-winit produces, INDIUM now answers them. They cannot prove egui-winit produces those events,
because that is a claim about a dependency on a real display — so the empirical half of P10 is in
§5's checklist and not here, and it is the half that matters.

`tests/package_path.rs` gains no test but stops hardcoding the revision in both artefact paths,
which is what stopped its eight `--ignored` package tests from silently pointing at files that do
not exist.

## 5. The release ritual

P6 §6's ritual as amended by P8 §6 — nothing built on the maker's machine — with the version step
changed:

1. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. All green
   before anything else. The workflow runs the same three inside `debian:bookworm`, but burning a
   rehearsal on a formatting slip wastes ten minutes for nothing.
2. Commit in house style, `P10: <what>`, no trailers. **This document goes in before the tag**,
   so it ships inside the release rather than after it — the fault P9 Deviation 1 recorded and
   this milestone is the first chance to not repeat.
3. Push to `master`.
4. **`workflow_dispatch` on master, watched green.** The tag does not exist yet, which is the
   whole point: the new gate, the derived revision and the renamed tarball are all first-run code
   and every one of them can fail. On a dispatch `pkgrel=2` puts the gate in its `>1` branch and
   the tag check is skipped entirely, so the rehearsal proves the build and not the gate.
5. **Press the keys.** Download the rehearsal's tarball, run that binary, select entries, press
   `Ctrl+C`, and read `wl-paste --list-types` for `text/uri-list`. This is the only step that can
   prove P10 did anything, for the reason §4 gives; it also closes P3's box 2, open since P3.
6. `git tag v1.0.0-2 && git push origin v1.0.0-2` — the form the gate now expects, refusing
   anything else by name.
7. Watch the tag run green. `verify` judges both packages together and must stay at **zero
   skips**.
8. Release from the sudo-megas account, three artefacts attached, notes naming the fix and
   nothing else.
9. `cmp` the released tarball's binary against the one inside the `.deb`. They come off the same
   build and must be byte-identical, as they were for `v1.0`.

## Deviations

*(recorded during implementation; empty is a valid state)*

1. **A revision is being spent on a source change, which is not what a revision means.** Both
   Debian and Arch reserve `pkgrel` for rebuilds of unchanged upstream source — new packaging,
   same program. `1.0.0-2` is a different binary from `1.0.0-1`. The maker chose this form over
   `v1.0.1` when both were on the table, so it is recorded rather than argued: the consequence is
   that **the About popup still reads `1.0.0`**, because Cargo's version is unchanged, and a user
   comparing About against the package they installed will see two different strings. Both are
   true. Neither is discoverable from the other.

2. **The fix was diagnosed against a released binary, not written against a failing test.** There
   was no test to fail. The chain — chord swallowed, key never emitted, watcher never fires — was
   read out of the dependency's source after the behaviour was observed twice on a real display,
   and the tests in §4 were written afterwards to pin the shape that was found. Tests-after is
   the honest description and it is what happened.

3. **P10 accepts a key form that this egui never sends.** `clipboard_chords` answers a
   `Ctrl`-modified `Key::C` as well as `Event::Copy`, and against egui-winit 0.36.1 that arm is
   dead code. It is speculative by construction, which this ledger usually treats as a fault. It
   is kept because the failure it guards against is the one that just cost seven milestones, it
   is four lines, and a `bool` cannot double-fire. Recorded so the next person to read it knows
   it was a decision and not an oversight.

4. **`Event::Paste` only fires when the clipboard carries text.** egui-winit calls
   `clipboard.get()` and pushes nothing at all when that comes back empty — so a clipboard
   offering `text/uri-list` and no `text/plain` would still be missed, even by the fixed code,
   and INDIUM's own `paste_paths()` would have read it correctly if it had ever been asked.
   Harmless in practice: Dolphin, Nautilus and Thunar all offer plain text beside the URI list.
   Not fixed here because fixing it properly means reaching past egui for raw winit events, which
   is a change to how the program receives input and has no business inside a revision. P8
   Deviation 11 was written before this was known and does not mention it; it is recorded here
   rather than edited into that document, because a milestone's ledger is what was known then.

5. **The workflow fault was found by trying to release, not by reading.** §2's gate was read
   through twice during P8 without anybody noticing that it admitted exactly one tag, because at
   the time exactly one tag was all it needed to admit. It surfaced only when the second release
   was actually attempted. There is no lesson here about better reading — the code was correct
   for every situation that had ever existed — only that a release path is not proven by any
   number of releases that were all the first one.

6. **`SHORT` was removed from three jobs.** Once the tarball carried the full version and
   revision, `SHORT=${VER%.*}` was set in all three jobs and read by none. Deleting a variable is
   outside what P10 was asked to do; leaving a dead assignment in a file whose entire argument is
   that a reader can see the whole provenance is worse.

7. **The eighth copy of the revision was found by the rehearsal, after seven were found by
   grep.** `verify.sh`'s `.PKGINFO` check builds its expected field as `"pkgver = ${ver}-1"`, and
   no search for the literal string `1.0.0-1` can match a line that never contains it — the
   number is assembled at run time out of two pieces. Seven copies were found by pattern and the
   eighth by dispatching the workflow and reading `FAIL: .PKGINFO has no 'pkgver = 1.0.0-1'
   (found: pkgver = 1.0.0-2)`. Recorded because the lesson generalises past this file: a grep for
   a constructed string finds the places that spell it out and silently misses the places that
   build it, and those are the same places most likely to be a check. The rehearsal step exists
   for exactly this and earned itself again — the first run stopped at **35 passed, 1 failed, 0
   skipped**, on a tag that did not yet exist.
