# P4 — Stage, apply, prove

*Implements CORE.md §3 `tasks`, §4's tray and its first two popups, and §5's write half.
When this file and CORE.md disagree, CORE.md wins.*

**Goal in one sentence:** INDIUM stops being a reader — files are added, removed and
renamed into a queue you can see and undo, a new archive is built to a recipe you choose,
and **Apply** proves the replacement before the original is touched — tagged `v0.4`.

**Not in P4:** Preview, icon integration, the look-and-feel pass (P5); packaging and
system-wide install (P6). No in-place editing, ever — CORE §9, and §2 below is why.

## 1. The staging engine

CORE §3: *"Every mutation — add, remove, rename, create — is a task in a queue."* Four
task kinds, no more, and the queue lives on the window beside the selection.

Tasks key on the **staged** path — the path as the table shows it *after* every earlier
task — which is the same `String` currency the selection already uses, and for the same
reason: a staged change must survive descending into a directory, filtering, and
re-listing. Rename an entry, then rename it again, and the second task names what the
first produced. Renames compose and need no special case.

**The queue is ordered, and it is what you edit. Apply never replays it.** Replaying a
list of mutations against a real archive is how half-written archives are made. Instead
Apply folds the queue **once**, through a pure function, into a plan: one disposition per
member of the source — kept under some name, or dropped — plus the list of new members to
append. The fold is where nearly all of this milestone's test value sits, because it is
pure: no archive, no filesystem, no window.

The plan's dispositions are **indexed by source position, not keyed by path.** A tar may
legally hold two members with the same stored name; a path-keyed lookup breaks on that
silently, and silence is the one failure this program does not permit.

Fold rules, each with its reason:

- A remove takes a directory's whole subtree, and cancels any pending add beneath it.
  Add-then-remove leaves the path gone, which is the only intuitive reading.
- A rename rewrites the path prefix of every live descendant, and preserves a directory's
  trailing `/` — write a file where a directory was and the archive is wrong.
- An add whose name collides with a survivor **replaces** it. That is what dropping a file
  onto an archive means everywhere else, and the `W` row says so rather than leaving you
  to discover it.
- Hardlinks fold twice. A tar hardlink names a member written earlier in the same archive,
  so renaming a target must retarget every link that pointed at it; and removing a target
  while a link survives is refused, because the data lives with the target and the
  surviving link would extract broken.

Conflicts are checked **when the task is staged**, against the current view, so an invalid
task never enters the queue and you learn immediately rather than at Apply. The fold
re-checks everything anyway: the archive can change on disk between staging and Apply, and
a guard that depends on two passes agreeing is not a guard. Removing a row from the queue
re-folds it, because a sequence can be orphaned by a deletion in its middle.

Two refusals belong here rather than in a later apology:

**A format INDIUM reads but CORE §5 does not list as writable cannot be staged against.**
cpio, ar, xar, mtree, iso9660, cab, lha, deb, rpm — the gate is up front and says so:
*"INDIUM reads cpio but does not write it. Nothing can be staged here."* Without this,
P4 would quietly turn a `.cab` into a tar.

**An encrypted zip cannot be staged against either.** CORE §9 forbids writing encrypted
zip, so a rebuild would necessarily store those members unprotected — a silent security
downgrade, and the only place in P4 where one is possible. Deciding neither way is the
only wrong option.

**Create is a task.** New Archive stages one into an empty queue and writes nothing: the
window adopts the chosen path, the entry list is empty, and the tray appears reading *"1
change — create photos-2026.7z."* Add files, then Apply, and the same engine builds it
through the same lock, verify and rename. The alternative — writing an empty archive when
the popup closes — touches the disk before you have staged anything, which is exactly the
surprise CORE §3's ethic exists to prevent.

## 2. Apply

The sentence this milestone is judged by is CORE §3's: *"builds the new archive in a temp
file beside the target, verifies it by walking its entries, then atomically renames over
the original. The original is never touched until the replacement is proven."*

In order:

1. **Take the lock.** Carried forward from P3 §4, which has held this requirement since it
   had nowhere to go: *Apply takes an advisory lock on the archive path so two windows
   cannot rebuild the same file.* `std::fs::File::try_lock` does it with no crate and no
   FFI, and the lock is held across build, verify and rename. Refused, it says so and
   writes nothing: *"Another INDIUM window is rebuilding this archive."*

   **But it must not be a lock on the archive file itself, and this is not a detail.**
   `File::try_lock` is `flock(2)`, whose lock lives on the *inode*, not on the name. Apply
   ends by renaming a different inode over that name — so the moment the first rebuild
   commits, the lock holder is holding a lock on an unlinked inode nobody can reach, and
   the next window to open the archive gets the new inode and locks it successfully.
   Measured on the build machine rather than reasoned about:

   ```
   PARENT try_lock            -> Ok(())
   CHILD  before rename       -> Err(WouldBlock)     the lock works
   CHILD  after  rename       -> Ok(())              the lock is gone
   ```

   The guard would therefore hold on the first Apply and silently fail on every one after
   it — which is precisely the case it exists for, since a second rebuild is what a second
   window is doing. So the lock is taken on **a lock file keyed by the archive's path,
   under `$XDG_RUNTIME_DIR/indium/locks/`**, which nothing ever renames over. The same
   probe confirms it survives:

   ```
   PARENT sidecar try_lock    -> Ok(())
   CHILD  sidecar after rename-> Err(WouldBlock)     still held
   ```

   It lives in the runtime directory rather than beside the archive so INDIUM leaves no
   litter in the user's folders, and so the session's own logout wipe clears anything a
   crash leaves behind; `platform::scratch` already owns that directory and its
   cache fallback for a machine with no `$XDG_RUNTIME_DIR`. Two paths that reach the same
   file by different routes — a symlink, a bind mount — are not detected as the same
   archive; the requirement is two *windows* on one path, and that is what is delivered.

   Creating a new archive additionally opens the target with `create_new`, which fails
   with `AlreadyExists` and so doubles as the check that a new archive never silently
   clobbers an existing file.

   State plainly in the release notes that the lock is advisory — it stops a second
   INDIUM, not a program that never asks.
2. **Re-list the source** in the worker. If its set of paths differs from what the queue
   was staged against, refuse: *"The archive changed on disk. Nothing was written."* One
   header pass, and exactly the paranoia the sentence above asks for.
3. **Fold** into the plan. A conflict here fails before a byte is written.
4. **Build** into a temp beside the target, streaming one pass over the source and then
   the adds, checking the cancel flag between members.
5. **Finish and sync.**
6. **Verify** by walking the temp's entries: the count, the exact set of paths, and the
   size of every regular file. Compare on normalised paths, because zip, 7z and tar
   disagree about trailing slashes on directories and INDIUM's own view is the honest
   common currency; compare sizes for regular files only, because a tar hardlink has size
   zero and a zip symlink stores its target as data, and failing `meta.tar` for that would
   be reporting a bug that is not there.
7. **Commit** — rename, then sync the parent directory, because the durability of a rename
   needs the directory synced too. Steps 5 and 7 together are `store::atomic_write`'s five
   steps wrapped around a streaming writer; it cannot be called directly, since it takes
   the whole file in memory.
8. **Clean up.** On any failure, and on cancel, remove the temp and leave the original.

Verification is a **reading** of CORE §3, and it is stated as one so the maker can
overrule it: *verification proves the new archive is structurally complete and names every
member it should, at the size it should. It does not re-checksum the data; the
compressor's own integrity check does that on extraction.* Re-reading every byte would
double Apply's cost — minutes on a large archive — to catch a class of failure the codec
already catches.

One quiet benefit worth naming: a 7z written by `sevenz-rust2` is verified by reading it
back through **libarchive**, a genuinely independent implementation.

**The rebuild streams. It never extracts to a temporary tree and repacks.** That would
double peak disk use; it would write an encrypted archive's plaintext onto the disk,
against the whole grain of CORE §9; and it would lose metadata no filesystem can hold —
owner *names* for users that do not exist locally, hardlink identity, exotic modes. Kept
members hold their source order and new ones are appended: INDIUM does not re-sort an
archive, member order is invisible behind a sorted table, and single-pass streaming
depends on it.

**The temp file and what a crash leaves.** The name is deterministic — a dotted name
ending `.indium-new`, beside the target, recognised by a strict predicate before anything
is ever deleted. Determinism *is* the orphan policy: a crashed Apply leaves exactly one
leftover per archive rather than an accumulating pile, and the next Apply on that archive
removes it with a notice. INDIUM sweeps no directory it was not pointed at, and will not
go looking through your disk for its own litter.

**Passwords.** A source that is encrypted rides P2's existing park-and-resume path. An
encrypted 7z being rebuilt is re-encrypted with the password you gave to read it — one
prompt, and no change-password screen CORE never asked for; *"to change the password,
create a new archive."* A new encrypted archive holds no password in the popup (CORE §9:
typed per use) and is asked at Apply, **twice**, because there is nothing to verify
against and a typo would produce an archive nobody can open.

## 3. The write path

Two backends behind one small interface, because CORE §5 splits the work: libarchive
writes `tar` with `gz`, `bz2`, `xz`, `zst`, `lz4`, and `zip` with Deflate; `sevenz-rust2`
writes 7z with LZMA2, and is the only road to AES-256.

`arch.rs` grows a write half that mirrors its read half — the write handle, the format and
filter setters, options, header, data, close; entry construction and the metadata setters.
Every declaration is checked by hand against `/usr/include/archive.h` and
`archive_entry.h`, exactly as the read half was, and every one is used. No `-sys` crate
and no bindgen; that rule does not bend because the file got longer.

A failure to set options is a **hard error**, never swallowed. Silently dropping the
compression level you chose is the kind of quiet lie this program does not tell.

`sevenz-rust2` lives in its own module rather than inside `arch.rs`, whose own first line
declares it hand-written FFI over the system libarchive. Modules outside CORE §3's table
already exist — `secret`, `util`, `theme` — so this needs no CORE edit, but it is recorded
in Deviations rather than assumed.

**What each format can carry, stated rather than discovered:**

| | tar | zip | 7z |
| --- | --- | --- | --- |
| mode, mtime | yes | yes | yes |
| uid / gid | yes | no | no |
| owner **names** | yes | no | no |
| symlink | yes | yes | no |
| hardlink | yes | no | no |

"The metadata is the main event" means telling you when metadata is about to die, so a
rebuild that changes format shows what the target cannot hold, before Apply, not after:
*"zip does not store owner names — indiumuser:indiumgroup will not survive."* A rebuild
that keeps its format loses nothing, so the note stays quiet where it should.

## 4. 7z, in both directions

CORE §2's sentence for `sevenz-rust2` promises two things — AES-256, which libarchive
cannot write, and *"7z-specific detail (solid blocks) the generic reader does not
expose"*. P4 collects both, and closes a hole P2 could not.

Routing lives in `arch`, the implementation in `sevenz`, and `Entry` stays the single
currency so the rest of the program keeps calling `arch::list_all` and never learns there
are two readers. The split is deliberately asymmetric:

- **Listing** a 7z goes to `sevenz` first, falling back to libarchive if the header will
  not parse.
- **Data** — extraction, CRC32, passphrase checks — goes to libarchive first, and to
  `sevenz` only where libarchive refuses.

The reason must be written down so it is not reopened: the crate is taken with its default
features **off**, carrying only AES-256 and the LZMA2 encoder, so it has no bzip2, ppmd,
deflate or zstd decoder. It parses headers broadly; it does not decode all data. Making it
the sole 7z reader would be a read regression against CORE §5's promise to read everything
libarchive reads. The invariant this split rests on gets a test of its own: both readers
must produce the same set of stored names for the same archive.

**Encrypted 7z headers now list.** P2 §6 wanted *"with the passphrase, lists and
extracts"* and could not have it — libarchive 3.8.9 answers every header on
`secret-headers.7z` with *"currently not supported"*, with or without the password, which
P2 recorded as its first Deviation. `sevenz-rust2` parses them natively. The prompt and
the flow have been waiting since P2; P4 puts a reader behind them.

**Packed size arrives, and it arrives honestly.** The crate reports a compressed size per
**block**, not per entry, attributing the block's packed size to the first file in it;
every other file in a shared block carries nothing. So the rule is:

> An entry's packed size is reported when that entry is the sole occupant of its block.
> When a block holds several entries, apportioning it between them would be a guess, and
> INDIUM shows nothing rather than guess.

**Gate that on the block's occupancy, never on whether the crate left a number behind.**
The committed `basic.7z` is solid — one block, three files — and the crate still stamps
the whole block's 45 packed bytes onto `alpha.txt`, because it happens to be first. A
check of the form "report it if it is not zero" would therefore show 45 for `alpha.txt`
and nothing for its two block-mates: wrong, and plausible enough to survive review.
Count how many entries name a block and report only where that count is one.
`basic.7z` is the fixture that catches this, and under the rule above it correctly yields
nothing for all three.

Block-level truth belongs to the archive, so the archive card gains it: whether the
archive is solid, and how many blocks it holds. That is what discharges CORE §4's promise
that *"7z solid-block detail arrives with `sevenz-rust2` in P4"* — satisfied, not
contradicted.

Five places currently say packed size is always absent, and they move together in one
commit: `Entry::packed`'s doc, two comments in `arch`, the aggregate's doc in `model`, the
Inspector's note, and the table's. `packed_size_is_absent_rather_than_guessed` is **not**
among them — it asserts against `basic.zip`, where libarchive still exposes nothing, so it
stays exactly as written and keeps guarding the zip path. It gains a sibling asserting
that a solid 7z reports nothing either.

**Where INDIUM's password hygiene stops, said out loud.** `secret::Secret` wipes its bytes
on drop, and `Reader`'s own doc already admits the guarantee covers our memory and not
libarchive's copy. The 7z crate is worse and must be recorded rather than glossed: its
`Password` has no `Drop`, derives `Clone` and is cloned several times into the writer's
own structures, derives `Debug` — so printing one anywhere would print the password — and
its key derivation caches the derived key in a process-global that is never cleared. CORE
§9's "passwords are never stored or remembered" still holds for everything INDIUM writes
to disk, which is what that rule is about; but the in-memory claim ends at the crate
boundary, and no wording in the window may imply otherwise.

One more, for the record rather than for action: when headers are encrypted the crate
reuses the content stream's salt and initialisation vector for the header. That is CBC key
and IV reuse across two plaintexts. The alternative it offers is leaving every filename in
the clear, which is worse for an archiver, so P4 takes encrypted headers and writes the
tradeoff down here.

## 5. The window

**The staging tray** — CORE §4's fourth zone — is a second bottom panel registered after
the status bar, so it stacks above it. It does not exist until the first staged change,
then it is one line: the count, a summary of the first tasks, *Discard*, **Apply**. It is
orange, which is the second of the three meanings CORE §6 reserves that colour for, and
the first time INDIUM has had cause to use it. The whole strip is a button that opens the
task list; the buttons drawn inside it consume their own clicks first.

**Pending tasks (`W`, or clicking the tray)** is the standard popup: one row per staged
operation with its own remove `×`, the target sentence, any metadata note, *Discard all*
and **Apply**. An empty queue reads *"Nothing staged."* rather than refusing to open —
a popup that will not appear teaches you nothing.

**New Archive (`N`)** is CORE §4.1, to the letter: the instruction line; four preset chips
— *Fastest*, *Balanced*, *Smallest*, *Encrypted* — each highlighting a row in the method
list below, where every method carries its one-sentence verdict from CORE §5, **verbatim,
held in one place and pinned by a test**; an *Advanced* disclosure holding the level
slider; and at the foot the live sentence stating exactly what will be built. The presets
are not arbitrary — each is the method whose own verdict claims that virtue.

**The keys** CORE §4 has listed since the beginning and P1–P3 answered with a promise:
`N` and `W` open their popups, `Del` stages a remove, `F2` starts a rename, `Ctrl+V` and a
file drop stage adds. `Ctrl+V` needs the clipboard's read half, which P3 never built —
copy-out only ever wrote. Dropping files currently opens the first one as an archive and
**silently discards the rest**; with an archive open it now stages every path, and with
none it opens the first, as before.

**Rename happens in the table, not in a popup.** CORE §4 says *"Five fixed zones and seven
popups. Nothing else appears, ever."* — an eighth would be a CORE edit, and this does not
need one. `F2` swaps the Name cell for a text field; `Enter` commits, `Esc` cancels. It
also earns something for free: a focused field is what already suppresses bare-key
shortcuts, so `Del` cannot fire into a rename. The last component only — moving an entry
between directories drags in a family of questions (renaming into a directory that is
itself staged for removal, and its cousins) that v0.4 deliberately does not open.

## 6. Four things P4 inherits, and fixes

Each was found while planning this milestone, each is real today, and each gets worse the
moment P4's surfaces land.

1. **Bare keys fire through an open popup.** The keyboard is guarded only by "is a text
   field focused", and About and Settings never focus anything — so with either open, `E`,
   `A`, `,`, the digits, `Space` and the arrows all fire straight through and silently
   swap the popup. P4's two new popups are full of chips, rows and sliders that hold no
   focus, which would make it worse. The bare-key block gains an explicit guard; the Ctrl
   chords keep working, as they should.
2. **A progress bar does not move.** egui is in reactive mode, which repaints on input;
   the listing spinner asks for its own repaints and so keeps the pump alive, but the
   progress bar does not, and the worker holds nothing it could ask with. Extraction's bar
   therefore advances only when the mouse moves. The drain requests a repaint while any
   operation is in flight — self-sustaining, stopping exactly when progress clears, and
   keeping `egui` out of `arch` and `tasks` entirely.
3. **A cancelled extraction is indistinguishable from a finished one.** It returns the
   same success with a partial tree on disk and says nothing. Apply must not inherit that,
   so cancel is a state of its own; and while the reader is open, extraction learns to say
   *"Cancelled — 12 entries were already written to /home/megas/out."* This reaches past
   P4's stated surface, and is logged in Deviations for it.
4. **`Esc` on the password prompt leaves the typed password in memory.** Closing clears the
   popup and the parked action but not the string, and the routine that would have wiped it
   is unreachable by then. CORE §9 says passwords are typed per use and wiped after; today
   an abandoned prompt keeps its plaintext until the next one overwrites it. Every close
   path routes through one function that clears all of it — which P4 needs anyway, having
   added a second password flow.

## 7. Fixtures and tests

New fixtures (commands recorded in `tests/fixtures/README.md`; fixtures may be born from
any tool on the build machine — INDIUM itself still shells out to nothing):

- a **non-solid** 7z, one block per file, which proves packed size is *reported*:
  `bsdtar -c --format 7zip --options compression=store $COMMON -f nonsolid.7z alpha.txt
  beta.txt sub` — `compression=store` is the only lever libarchive 3.8.9 offers here, and
  it gives the Copy coder one block per entry. `--options solid=off` and `7zip:solid=off`
  are both rejected outright, so a *mixed* archive cannot be built on this machine at all.
- a single-file 7z with a compressible payload, so packed is genuinely smaller than real —
  `alpha.txt` is 21 bytes and LZMA *expands* it, and a `store` fixture has packed equal to
  real, so neither on its own would catch an implementation that put the uncompressed size
  in the packed column.

The solid case needs no new fixture: `basic.7z` already is one, verified by parsing its
header rather than assumed — a single LZMA block of 45 packed bytes holding all three
files, with the three payload CRC32s matching the README's table exactly.

Note also that `py7zr` and `pyzipper` are **gone** — they lived in a `/tmp` venv that has
since been wiped. The py7zr cross-check below needs that venv rebuilt first, by the recipe
the fixtures README already records, and `secret-headers.7z` cannot be regenerated until
it is.

`cargo test` additions, at minimum. The fold is pure, so the whole of §1 is provable
without touching a disk:

- a plan over an empty queue is the identity — the load-bearing one, since Apply with
  nothing staged must reproduce the archive it read
- removing a directory drops everything beneath it; renaming one rewrites every child
  path and keeps its trailing slash
- two renames of one path compose into one; an add over an existing name replaces it
- a rename retargets every hardlink that pointed at the old name
- removing a hardlink target while a link survives is refused
- duplicate stored names are dispositioned independently
- an encrypted zip, and a format CORE does not write, cannot be staged against
- verification names a missing, an extra and a resized member, and compares sizes for
  regular files only
- every method verdict is CORE §5 verbatim, and the live sentence reads as CORE writes it
- the temp path sits beside the target and is recognisably ours; nothing else ever is

And in `tests/write_path.rs`, against real archives:

- an Apply with no tasks reproduces the archive, metadata included
- a removed entry is gone and every survivor is byte-identical, by CRC32
- **a failed Apply leaves the original untouched** — same bytes, same mtime, and no temp
  left behind
- a cancelled Apply does the same, and says it was cancelled
- a second Apply on a locked archive refuses, and writes nothing
- an orphaned temp is overwritten, not multiplied
- every writable format round-trips its payload
- **metadata survives a tar rebuild** — `meta.tar`'s symlink, hardlink, uid, gid, owner
  names and both mtimes. The flagship, because it is the sentence CORE opens with
- a zip rebuild loses owner names and says so
- both 7z readers agree on the same entry list
- `secret-headers.7z` lists with its password at last
- an AES-256 7z written by INDIUM opens in `py7zr` — `#[ignore]`d and run deliberately,
  as P3's live clipboard test is. CORE §1's "never shell out" governs INDIUM, not its
  tests

Manual checklist before release:

- [ ] stage a remove, a rename and an add on a copy of a real archive; open `W`; drop one
      row; Apply; re-open and confirm the result
- [ ] create a new AES-256 7z, add files, Apply, close, re-open with the password
- [ ] a wrong confirmation on the new-archive password is refused before anything is built
- [ ] open one archive in two windows; Apply in both; the second refuses and the first
      completes
- [ ] cancel a long Apply; the original opens unchanged and no `.indium-new` remains
- [ ] the tray appears on the first staged change and not before; orange only where CORE
      §6 permits
- [ ] drop three files onto an open archive; all three stage, not one
- [ ] `./build/check-deps.sh` still prints `OK: toolkit-free` — with `sevenz-rust2` linked
      in, this run is the one that proves the crate brought no baggage

## 8. The release ritual

```
cargo fmt
cargo clippy -- -D warnings
cargo test
cargo build --release
./build/check-deps.sh
git add -A
git commit -m "P4: staging, apply, new archive, 7z AES-256"
git push
git tag v0.4
git push origin v0.4
tar czf indium-0.4-x86_64.tar.gz -C target/release indium
```

`Cargo.toml`'s version becomes `0.4.0` in this milestone. No P-document has ever ordered a
bump, so `-V` and the About panel have reported `0.1.0` from a `v0.3` binary; that is a
step never written rather than a step skipped, and it is written now.

GitHub release on `v0.4`, pre-release, tarball attached, notes in the house voice —
including the advisory-lock sentence, the re-encryption sentence, and the plain statement
that verification checks structure and not checksums, each said before anyone has to
discover it.

## Deviations

*(recorded during implementation; empty is a valid state)*
