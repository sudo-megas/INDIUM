# P14 — the sidebar scrollbar threshold

*One defect, found by measurement after a long evening of not finding it, plus the four things
that were churning around it.*

## What it was

The maker runs a **1.25 display scale**. After P13 shipped, dragging the window edge made the
sidebar jump; at 100% the same drag was smooth. Two full testing rounds at 1.25 *before* P13 had
shown nothing, which is the fact that eventually solved it.

egui decides whether a `ScrollArea` needs a scrollbar with a bare comparison — no hysteresis, no
dead band. INDIUM sets `ScrollStyle::solid()`, so a visible bar **costs 10 points of width**, ramped
in over 0.2 seconds, with a repaint requested on every flip. At the one window height where the
sidebar's content equals its viewport, a drag across that height reflows the whole zone.

That height is arithmetic, not luck. The zone's content is a constant **≈257 points**; its viewport
is the window less the status bar (112), the frame (40) and the reserved foot (≈105). So the
crossing sits at a window of about **515 points** — and this compositor hands INDIUM **540**.
Twenty-five points of slack: about thirty physical pixels of drag.

**P13 is what put it there.** Before it, rows were ≈21.6 points and `SB_HEIGHT` was 100, so the
content was ≈232 and the foot ≈86, putting the crossing near **470** — seventy points below any
window this machine produces. The icons and the taller bar spent three quarters of that slack:
four content rows (+25), three foot rows (+19), `SB_HEIGHT` (+12).

At 100% the same physical window is **675 points**, so the slack is ≈160 and the crossing is
unreachable. That is the whole of "1.25 snaps, 100% is smooth" — not a rendering difference, an
operating point.

## What was fixed

1. **The sidebar's scrollbar floats instead of displacing.** A floating bar allocates no width, so
   egui's decision can flip without the zone reflowing. Shrinking the content was rejected: it only
   moves the crossing, and the compositor decides the window.
2. **The sidebar's foot panel was resizable by accident.** `Panel::resizable` defaults to `true` and
   this one never said otherwise, so it carried an invisible drag handle across the rule above
   *New* and remembered whatever height it was dragged to.
3. **The status bar's hairlines round to pixels, not points.** `.round()` snapped them to a whole
   point, which is 1.25 pixels here, so each rule straddled two rows of them and its share shifted
   as the window moved. `round_to_pixels` is `emath`'s answer and is the identity at 1.0.
4. **The entry table tracks the window again.** `resizable(true)` on the *builder* made
   `egui_extras` remember every column as exact after the first frame and ignore the available
   width — so widening left dead space to the right of *Method* and narrowing clipped. Only *Name*
   is resizable now, which is what `Column::remainder` meant. **This is probably the real "weird
   place" P13 chased**: that round read the dead strip as the cursor ring overhanging and made the
   ring follow the cells — correct in itself, but it matched the ring to a table that had stopped
   tracking.
5. **The elided path holds still.** Its budget now needs to be wrong by two columns before it
   re-cuts, and `elide_middle` gives the odd column to the tail every time instead of alternating —
   so one character appears at one end rather than both ends re-partitioning.

## What is not ours, and must not be chased again

**The window's own edge advances unevenly at a fractional scale, and no application can fix it.**
winit stores a Wayland window's size as `LogicalSize<u32>` and derives the physical size by
rounding: `959 × 1.25 = 1198.75 → 1199`. eframe divides straight back, `1199 / 1.25 = 959.20`. So
the only widths that exist are `959.2, 960.0, 960.8, 962.4…` and the physical sequence runs
`1199, 1200, 1201, 1203` — one pixel in four is skipped. It is unconditional for every eframe 0.36
application on a fractional-scale Wayland display; eframe never asks for a size back for the root
window, and INDIUM's only viewport command is the title. At 100% the conversion is the identity,
which is why it looks perfect there.

Also cleared, with evidence, so nobody re-opens them: `Panel`/`exact_size` layout is
`pixels_per_point`-independent end to end (egui rounds layout to 1/32 point, never to the physical
grid, and epaint's row heights carry no scale term); the resizable Inspector does not oscillate; and
the status bar's arithmetic is exact at both scales.

## And then the actual one

Everything above is real and worth having, and **none of it was what the maker was reporting.**
The report was *"jumped again"*, and the question that ended it was one nobody had asked: **what
jumps — the window's outline, or the contents inside it?** The answer was the outline, and that
ruled out every layout theory in a sentence.

INDIUM declared a minimum window of **840×600**. This compositor hands it a window **540 points
tall** — and KWin does not apply a minimum when it restores a remembered geometry, only when a
person grabs an edge. So the first pixel of any drag snapped the frame up sixty points before it
moved anywhere. At a scale of 1.0 the same physical window is 675 points, clears 600, and never
snaps — which is precisely why this looked like a fractional-scale defect for an entire evening and
was not one.

The floor is now **560×400**, far below anything in use. A floor's job is not to describe a
comfortable window; it is to refuse one nothing can be done in. Every zone gives way on its own long
before that, and the evidence had been sitting in the session all along: while the floor briefly sat
at 640×480, no jump was reported; it returned within an hour of the floor going back to 840×600.

**The lesson worth keeping:** the layout was measured and proven smooth — a one-physical-pixel sweep
gave `283.2 → 282.4 → 281.6`, linear and monotonic — *before* the right question was asked. Proving
the innocent innocent is not the same as finding the guilty.

## Deviations

1. **The sidebar's scrollbar floats; every other one in the program stays solid.** The first cut
   pinned it visible, which did stop the reflow and drew a track down a zone with nothing to
   scroll — *"idk if this is intentional… scrollbar is always visible now"*, and it was a worse
   thing to look at than the problem it solved. A floating bar allocates **no width at all**, so
   the decision may flip as often as it likes and the layout never moves, and the track is gone
   when it is not needed. Scoped to that one `Ui`, whose style is clone-on-write, so §6's solid
   bars survive everywhere else.
2. **The hysteresis on the path is two columns, not one.** One column would still change on every
   step; two halves the changes for a budget that can never overrun, because the label is truncated
   anyway.

## P14 is done when

- [x] The status bar's hairlines sit on physical pixels.
- [x] The entry table's *Name* column grows with the window.
- [x] The elided path does not re-cut itself on every few pixels of drag.
- [x] The declared minimum sits below the window the compositor actually hands out.
- [ ] Checked at the window, at **both** 125% and 100%.
