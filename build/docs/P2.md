## 1. `platform::store` — TOML, atomically, forgivingly

Two files, and the rules around them matter more than the fields:

- `$XDG_CONFIG_HOME/indium/settings.toml` (default `~/.config/indium/`) — what the user
  chose. Hand-editable on purpose; a hand edit in a text editor must be respected on the
  next launch.
- `$XDG_STATE_HOME/indium/recents.toml` (default `~/.local/state/indium/`) — what the
  machine remembers.

```toml
# settings.toml
[extract]
default = "subdir"        # "here" | "subdir" — which popover action is preselected

[[bookmark]]
name = "Downloads"
path = "/home/megas/Downloads"
```

```toml
# recents.toml
[[recent]]
path = "/data/backups/backup-2026.7z"
opened = 1786142074       # unix seconds; list is ordered by this, capped at 15
```

Rules:

- **Atomic writes only**: serialize to `<file>.tmp` in the same directory, `fsync`,
  rename over. The same discipline the archive rebuild will use in P4.
- **Malformed files are tolerated, never fatal**: on a parse error, copy the file aside
  once to `<file>.broken`, run on defaults, say so in the status bar. Never silently
  overwrite a file that failed to parse until the user changes something.
- Writes happen on change, not on a timer and not on every frame.
- Passwords never appear in either file, in any field, under any name (CORE §9).

`serde` + `toml` enter `Cargo.toml` here; their one-sentence justifications are already
written in CORE §2's table.

## 2. Sidebar sections go live

P1 rendered *Recent files* `1` and *Bookmarks* `2` muted. Now they are center views, the
JADEITE way: the sidebar selects what the center shows — *Archive* `3` is the table,
`1` and `2` are lists. With no archive open, INDIUM starts on *Recent files* with the
drop-a-file hint beneath.

**Recent files**: name in primary text, full path beneath in muted mono, ordered newest
first. Opening an archive (CLI, drop, `Ctrl+O`, or this list) bumps it to the top; the
list caps at 15. A missing file renders dimmed — `Enter` on it does nothing but a status
notice; `Del` removes the row. No automatic pruning: the list only loses entries by the
user's hand or the cap.

**Bookmarks**: named directories, because in an archiver a bookmark is an *extract
destination*. This view lists them; `Del` removes. They are consumed in two places: the
Extract popover's bookmark row (P1 stubbed it — un-stub it now), and the Settings panel.
Adding happens where the path is already in your hands: a small ☆ beside the popover's
path field pins the typed path (prompting only for a name), and the Settings panel has a
plain add row.

## 4. `Ctrl+F` — the filter bar

Appears between breadcrumb and table. While active, the table switches to **flat,
whole-archive** view — full paths, case-insensitive substring match, live as you type —
because the moment you reach for a filter in an 11,000-entry archive, the directory you
happen to be standing in is the wrong scope. The status bar reports *"214 of 11,482
match"*. Plain substring only in v1; globs are a temptation, not a requirement.

Mechanics: selection maps to real entries, so the Inspector and `E` extract work
unchanged on filtered rows. `Esc` priority order, fixed here for good: a focused filter
bar clears and closes first; then the topmost popup; then nothing.

## 5. Encrypted reads — ask once, wipe after

P1 already *lists* per-entry encryption (`archive_entry_is_encrypted`) and refuses
nothing. P2 makes the data readable.

**FFI additions to `arch`:** `archive_read_add_passphrase`,
`archive_read_has_encrypted_entries`.

**`src/secret.rs`:** a `Secret(Vec<u8>)` wrapper whose `Drop` overwrites every byte with
`core::ptr::write_volatile` behind a compiler fence — twenty lines, tested, no crate
(CORE §2's hand-written rule). One honesty note that goes in a code comment and stays
there: libarchive keeps its own internal copy of the passphrase for the reader's
lifetime; freeing the reader at the end of the operation is the best that exists. Our
copies are provably wiped; that one is freed.

**Two shapes of encryption, two flows:**

- *Encrypted entries, readable listing* (zip AES, most 7z): extraction proceeds normally
  until the selection includes an encrypted entry — which is known **before starting**,
  from the flags. Prompt first, verify by test-reading the first data block of the first
  encrypted entry with a throwaway reader, then run the real extraction with the
  passphrase preloaded. A wrong password re-prompts, three attempts, then cancels
  **before anything is written to disk** — no partial output to clean up because none
  was created.
- *Encrypted headers* (7z with encrypted filenames): the very first `next_header` fails.
  If the error string mentions the passphrase or `has_encrypted_entries` says so, prompt
  and reopen with the passphrase, same three-attempt rule, then a plain error.

The CRC *compute* action on an encrypted entry rides the same prompt.

**The prompt itself** is a modal popup: masked field, `Enter` confirms, `Esc` cancels,
nothing echoed anywhere, value carried as `Secret` end to end.

**The ordered CORE edit:** CORE §4 declares six popups and *"nothing else appears,
ever"* — the password prompt is a seventh. As part of this milestone, edit CORE.md §4:
the count becomes seven, and the list gains *"7. **Password** (modal). Appears at the
moment of use, per use, and nowhere survives it."* Commit that edit in its own commit,
message `CORE: §4 gains the password popup (ordered by P2)`. This is the deviation
protocol working as designed, not an exception to it.

## Deviations

*(recorded during implementation; empty is a valid state)*

1. **`secret-headers.7z` cannot be read by libarchive at all — §6's "with the passphrase,
   lists and extracts" is not reachable.** libarchive 3.8.9 returns `ARCHIVE_FATAL` and
   *"The archive header is encrypted, but currently not supported"* from every
   `next_header`, with or without `archive_read_add_passphrase`. The fixture is sound —
   py7zr reads it correctly — so this is a limitation of the reader, not the archive.
   What P2 ships is the half that is reachable: `archive_read_has_encrypted_entries`
   reports the situation, and INDIUM says so in a plain sentence rather than presenting
   an empty archive. `encrypted_headers_are_detected_and_reported_not_silently_empty`
   pins that it is never silently empty. The other half needs `sevenz-rust2`, which
   P1 §2 already defers to P4; the encrypted-headers flow in `arch` and the prompt are
   written and will work the moment a reader that can do it is behind them.

2. **Extraction resolves encryption before writing, not on failure.** §5 asks that three
   wrong attempts leave "no partial output to clean up because none was created". That
   does not fall out of the obvious implementation: libarchive creates the destination
   file and *then* fails to decrypt, so a wrong password left a zero-byte `secret.txt`
   behind. Caught by `a_wrong_password_errors_and_writes_nothing`. `arch::extract` now
   runs a pre-flight listing pass and settles everything knowable before touching the
   filesystem — traversal refused, encryption resolved from the entry flags, passphrase
   verified with the throwaway reader §5 describes. Only then does it open for writing.

3. **A `.broken` copy is never replaced.** §1 says "copy the file aside **once**". Read
   as: the *first* breakage is the one worth keeping, so if `settings.toml.broken`
   already exists a later breakage does not overwrite it. Pinned by
   `the_first_broken_copy_is_not_overwritten_by_a_later_one`.

4. **`Secret::from_str` is named `from_text`.** clippy rejects `from_str` as confusable
   with `std::str::FromStr::from_str`, and implementing that trait would mean returning
   a `Result` for something that cannot fail. Behaviour is unchanged.

5. **Zip mtimes in `evil.zip` and `secret.zip` are timezone-dependent** — Python's
   `zipfile` writes only DOS local time, so the same file reads back differently under
   different `TZ`. No test asserts an exact mtime on those two. `basic.zip` carries an
   extended-timestamp field and every tar is safe, so `meta.tar` is where timestamp
   round-tripping is proven.

6. **P1 and P2 were implemented in one pass, so no `v0.1` tag was cut.** The maker asked
   for both milestones consecutively; the tree that exists is the P2 tree, and tagging a
   `v0.1` reconstructed after the fact would name a state that was never separately
   built and checked. `v0.2` is tagged on what was actually verified. If the `v0.1` tag
   is wanted for the record, say so and it can be reconstructed and checked properly
   rather than back-dated.
